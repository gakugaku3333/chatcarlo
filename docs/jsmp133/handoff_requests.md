## 依頼 A: 治療領域（10 MV）の水ファントムを、対話の入口（scene.yaml → run）に接続する

### 目的
抄録 Methods の「最大 10 MeV の光子・電子・陽電子」と Results の依頼 1 を、**対話の入口から実際に実行した結果**で裏づける。
今、治療領域のコードは `prototypes/mv_electron/`（本番 `chatcarlo/` の外）にあり、scene.yaml からは動かせない。

### やること
1. 10 MV の水ファントム（Mohan 10 MV スペクトル、10×10 cm 照射野、深さ方向の PDD と横方向の OCR）を、scene.yaml で宣言して `run` で実行できるようにする。
   - 使う計算は、合格済みの構成（GPU は P5k variant F の系列、P6 / P7 の照射野カーネル）。合格構成を変える高速化はしない。
   - スペクトルは未追跡のデータ（`docs/validation/mv/p0/data/`、`~/.cache/chatcarlo/p7/spectra/`）を読む。値を追跡ファイルへコピーしない。
2. 3D 表示（`preview`）で、治療領域の条件（ビーム、ファントム、積層）を確認できるようにする。
3. **「承認された条件」と「実際に計算された条件」が一致することを機械的に確かめる仕組み**を作る（例: 承認時の条件のハッシュを計算結果に刻み、照合する）。抄録 Methods の評価（承認条件と実計算条件の整合性の検証）がこれに依存する。
4. 入口から実行した結果を、EGS5 の保存済み結果と比較する。出力の書き方は、**深部は最大 |差| と RMS（基準線量比）と SEM の範囲、ビルドアップとペナンブラは別の行**（abstract_ja_draft.md の Results 参照）。平均 ± 標準偏差は使わない。
5. 余力があれば、水・肺・骨・鉛の積層（P8e）も同じ入口で実行できるようにする（P8f の GPU 判定の結果次第）。

### 完了の条件
- scene.yaml から 10 MV 水ファントムを実行でき、結果が既存の合格済み結果と矛盾しない（統計の範囲内）。
- 条件の一致を確かめる仕組みが働き、わざと条件を変えると不一致を検出する。
- テストが通る（本体と試作は別々に実行する: `pytest tests/ -q` と `pytest prototypes/mv_electron/tests -q`）。

### 注意
- `chatcarlo/` の変更を伴うので、**計画を先に書く**（codex-kyodo）。承認前に実装しない。
- 治療領域の GPU は、Colab 側でしか動かない部分がある。A 単体では CPU（Numba）版で入口を作り、GPU 実行は B と接続する。

## 依頼 B: 対話の入口から Colab の GPU 計算まで自動で通す（バンドル作成 → 実行 → 読み戻し）

### 目的
抄録 Methods の「承認された条件は Google Colab の GPU 上で計算される」を、**登録前に 1 回、対話の入口から通した実績**にする。
今は、バンドルを手元で作り、Drive に置き、ユーザーが Colab で「すべてのセルを実行」を押し、結果を Drive から読む（手作業が残る）。Colab CLI で自動化できることは、2026-10-21 にユーザーが確認済み（別セッション「Google Colab CLI」あり）。

### やること
1. バンドル（計算条件、材料の表、GPU 用計算プログラム、照合用のハッシュ）の作成を、承認された条件から自動で行う。
2. Colab CLI で、バンドルの送付、ノートブックの実行、結果の取得を自動化する。ブラウザ操作を人が行わない形にする。
3. 結果を読み戻し、A の「条件の一致」の照合まで通す。
4. 失敗時（Drive の権限、マウントのタイムアウト、部分アップロード）に、止まって理由を報告する。無駄な再計算をしない。

### 完了の条件
- 対話の入口（または scene.yaml からの `run` に相当する呼び出し）から、人の手を介さずに Colab の GPU 計算が走り、結果が手元に返る。**これを 1 回、記録に残す**（所要時間、履歴数、条件のハッシュ）。
- 通せなかった場合は、どこで止まったかを報告する（抄録の該当文を弱める判断に使う）。

### 注意
- 既存の Colab 手順の決まり（[.claude/rules/mv.md](../../.claude/rules/mv.md) の「Codex and Colab hand-off」）に従う。Drive は gmail 側（大学アカウントではない）。
- GPU の計算プログラムは、合格構成（P5k F）をそのまま使う。
- 認証情報（トークン、アカウント情報）をファイルや履歴に書かない。

## 依頼 D: 履歴数を増やすとざらつきが減る画像（依頼 2）

### 目的
抄録 Results の依頼 2。診断領域の X 線画像で、モンテカルロの履歴数を増やすと統計ノイズが減る様子を示す。抄録に載せられるのは JPEG のみ（Supporting Data も JPEG 1 枚）。動画は本番の発表用。

### やること
1. 診断領域のシーン（骨と軟部組織を含む被写体、検出面に平面検出器のタリー `chatcarlo/detector.py`）で、履歴数を段階的に増やした画像を作る（例: 10^4 から 10^8 を対数で数段階）。
2. 均一領域の相対誤差を履歴数に対してプロットし、約 1/√N で減ることを示す。
3. 並べた JPEG（複数パネル。共通の濃淡目盛り）を作る。匿名審査向けの Supporting Data にも使えるよう、施設名・著者名・ロゴを入れない。

### 注意
- **モンテカルロの履歴数（計算の統計誤差）と mAs（撮影時の量子ノイズ）を混同しない。** 重みつき履歴を実際の検出光子と見なさない。図のキャプションと本文でこの区別を明記する。詳細は [educational_simulation_ideas_2026_10_08.md](../educational_simulation_ideas_2026_10_08.md) の 5 節。
- 診断領域の計算は本番の `chatcarlo/`（150 keV 上限、Numba CPU）で行う。GPU は要らない。
- 履歴数の範囲の選び方と、均一領域の取り方は、事前に決めて記録する。
