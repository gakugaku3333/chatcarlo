## 目的

一連の性能最適化を経た現在のChatCarloが、確立コードEGS5と比べて計算速度でどう
位置づけられるか（実務的な待ち時間としてどちらがどれだけ有利か）を定量化する。
精度のクロスチェックとは異なり合否判定はなく、数値と前提条件を報告することが目的。

## 前提として明確にすべき非対称性（速度比較の妥当性を左右する）

比較を始める前にこれらを固定しないと、「ChatCarloがNx速い」という見出しだけが
一人歩きして誤読される（EGS5の方が計算している物理量が多いことを無視した比較になる）。

1. **物理スコープの違い**: EGS5は電子（制動放射・knock-on電子）をECUT/PCUTのカットオフ
   まで完全輸送するのに対し、ChatCarloはkerma近似（電子飛程無視、相互作用点で局所吸収、
   蛍光光子のみ例外的に輸送継続）。意図的な設計差であり「バグ」ではない
   （CLAUDE.md「Physics」節参照）。単純な「1 historyあたりの時間」比較は、異なる量の
   物理計算にかかる時間を比べていることになる。→ 結果には必ずこの非対称性を明記する。
2. **実装言語の違い**: コンパイル済みFortran(EGS5) vs Python+NumPyベクトル化バッチ処理
   (ChatCarlo)。「今この環境でChatCarloを使うと実際どれだけ速い/遅いか」には意味がある
   実務的な問いだが、「どちらのアルゴリズム設計が優れているか」の答えにはならない。
3. **起動/コンパイルオーバーヘッド**: EGS5はシナリオごとにFortranコンパイルが必要
   （`egs5run`）。ChatCarloは断面積テーブル構築などのインポート時オーバーヘッドがある。
   計測対象のループ本体から除外するか、別途「固定コスト」として明記する。マルチプロセス
   (`--workers`)使用時のワーカー起動オーバーヘッド（約0.8秒/ワーカー、CLAUDE.md記載）も
   主要な比較から分離する。

## 計測指標（採用する定義）

**ユーザー指示（2026-07-27）によりC（同等の統計誤差に到達するまでの時間）を主指標に
格上げする。** A/Bは補助診断（Cの導出材料・スケーリング確認用）という位置づけに変更。

- **C（主指標）**: 両コードが共有する観測量（一次透過率）で、目標相対誤差（既定案: 1%）
  に到達するまでの壁時計時間。実務的に最も意味のある指標であり、電子輸送スコープの
  違いによる「1historyあたりの仕事量の差」を吸収して公平に比較できる
  （ただし分散低減手法自体に差があれば、それは正しくCの差として表れる — 後述）。
  - **算出法（新規に収束するまで走らせ直さない）**: 3エネルギーとも既存のEGS5相互検証で
    両コードのN=500,000時点での統計誤差が実測済み（例: `water20kev`で±0.06pp、
    `RESULTS.md`参照）。R∝1/√Nのスケーリングから目標Rに必要なN_requiredを外挿し、
    指標Aで実測したhistories/secスループットを掛けて時間に変換する。
  - R∝1/√Nのスケーリング則自体は仮定のままにせず、各コード・各エネルギーで最低2点
    （例: N=1e5とN=1e6）を追加測定し、実測Rがこの則に乗ることを確認してから外挿する
    （乗らない場合は分散低減や無限分散テールの疑いがあるため外挿せず素直に収束まで
    走らせる）。
- **A（補助）**: 固定N historiesでの壁時計時間（transportのみ、tallyなし）— Cの算出に
  必要なhistories/secスループットを得るための計測。複数のNでスケーリング
  （historyあたりコストが一定かどうか）も確認する。
- **B（補助）**: histories/sec スループット（Aから導出、Cの算出に使用）。
- **D**（ChatCarlo限定・EGS5と比較しない）: `--dose-grid`タリーのオーバーヘッド。EGS5側の
  user codeには相当するボクセルタリーが実装されていないため比較対象にはせず、
  「ChatCarloのタリー機能を使うと追加でどれだけかかるか」の参考値として別掲する。
- **E**（副次・主要比較とは分離して報告）: ChatCarloの`--workers`によるマルチプロセス
  スケーリング。EGS5側を並列実行する場合との比較まではスコープ外（必要なら別途相談）。

## シナリオ選定（ユーザー指示により確定）

**診断領域（10–150 keV）に限定し、ジオメトリー差が出にくい既存の均質スラブ検証シナリオ
3件のみを対象とする**（新規シナリオは追加しない）:

- `water20kev`（20 keV鉛筆ビーム、水スラブ1.5cm、一次透過率相対差0.16%・0.52σで
  相互検証合格済み）
- `water60_free`（60 keV鉛筆ビーム、水スラブ10cm、相対差0.88%・1.7σで合格済み）
- `water150kev`（150 keV鉛筆ビーム、水スラブ10cm、相対差0.22%・0.58σで合格済み）

いずれも「鉛筆ビーム＋均質材料スラブ1枚」という、ChatCarloの解析的境界交差計算・
EGS5の領域ジオメトリーの双方にとってほぼ最小構成のシナリオであり、ジオメトリー
エンジン自体の速度差が計測に混入しにくい。

**主比較から明示的に除外するもの**: `bsf60_phantom`・`pdd60_phantom`・`chest_room`
（ChatCarloのbox/cylinder/sphere交差判定が絡む多面体ジオメトリー）。これらを含めると
「物理エンジンの速度差」ではなく「ジオメトリーエンジンの速度差」を測ってしまう
混入要因になるため、本計画のスコープ外とする（必要なら別途の計画として立てる）。
ChatCarlo限定の指標D測定には、この除外方針とは別に、CLAUDE.md記載の`chest_room`
回帰条件（res=2cm, n=2e5, batch=2e5、~5.5s/1.7GB）をそのまま再利用する
（Dは元々EGS5と比較しないchatcarlo限定の参考値のため、幾何除外方針の対象外）。

## 計測方法の設計判断（確定事項）

1. 同一マシン・同一セッションで実行し、他の重い処理を並行させない。
2. ChatCarlo側は既定でシングルプロセス（`--workers`なし）を主指標とする。
3. 壁時計時間は`time.perf_counter`（ChatCarlo）／シェルの`time`または`SYSTEM_CLOCK`
   （EGS5）で計測。EGS5はコンパイル済みバイナリを直接再実行してコンパイル時間を除外する
   （実装は`egs5-operator`エージェントに委任）。
4. 各条件は最低3反復、A/Bの実行順序を固定しない（インターリーブ）。中央値を報告する。
   `docs/speedup_baseline/tally_speedup_timing.py`と同じ規律
   （交絡・反復不足を避ける — `feedback_critical_code_review`メモリ参照）。
5. N historiesは対数刻みで複数点（例: 1e4/1e5/1e6/1e7）取り、両コードのスケーリング挙動を
   確認する。

## 実施フェーズ

- **Phase 0**: この計画書のレビュー・ユーザー確認（特にシナリオ選定とNレンジ、EGS5側の
  電子輸送カットオフをどう設定するか）。
- **Phase 1**: 計測スクリプト整備。
  - ChatCarlo: `docs/speed_comparison/chatcarlo_timing.py`
    （`tally_speedup_timing.py`と同パターン、tallyなしのtransport-onlyパスを計測）。
  - EGS5: `egs5-operator`エージェントに委任し、対象user code（tutor5ベース）に
    タイマーを追加、コンパイル済みバイナリを直接再実行できるようにする。
- **Phase 2**: 指標A/Bの計測（transportのみ、シングルスレッド、インターリーブ3反復以上、
  N=1e5/1e6の2点以上でR∝1/√N則を確認）。
- **Phase 3**: 指標C（主指標）の算出 — Phase 2のスループットと既存RESULTS.mdの
  N=500,000時点統計誤差から目標R到達時間を外挿し、3エネルギーそれぞれで報告。
- **Phase 4**: 指標D/E（副次、ChatCarlo単体）。
- **Phase 5**: 結果を`docs/egs5_crosscheck/speed_comparison/RESULTS.md`にまとめ、
  `vive-auditor`で監査（測定方法の交絡・非対称性の記載漏れがないか）。

## 受入/報告基準

合否判定のあるクロスチェックではなく実測値の報告なので「合格基準」は設けない。
ただし前述の非対称性（電子輸送スコープ差・言語差・起動コスト）を必ず数値と併記し、
文脈を欠いた「ChatCarloがNx速い」という一行結論だけを書かないこと。
