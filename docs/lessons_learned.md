## xraylib の `CS_Energy`（μen/ρ）を吸収線量計算に使ってはいけない

`xraylib.CS_Energy` / `CS_Energy_CP` が返す質量エネルギー吸収係数 μen/ρ は、
NIST XAAMDI（Hubbell & Seltzer）の公表値と最大約17%（Al, 60 keVで実測）乖離する。
一方 μ/ρ（全断面積、`CS_Total`/`CS_Total_CP`）はNISTと1%以内で一致する。

**対応**: μ/ρ は xraylib、μen/ρ は NIST XAAMDI を直接取得したCSV
（`scripts/fetch_nist_xaamdi.py` → `chatcarlo/data/nist_xaamdi/`）から
log-log補間で得る2系統構成にした（[materials.py](../chatcarlo/materials.py)）。
`tests/test_materials.py` でNIST公表値とのスポット照合を自動テスト化済み。

**なぜ気づけたか**: 実装直後にNIST公表値と機械的に突き合わせるテストを書いたため。
新しい断面積・線量係数データソースを追加するときは、実装を信用する前に
必ず1次資料の数値と照合するテストを先に書くこと。

## 生体組織の組成規格の違いによるμ/ρの数%ずれは実在する物理差

xraylib の骨データは ICRP 組成、NIST XAAMDI は ICRU-44 組成で、
同じ「骨」でも μ/ρ が最大約2%異なる（60 keVで実測）。
これはバグではなく組成定義の違いによる正当な差なので、
テストの許容誤差は物質ごとに変える（`tests/test_materials.py` の `_LOOSE` 集合）。

## 線量係数（H*(10)等）は記憶で書かず1次資料を取得する

ICRP Publication 74 / ICRU Report 57 の h*(10)/Φ 表は数値を暗記していても
誤る危険が高い防護量データで、公式PDFの数値表は検索だけでは本文抽出できない
ことが多い（WebFetchがPDFのバイナリ内容を正しくテキスト化できないケースが
あった）。OpenMCプロジェクト（MITライセンス）がICRP74値をそのままテキスト
ファイルとして同梱していたため、`gh api repos/openmc-dev/openmc/contents/...`
で直接取得できた（[scripts/fetch_h_star_10.py](../scripts/fetch_h_star_10.py)）。

**対応**: 新しい線量換算係数を追加するときは、(1)記憶から値を書かない、
(2)1次資料PDFが読めない場合はオープンソースプロジェクトが同梱する
転記データ（ライセンス・出典明記の上で）を探す、(3)取得元をコード内
コメントとfetchスクリプトに明記する、の順で対応する。

## 「重元素ほど前方散乱に偏る」という直感は誤り（レイリー散乱の原子形状因子）

原子形状因子 F(Z,q) は q=0 で F=Z、単調減少するが、その減衰の速さは
**軽元素の方が急峻**（xraylibで実測: q=0.5 Å⁻¹でのF/ZはC:0.28, Ca:0.41, Pb:0.59）。
そのため同じ光子エネルギーでは軽元素の方が前方散乱に強く偏り、
重元素は後方まで広がる — 「重い原子ほど前方に強く散乱するはず」という
直感は逆だった。テストを先に直感で書いて失敗し、xraylibの生データを
確認してから修正した（[tests/test_rayleigh.py](../tests/test_rayleigh.py)）。

**対応**: 物理的な直感でテストのアサーションを書く前に、実装が使う
1次データ（この場合はxraylib自体）で数値を直接確認してから書く。
直感と実装のどちらが誤っているか区別がつくまでテストの向きを決め打ちしない。

## mAs絶対値校正でn_historiesを二重に割るバグ（符号・有限性しか見ないテストは桁バグを検出できない）

`chatcarlo run --dose-grid` のmAs校正済み絶対値出力が、実際の期待値より
約`n_histories`倍（実測で約100万倍）小さい値になっていた
（[__main__.py](../chatcarlo/__main__.py)）。原因は
`dose_per_history = dose / n_histories` で既に「1光子あたり」に変換した値に、
さらに `scale = n_photons_real / n_histories` という`n_histories`で割った
係数を掛けていたため。正しくは `scale = n_photons_real` のみでよい
（1光子あたりの値に実光子数を掛ければ絶対値になる）。

発見の経緯: ユーザーから「胸部X線撮影の皮膚線量を計算して」と実際に使ってみた際、
SpekPyの`get_kerma()`（自由空間カーマの参照値）およびChatCarlo自前の
`mu_en_rho`データを使った独立の手計算と突き合わせたところ、桁が大きくずれて
いることに気づいた。既存の`tests/test_calibration.py`はこの絶対値校正の結果に
対して「正の値か・有限か」しかアサートしておらず、桁の間違いを検出できていなかった。

**対応**: 絶対値・物理量を扱うテストは、符号・有限性だけでなく
**独立した参照計算との桁の一致**（今回はSpekPyの`get_kerma()`、factor 50以内）
まで検証する。「実際にツールを使ってみる」というユーザー視点の検証が、
単体テストでは拾えないスケーリングバグの発見につながった
（`tests/test_calibration.py::test_calibrated_dose_matches_spekpy_kerma_order_of_magnitude`）。

## グリッド全体の「最大値」統計は空気ボクセルという非物理的な位置に落ちやすい

`chatcarlo run --dose-grid`が出力する「最大吸収線量」「最大H*(10)」は、
実際に調べると多くの場合**背景（空気）ボクセル**に落ちる。原因は2つあり、
どちらもtrack-length estimatorそのものは正しく、統計として意味のある
「グリッド全体の最大」という統計量の選び方が悪いだけだった:

1. **H*(10)の点線源近傍発散**: 点線源モデルではフルエンスが1/r²で発散する。
   線源直近（chest_room.yamlの実測で線源から3〜19cm）の空気ボクセルが
   最大H*(10)を占め、実測で約1e11 pSv（=100 Sv超）という非物理的な値になった。
   実際のX線管にはhousing・コリメータがあり、この位置に人や検出器が
   存在することはない。
2. **吸収線量の材料境界での後方散乱発散**: 水スラブに鉛筆ビームを垂直入射
   させる単純なシーンでも、最大吸収線量は水の内部ではなく**表面直前の空気
   ボクセル**に落ちた。しかもこれは粗い解像度の離散化誤差ではなく、
   **解像度を細かくするほど値が増大する**現象だった
   （2cm: 1.4e-13, 1cm: 1.5e-13, 0.5cm: 6.4e-13, 0.2cm: 3.5e-12 Gy/history、
   おおよそ1/解像度²で成長 — カーマは密度で正規化済みなので密度の
   アーティファクトではなく、材料境界での後方散乱によるkerma track-length
   タリーの境界効果と考えられる）。「粗いグリッドのせいだろう」という
   直感は誤りで、解像度を振って確認するまで気づけなかった。

**発見の経緯**: 前セッションで「H*(10)最大値が線源近傍で異常に大きい」と
気づいたことをメモリに残しておき、次セッションで検証を依頼された。
実際に最大値ボクセルの位置・材料・線源からの距離を出力するスクリプトを書いて
確認したところ、上記2つの異なる原因が判明した。特に(2)は「解像度を細かくすれば
直る」という直感で終わらせず、実際に4段階の解像度で数値を比較したことで
「離散化誤差ではなく真の発散に近い現象」だと分かった。

**対応**: タリー自体（track-length estimator）は修正していない（物理的に
正しい推定量のため）。代わりに`chatcarlo run`の「最大」統計に診断を追加した:
- `Geometry.nearest_object_distance_cm`: 線源等の点からシーン内の各物体の
  境界ボックスまでの最短距離
- `background_medium_warning`（[diagnostics.py](../chatcarlo/diagnostics.py)）:
  最大吸収線量ボクセルが背景（空気）なら常に警告する（吸収線量は媒質固有の
  量なので、空気中の値は患者・検出器等の実体がある位置の被ばく評価には使えない）
- `near_source_air_warning`: 最大H*(10)ボクセルが背景かつ、シーン内の
  どの物体よりも線源に近い位置にある場合のみ警告する（H*(10)自体は
  面積線量モニタリング用に空気中で評価する量なので、単に「空気だから」
  では警告しない。「物体より線源に近い」という条件は、実在し得ない
  近傍であることの明確な根拠になる）

数値そのものは変更せず（勝手な除外・補正はしない）、位置・材料の診断情報と
警告メッセージだけを追加した。グリッド全体の「最大」を安全に報告できる
統計量として使いたい場合は、この2つの警告が出ないことを確認するか、
評価したい位置（患者表面等）に直接細かいグリッドを敷く方法を使うこと
（`tests/test_dose_diagnostics.py`）。

## チャット添付のインライン表示（render）は自己完結HTMLの`<script>`を実行しないことがある

`chatcarlo trace`/`preview`が生成する自己完結HTML（vanilla JS + canvas）を
チャットの添付ツールで`display: "render"`（インライン表示）で送ったところ、
ユーザー側で「何も表示されない」という報告があった。実際にブラウザ
（ローカルHTTPサーバ経由でこのツールのBrowser機能から開く）で検証すると
コンソールエラーなく正しく描画され、コード側の不具合ではなかった。

**原因**: チャットのインラインプレビュー枠は、埋め込みJSを実行しない/制限
する場合がある（サンドボックスの`<script>`実行制約と推測、明確な仕様は
不明）。ファイルの中身自体は正しくても、この経路では空白キャンバスになる。

**対応**: ChatCarloが生成するインタラクティブHTML（trace/preview）は
`display: "attach"`（ダウンロードカード）で送り、実ブラウザで開いてもらう
運用にした。`.claude/skills/vive-check/SKILL.md`の「`open <html>`でブラウザ
表示」という既存の指示もこの前提に基づいている——チャット添付プレビューは
静的な検証手段としては信用しないこと。真に描画を検証したいときは、
このツールのBrowser機能（`preview_start`+`navigate`、file://は使えないため
`python -m http.server`でローカル配信してから開く）でコンソールエラーの
有無まで確認する。

## 新しい物理モデル（CTDIvol校正・ヒール効果）もSpekPyの実挙動を先に実測してから実装する

CTDIvol校正・ヒール効果の実装前に、SpekPyの軸外計算（`Spek(x=...)`）の
座標系（どちらが陽極側か）を記憶で仮定せず、`x`を振ってフルエンス・平均
エネルギーを実測してから設計した（x<0が陽極側であることを確認）。
既存の教訓（xraylib CS_Energy、h*(10)係数、レイリー原子形状因子）と同じ
パターンで、外部ライブラリの規約は使う前に必ず実測すること。

**副産物のバグ**: ヒール効果のエネルギー抽選で、陽極カットオフ境界を
補間する際に受理された光子がゼロ放出ビンに落ちて`rng.choice`の確率が
合計1にならず例外になるケースがあった（`tests/test_heel_effect.py::
test_heel_composes_with_cone_and_rotation`で発覚）。**対応**: ビンindexを
非ゼロフルエンスの範囲にクランプ（`chatcarlo/source.py`）。境界条件・
カットオフのような「稀にしか踏まないパス」は、通常の物理的検証テストとは
別に、境界そのものを狙ったテストケースを書かないと見つからない。

## `set()`の反復順に依存すると、同一seedでも実行のたびに結果が変わる

`transport.py`を`transport.py`/`source.py`/`spectrum.py`/`physics.py`/
`trajectory.py`/`diagnostics.py`に分割するリファクタリング（2026-07-14）の
検証中、**リファクタリング前から** `chatcarlo run --seed 42` の出力が
実行のたびに微妙に変わるバグが既存していたことが判明した。

原因: 材料名でバッチをグループ化する箇所（`_linear_mu_batch`等、5箇所）が
すべて`for name in set(materials.tolist())`で反復しており、Pythonの文字列
ハッシュはプロセスごとにランダム化される（`PYTHONHASHSEED`）ため、
グループを処理する順序がプロセスごとに変わっていた。レイリー元素抽選など
グループ処理の順に依存して乱数を消費する経路があるため、抽選結果自体が
ずれて`--seed`を固定しても再現しない。

**対応**: グループ化を`materials.material_groups()`に一本化し、内部で
`sorted(set(...))`にソートを固定した。異なる`PYTHONHASHSEED`の2プロセスで
同一seedの結果が一致することを`tests/test_reproducibility.py`で回帰
テスト化した。

**教訓**: `set`や辞書のキー反復順は「その場では動くが再現性がない」典型
パターン。乱数を消費するループでバッチを名前・IDでグループ化するときは、
反復順を明示的に固定（ソート等）しないと、シード固定による再現性の
保証が静かに壊れる。この手のバグはテストが通っていても気づけない
（テストはseedを毎回変えないため、たまたま同じ順序が出続けて隠れる）。
再現性が要件のコードでは「同一seedを2回実行して完全一致するか」を
定期的に手で確認する価値がある。

## コード間の数値差は、まず「物理モデルが揃っているか」を疑う（EGS5相互検証, 2026-07-15）

PHITSライセンス取得が抄録締切（2026-07-17）に間に合わないため、KEK配布の
EGS5（登録不要で即日入手可）に切り替えて相互検証を行った際、初回実行で
ChatCarloとEGS5の一次透過率が相対4.7%（約8.6σ）ずれ、独立監査
（vive-auditor）で差し戻しになった。

**原因**: EGS5チュートリアル（`tutor5`）のデフォルトPEGS5設定が
`IBOUND=0`（自由電子Klein-Nishina全断面積）だったのに対し、ChatCarlo/xraylib
の`CS_Compt`はEPDL由来の**束縛電子補正込み**断面積を使っていた。60 keV水では
コンプトンが全断面積の86%を占めるため、この物理モデル差だけで透過率が
数%動く。「断面積ライブラリの版数差（±1%程度）」という説明は、支配的な
相互作用チャネルの寄与を考えれば数値的に足りないと気づけたはずだった。

**対応**: 自由電子KN全断面積を解析式から独立計算し、xraylibのEPDL値
（束縛補正込み）と比較して+3.03%の乖離を確認。EGS5側を`IBOUND=1`
（束縛コンプトン）に揃えて再実行したところ、相対0.88%・約1.7σまで縮み、
計画書の事前基準（2σかつ2%以内）に適合した（詳細:
[egs5_crosscheck/RESULTS.md](egs5_crosscheck/RESULTS.md)）。

**教訓**: 独立実装のコード同士を比較検証するときの不一致は、まず
「支配的な相互作用チャネルについて、両者が同じ物理モデル（自由電子 vs
束縛電子、コヒーレント散乱の有無等）を使っているか」を最初にチェックする。
「ライブラリの版数差」のような曖昧な説明で±数%の系統差を片付ける前に、
その相互作用が全断面積に占める割合から「その説明で数値の桁が合うか」を
概算すること。コード間比較（物理モデルを揃えて実施）は輸送アルゴリズム・
実装の検証であり、断面積データそのものの正しさは別途一次資料
（NIST等）との照合で担保する、という役割分担を混同しないこと。

**続報（Phase 2a BSF、2026-07-17）**: 上記の教訓を知っていたはずなのに、
Phase 2aのStep 2（後方散乱係数BSF、水薄層カーマ再定義後の比較）で
`IBOUND=1`だけを確認し、`INCOH=1`の確認を委任プロンプトから漏らして
同じ罠にもう一度落ちた（EGS5側がINCOH=0=自由電子コンプトンのまま実行され、
束縛コンプトンを使うChatCarloと物理モデルが揃っていなかった。
vive-auditor監査で発覚、独立検証で相対0.4〜0.6%規模の影響を確認）。
さらに判明したのは、**`IBOUND=1`（PEGS5の全断面積レベルでの束縛補正）と
`INCOH=1`（EGS5ランタイムでの角度・エネルギー抽選への反映）は別物**という
こと——PEGS5の`INCOH=1`はS(q)テーブルを生成するだけで、EGS5ユーザーコード
（.f）側で各リージョンに`incohr(region)=1`を明示的に立てないと束縛コンプトン
散乱は角度分布に反映されない（`egs5job.out`に`INCOHERENT DATA AVAILABLE
... BUT OPTION NOT REQUESTED`という警告が出るが、見落としやすい）。
**教訓の更新**: 「物理モデルを揃える」チェックリストは一度確立しても、
egs5-operatorへの個別タスク委任プロンプトに毎回明示すること
（`IBOUND=1`かつ`INCOH=1`かつユーザーコード側`incohr(region)=1`の3点セット）。
チェックリストの存在を知っていることと、それを新しいタスクの実行時に
実際に適用することは別で、後者を担保する仕組み（委任プロンプトへの
明記、または実行後のgrep確認をタスクの標準手順に組み込む）が必要。

## legacy Fortran（EGS5等）をモダンgfortranでビルドするには明示的な緩和フラグが要る

Homebrew gfortran 16.1.0はデフォルトで、F77の暗黙インターフェース
（関数と宣言の食い違い、例: `cprfil`/`alin`/`alini`/`pairfr`/`pairfz`/
`brmsfz`/`bremfr`/`bremfz`/`QFIT`）をエラーにし、古いgfortran/g77では
通っていたコードのビルドが失敗する。

**対応**: EGS5の`egs5run`スクリプトの`gfort`マシンプロファイルの`CFLAGS`に
`-std=legacy -fallow-argument-mismatch -w`を追加（デフォルトは
`-fno-automatic`のみ）。これでtutor5・水スラブ検証コードとも問題なく
ビルド・実行できた。

**教訓**: 配布年代の古いFortran資産を新しい環境でビルドするときは、まず
コンパイラのデフォルト厳格化（インターフェースチェック強化等）を疑い、
`-std=legacy`系のフラグを最初から試す。エラーメッセージの個々の関数名を
一つずつ潰そうとするより早い。

## 全断面積が一致しても、エネルギー付与（kerma）の絶対値まで一致するとは限らない（EGS5相互検証Phase 2b, 2026-07-16）

Phase 1（一次透過率、相対0.88%一致）・Phase 2a（BSF、EGS5側の測定不確実性で保留）に
続けて、水ファントムのPDD＋側方プロファイル（47ビン、per-history絶対値Gy/history）を
ChatCarlo・EGS5で相互検証したところ、**EGS5が全47ビンで一貫してChatCarloより
約−1.71%低い**という、統計揺らぎでは説明できない系統差が見つかった
（詳細: [egs5_crosscheck/PDD_RESULTS.md](egs5_crosscheck/PDD_RESULTS.md)）。
vive-auditorの独立監査で数値・判定は完全に再現され（条件付き合格）、原因は
未確定のまま次の課題として持ち越した。

**分かったこと**:
- **形状（深さ依存・側方依存の相対的なプロファイル）は両コードで完全に一致**する。
  各コードを自分自身の基準ボクセルで100%正規化して形状だけを取り出すと、
  47ビン中2σを超える有意差は実質ゼロ（多重比較を考慮すればノイズの範囲）。
  問題は**絶対値スケールだけ**に局在している。
- **有力仮説（未検証）**: ChatCarloのkerma推定量は各飛行区間でNIST XAAMDI
  （Hubbell-Seltzer）のμen/ρを直接テーブル参照する「係数ベース」。EGS5の
  ausgabは、PEGS5が生成した断面積データ（Storm-Israel系＋IBOUND束縛コンプトン
  補正）に基づく実際のモンテカルロ相互作用から積み上げた「シミュレーション
  ベース」の局所エネルギー付与で、**NIST XAAMDIとは独立に評価された別データ
  ソース**である。Phase 1で検証済みの「全断面積・透過率が0.88%で一致」は
  低Z水で支配的なコンプトン散乱確率で決まる量であり、光電吸収の断面積に
  数%規模のずれがあっても透過率にはほとんど影響しない。しかし光電吸収は
  相互作用1回あたりほぼ全エネルギーを局所付与するため、**エネルギー付与
  （kerma/dose）の比較では、透過率の比較より断面積の食い違いが増幅されて
  見える**可能性がある。
- ChatCarlo側のμen/ρ参照値そのもの（NIST XAAMDIテーブル読み取り）にデータ
  入力ミスはないことをファイル・単位換算・σ計算まで独立に検算して確認済み。

**教訓**: 「コード間で全断面積・一次透過率が良く一致した」ことは、「エネルギー
付与（kerma/dose）の絶対値も同精度で一致する」ことを保証しない。両者は
異なる物理量（総相互作用確率 vs 相互作用種別ごとのエネルギー移行の内訳）で
あり、後者は前者よりデータソース間の食い違いに敏感になりうる。線量計算コードの
相互検証では、透過率だけでなくエネルギー付与量そのものを独立に照合する
フェーズを必ず設けること（Phase 1だけで「検証完了」と判断しない）。

**続報（2026-07-17、原因究明完了）**: 上記の「有力仮説（未検証）」を
[plan_compton_transfer_check.md](egs5_crosscheck/plan_compton_transfer_check.md)で
検証したところ、**光電吸収断面積の食い違いという当初の仮説は棄却**された
（PEGS5内部データ vs xraylib/EPDLの光電断面積差は+0.408%で、kerma全体への
影響は+0.19%と観測方向と符号が逆。「部分的要因」の条件すら満たさない）。
代わりに**コンプトン散乱のエネルギー移行分布の差**が部分的要因（観測−1.71%の
約64%を説明）と判明した。EGS5側のPEGS5設定`IBOUND=1, INCOH=0`は「全断面積の
みStorm-Israel系の束縛補正を適用し、散乱光子のエネルギー・角度抽選は自由電子
Klein-Nishinaのまま（S(q)補正の棄却法なし）」という**混成構成**であり、
ChatCarlo/NIST XAAMDIはS(q)補正込みの散乱理論で評価されているため、平均
エネルギー移行率に系統差（60 keVで−2.35%）が生じる。机上検算（自由電子KNの
解析的平均移行率）・EGS5ソースコード裏取り（`egs5_compt.f`の棄却関数が
実際にS(q)補正なしで動くことをコード行で確認）・EGS5計装再実行（実際の
コンプトンイベント900万件超から⟨T⟩を直接測定し机上予測と0.48σで一致）の
三重の独立手法で確認済み（vive-auditor監査も条件付き合格）。残り約36%は
依然未解明。

**教訓（追加）**: 「断面積（相互作用が起こる確率）が高精度で一致している」
ことは、「その相互作用でどれだけのエネルギーが移行するかの分布まで一致する」
ことを含意しない。EGS5のIBOUND（全断面積の束縛補正）とINCOH（散乱光子の
エネルギー・角度抽選への束縛補正）は独立なフラグで、片方だけ有効にする
「断面積のみ束縛・運動学は自由電子」という混成構成は現実的なユースケース
だが、kerma/線量レベルの精密比較では数%規模の見かけの系統差を生みうる。
コード間クロスチェックで物理モデルを揃える際は、「断面積を揃えたから
物理モデルは同じ」と即断せず、断面積と運動学（角度・エネルギー分布）を
別々のチェック項目として確認すること。

**続報2（2026-07-17、残差調査完了）**: 残り約36%の未解明分を
[plan_residual_check.md](egs5_crosscheck/plan_residual_check.md)で調査したところ、
2つの独立要因の合算でほぼ説明できることが判明した。

1. 単一エネルギー(60 keV一次成分のみ)の机上検算では見えなかったが、実際の
   散乱スペクトル（多重散乱で軟化した二次光子を含む）まで畳み込むと、
   「コンプトン移行分布差」単独の寄与は−0.75%程度（60 keV一次成分のみの
   −1.095%より小さい）にとどまった。
2. 代わりに、**ChatCarlo自身のμen/ρ log-log補間**に、想定していなかった
   系統誤差が見つかった。NIST XAAMDIの公表データは30-40-50-60-80 keVという
   疎な格子しか持たず（この帯域でμen/ρ(E)は極小を持つ凸型の曲線）、格子点
   そのものでは補間なしの第一原理近似と0.02-0.08%で一致するにもかかわらず、
   格子点の中間（35/45/55 keV）ではlog-log線形補間が実際の値より+1.5〜1.8%
   高く出ることを直接確認した。
3. EGS5をINCOH=1（S(q)束縛補正込みのコンプトン散乱、ChatCarloの物理と
   整合する構成）で再実行したところ、47ビン平均相対差は−1.71%から−0.633%まで
   縮小し、事前登録した予測値（コンプトン移行分布差の解消＋補間アーティファクト
   の残存を織り込んだ−0.81%±0.3pt）の範囲内に収まった。密度・断面積の
   微小差（候補として検討）は最深部でも0.19%pt程度で無視できる規模だった。

**教訓（追加2）**: ①単一エネルギー・単一相互作用種別だけの机上検算は、
多重散乱で生じる二次光子スペクトル全体を通した効果を過小・過大どちらにも
見誤りうる。可能なら実際のスペクトルで重み付けした畳み込み計算まで行う
（ChatCarlo自身の輸送結果を重みに使う近似でも一定の説明力がある）。
②離散テーブルを補間して使う物理量（今回はμen/ρ）は、格子点そのものでの
検証だけでは不十分——格子点の**中間**で検証しないと、曲率由来の補間誤差
（今回は水で+1.5〜1.8%、無視できない規模）を見逃す。これはEGS5比較固有ではなく、
水の場合ChatCarlo全体の線量計算精度に関わる限界であり、30〜80 keV帯を含む
シミュレーションでは常にこの影響を受けうる。他材質も同型の疎な格子・凸曲線を
持つため方向性は共通すると推測されるが、バイアス幅が水と同程度かは未確認
（水以外での定量評価・対処は本調査のスコープ外、今後の課題）。

## 推定量の種類が違うと、同じ物理量でも履歴あたりの統計誤差が桁違いになる（EGS5相互検証Phase 2b, 2026-07-16）

Phase 2bでChatCarlo（n=5,000,000）とEGS5（n=100,000,000、20倍の史数）を比較したところ、
薄い（1cm×2×2cm程度の）スコアビンにおいてChatCarloの統計誤差がEGS5の単純な
1/√nスケーリング予測（史数差から期待される値）よりずっと小さい（履歴あたり
分散でおよそ12〜14倍小さい）ことが分かった。バグではなく、推定量の種類の違い
による既知のMC効果:
- **track-length（飛程長）推定量**（ChatCarlo）: ビンを通過した光子**全員**に
  ついて、飛行距離×μen/ρ×エネルギーを決定論的に積算する。相互作用の有無に
  関係なく通過さえすれば必ず寄与するため、履歴あたりの分散が小さい。
- **collision（衝突点）推定量**（EGS5のausgab）: ビン内で実際に相互作用が
  起きた光子だけが寄与する。薄いビンでは通過光子のうちごく一部しか実際に
  相互作用しないため、「ほとんど0、稀に大きい値」という当たり外れの激しい
  分布になり、履歴あたりの分散が大きい。

**教訓**: 異なるコード・異なるタリー方式で統計誤差を比較するとき、史数比から
単純に期待される誤差比と大きくずれていても、それだけでは異常のサインにならない。
両者が同じタリー技法（track-length vs collision）を使っているかを先に確認する。
逆に、薄い領域での精密なタリーが必要な場面では、可能ならcollision推定量ではなく
track-length推定量を選ぶ方が、同じ史数で大幅に統計精度を稼げる
（`chatcarlo/tally.py`のcollision/track-length二推定量設計、Phase 2aの
BSFスクリプトの選択と同じ理由）。

## track-lengthタリーの「サブステップ中点」スコアリングは、区間始点が境界に位相同期すると系統バイアスを生む（会話ワークフロー実演, 2026-07-16）

学会抄録用に「vive-interview→vive-checkの会話ワークフローだけで、EGS5相互検証
（Phase 2b）と同じ結論に行き着く」実演を作る過程で、新機能`source.field.shape:
parallel`（非発散の平行ビーム）を追加した。この機能で組んだシーン（全光子が
水ファントム前面ちょうどy=0から出発）を`--dose-grid`で計算したところ、
vive-auditorの独立監査（同一乱数トラックに対する厳密box-overlap推定量との
並行計算）で、**ファントム表面ボクセル層だけが約−2.7%系統的に過小評価**
されていることが発覚した（[egs5_crosscheck](egs5_crosscheck/)関連ドキュメント参照）。

**原因**: `accumulate_track_length`（[tally.py](../chatcarlo/tally.py)）は
区間をサブステップに等分し、各サブステップの**中点**（決定的な位置）が属する
ボクセルへスコアしていた。区間の始点がボクセル境界ちょうどに揃わない通常の
シーン（点線源からの発散ビームは空気中を経てから材料境界に達するため、
最初の区間は境界ちょうどからは始まらない）では、サブステップ中点の量子化誤差は
光子ごとにバラバラな位相を持ち、平均すると打ち消し合う。しかし今回の平行ビームは
**全光子の第1区間が同じ座標（材料境界）から始まる**ため、量子化誤差の位相が
全光子で揃い、打ち消されずに系統誤差として残った（表面ボクセル層のみ、
1/解像度で発散しない新種のパターン）。既存の`background_medium_warning`/
`near_source_air_warning`（[diagnostics.py](../chatcarlo/diagnostics.py)）は
どちらのボクセルも「水」で発火しない設計のため、この種のバグは盲点だった。

**対応**: サブステップの中点ではなく、各サブステップ内の**層化乱数点**で
スコアするよう変更した。これで区間の始点位置に関わらず、任意のボクセルへの
期待寄与が厳密な幾何学的重なり長に一致する（不偏推定量）。修正はスコアリング
（空間分配）だけに限定され、区間全体のエネルギー積算（Σweight×length）は
乱数点の位置と無関係に厳密なままなので、輸送本体の結果（吸収/脱出割合、
相互作用サンプリング）には一切影響しない設計にした（`transport_photons`に
`tally_rng`引数を追加、`rng.spawn()`で輸送用乱数列と分離）。

**教訓**:
- 決定論的な離散化（中点・格子点など）を使う推定量は、入力データの位相が
  たまたま離散化格子と同期する条件で系統バイアスを生みうる。「ランダムな
  入力なら中点近似は十分」という直感は、入力の分布が本当にランダムである
  前提が崩れると成り立たない。層化乱数点は原理的にこの種のバイアスを消せる。
- 新しいソースジオメトリ（今回は非発散の平行ビーム）を追加するときは、
  それが既存の暗黙の前提（「光子は必ず空気中から材料に入射する」等）を
  破っていないかを疑うこと。この種の前提破りは、通常のシーンでの回帰テストでは
  絶対に検出できない。
- 独立監査（vive-auditor）が「同一乱数トラックに対する2つの推定量の並行比較」
  という決定論的な検証手法を使ったことが発見の鍵だった。統計誤差に埋もれる
  規模のバイアス（今回は表面層のみ−2.7%）は、単純な数値比較や集計値の
  照合だけでは見逃しやすい。

## 疎な参照テーブルのlog-log「線形」補間は、格子点で一致していても格子点間で無視できない曲率誤差を持ちうる（EGS5相互検証Phase 2b残差調査, 2026-07-17）

Phase 2b（PDD/OCR相互検証）で観測された−1.71%系統差の原因究明の過程で、
`chatcarlo/materials.py`の`mu_en_rho()`（NIST XAAMDIテーブルのμen/ρをlog-log
線形補間で参照）に、格子点そのものでは0.1%未満で一致するにもかかわらず、
格子点間の中間エネルギーでは最大3.3%（60〜80keVの20keV間隔区間で最悪）の
曲率誤差があることが判明した。原因は「格子点で正しい＝補間全体で正しい」という
暗黙の前提の誤り。XAAMDIテーブルは対数対数でもなお緩やかに曲がっており、
特に格子間隔が広い（20keV前後）区間でlog-log線形補間の直線近似が実際のカーブから
乖離する。

**検出方法**: 独立に評価できる「第一原理近似」（xraylib photo+compton×
Klein-Nishina/S(q)平均エネルギー移行率、格子点で0.02〜0.08%の高精度一致を
別途確認済み）を基準に、格子点間の中間エネルギーでテーブル補間値と比較した。
単純に「補間値は両隣の値の間にある」というテスト（`test_loglog_interpolation_
between_grid_points`、既存）だけでは検出できない種類のバグで、外部の独立な
参照値との比較が必要だった。

**対応**: `mu_en_rho()`をlog-log線形補間からlog-log PCHIP（区分3次エルミート、
形状保存・格子点は厳密通過）に変更した。30〜80keV帯の最大曲率誤差は3.3%→0.6%
（82%削減）。実際のPDD/OCRスペクトルで畳み込んだ寄与も改善を確認し、Phase 2bの
EGS5相互検証残差が−1.71%→−0.91%まで縮小したことで実効果を検証した
（詳細: [egs5_crosscheck/PDD_RESULTS.md](egs5_crosscheck/PDD_RESULTS.md)）。

**教訓**:
- 疎な参照テーブル（格子間隔が広い、対数軸でもなお曲がっている量）をlog-log
  線形補間で使う設計は、格子点での検証だけでは補間全体の精度を保証しない。
  格子点間の中間値を独立な参照値と比較するテストを別途用意すべき。
- 「格子点一致のテスト」と「補間区間全体の精度」は別物として扱う。今回は
  前者（`test_mu_en_rho_matches_nist`）は既にパスしていたが、後者の欠陥が
  1年近く未検出のまま残っていた。
- 形状保存補間（PCHIP等）は、格子点を厳密に通過しつつ区間内の曲率を線形補間
  より正確に再現できるため、線形補間からの置き換えとして低リスク・高効果な
  選択肢になりやすい（外挿はしない・オーバーシュートしない特性を持つ）。
- この種のバグは、コード単体のテストでは検出しにくく、**独立コード
  （EGS5）との定量的なクロスチェックが実効的な検出手段になった**。
  Phase 1・2aのような「同一コード内の比・全断面積の粗い一致確認」だけでは
  見えなかった精度課題が、Phase 2bの「絶対値同士の直接比較」で初めて
  露見した（[pdd60_NOTES.md](egs5_crosscheck/pdd60_NOTES.md)の「未確認事項」
  節も参照）。

**関連**: Phase 2b の残差調査では、35/45/55 keV で補間が +1.5〜1.8% 高く出た（「全断面積が一致しても…」の続報2）。

## 相互作用確率の抽選と実際のサンプリングモデルが、別々の物理仮定を暗黙に使っていることに気づかず放置していた（束縛コンプトン実装, 2026-07-17）

Phase 2b残差調査（この教訓集の直前の節、μen/ρ補間アーティファクト）で
μen/ρを修正した後もなお約−0.91%の系統差が対標準EGS5(INCOH=0)で残っていた。
原因を辿ると、ChatCarloは**相互作用種別（光電/コンプトン/レイリー）の抽選確率**
には`xraylib.CS_Compt`（EPDLベース、束縛効果=非干渉性散乱関数S(q)補正込み）を
使っていたのに、**実際にコンプトン散乱が起きた後の角度・エネルギー移行の
サンプリング**は自由電子Klein-Nishina（束縛効果なし）のままだった、という
内部不整合が最初から存在していたことが分かった。「相互作用が起きる確率」と
「起きた後にどう振る舞うか」を別モデルで評価していたことに、実装時も
その後のテスト・レビューでも誰も気づいていなかった。

**対応**: `chatcarlo/physics.py`に`sample_compton_bound`を実装し、自由電子KNの
Kahn型棄却法による提案に、非干渉性散乱関数S(Z,q)/Z（`xraylib.SF_Compt`、q→∞で
Zに収束するため0〜1の受理確率としてそのまま使える）による追加棄却を重ねた。
元素選択もRayleighと同様に質量分率×`CS_Compt`で明示的に抽選するようにした
（詳細: [egs5_crosscheck/plan_bound_compton.md](egs5_crosscheck/plan_bound_compton.md)、
[egs5_crosscheck/PDD_RESULTS.md](egs5_crosscheck/PDD_RESULTS.md)）。

**効果の検証**: 同じ束縛コンプトン物理を使う構成同士（ChatCarlo vs EGS5
INCOH=1）で比較すると、47ビン平均残差が+0.02%までほぼ完全に一致した。一方、
角度分布が自由電子KNのままの標準EGS5(INCOH=0)との比較では約−1.0%の差が
残ったが、これは修正漏れではなく「EGS5 INCOH=0自体が同じ内部不整合（断面積は
束縛込み・角度分布は自由電子）を持つ設定である」という、比較対象コード側の
モデル限界に起因することが分かった。

**教訓**:
- 「相互作用が起きるかどうかの確率」と「起きた後の挙動」を別々のサブルーチン・
  別々のデータソースで計算する設計では、両者が同じ物理近似レベルを前提にしているか
  を明示的に確認しないと、今回のような内部不整合が実装当初から静かに紛れ込む。
  レビュー・テストでは「それぞれの部分は正しいか」だけでなく「部分同士の物理的
  前提が揃っているか」を別途チェックする価値がある。
- 独立コード（EGS5）との相互検証は、単に「ChatCarloの実装ミスを見つける」だけ
  でなく、**比較対象コード側の設定（今回はINCOH=0 vs INCOH=1）によって
  結論が変わりうる**ことも教えてくれた。「EGS5と一致した/しなかった」を
  一枚岩の結論として書くのではなく、どちらの設定と比較したかを明記しないと、
  読者に誤った精度の印象を与える。
- Rayleigh散乱（原子形状因子F(Z,q)、q=0で最大→前方散乱優勢）とコンプトン散乱
  （非干渉性散乱関数S(Z,q)、q=0で0→前方散乱抑制）は、同じ「原子構造による
  補正関数」という枠組みでありながら、q=0での挙動が正反対になる。単体テストを
  Rayleigh用のテンプレートから複写した際、この違いに気づかず「重元素ほど
  相互作用確率が質量分率より過大代表される」という誤った予測をそのままテストに
  書いてしまい、実行して初めて誤りに気づいた（水素の電子密度Z/A=1が全元素中
  最大で、逆に水素が過大代表されるのが正しい）。物理的な類推でテストを書くときは、
  「似た構造の既存テスト」をそのまま複写するのではなく、対象の物理量が本当に
  同じ方向に効くかを都度確認すること。

## xraylib.CS_Photo_Partial は軽元素・高エネルギーでスプライン外挿エラーを起こす（K殻蛍光X線実装, 2026-07-17）

K殻蛍光X線（光電吸収後の特性X線放出、[docs/plan_fluorescence.md](plan_fluorescence.md)）
を実装し、`tests/test_fluorescence.py`以外の既存テスト全体（水を含む大半のシーン）を
流した瞬間に`ValueError: Spline extrapolation is not allowed`で即死した。

原因: `xraylib.CS_Photo_Partial(Z, K_SHELL, E)`（K殻イオン化確率の分子）は、
軽元素・高エネルギー域（例: 酸素Z=8でE>約103 keV）でテーブル外挿を拒否して
例外を投げる。診断領域の上限（150 keV）は水・軟部組織・空気の主成分である
酸素にとって「テーブルの外」になりうる。

**対応**: 呼び出し前に「その元素のK線が全て蛍光カットオフ(5 keV)未満」なら
そもそも蛍光を放出し得ないと分かるので、`CS_Photo_Partial`自体を呼ばずに
早期スキップする（`chatcarlo/physics.py: sample_fluorescence`）。酸素・
カルシウム等の軽元素はまさにこの条件に該当し、物理的に正しい理由で
問題のあるZ・E領域の呼び出しを回避できた。

**教訓**:
- 新しいxraylib API（今回は`CS_Photo_Partial`）を使うときは、実装対象の
  診断領域の下限だけでなく**全範囲**（軽元素×高エネルギーのような対角の
  組み合わせ）で例外が出ないか、実際に使われる材料組成全体で一度は
  総当たりしてから本実装に進むべきだった。単一元素（鉛）でのテストだけを
  先に書いて安心し、水（酸素+水素）を含む既存シーンでの回帰テストを
  後回しにしたために発見が遅れた。
- 「そもそも起こり得ない物理条件を早期に弾く」対処は、例外処理で握りつぶす
  よりも良い解決策になりやすい。今回は蛍光カットオフという既存の物理的
  足切りがそのまま安全装置としても機能した。

## K殻蛍光線リストの「4線で99%以上」は思い込みだった — EGS5相互検証で発覚（2026-07-18）

K殻蛍光の実装当初、`fluorescence_k_data`（[materials.py](../chatcarlo/materials.py)）は
主要4線（Kα2/Kα1/Kβ3/Kβ1相当: KL2/KL3/KM2/KM3）だけを使い、docstringに
「K放射遷移の99%以上を占める」と書いていた。この数字は検算せずに書いた思い込みで、
実際にxraylibで確認すると鉛(Z=82)では**95.05%しかカバーしていなかった**
（欠落分はKβ2系列KN2/KN3とKO/KP線、合計約4.95%）。

発覚の経緯: EGS5相互検証（Phase 4、[egs5_crosscheck/fluorescence/RESULTS.md](egs5_crosscheck/fluorescence/RESULTS.md)）
で、EGS5側の脱出光子エネルギーヒストグラムに、ChatCarlo実装の4線では説明できない
**88 keV付近の未説明ピーク**が出た。ChatCarlo単体のテスト（`tests/test_fluorescence.py`）
はPb/Wの主要2線の値をピンポイントで照合するだけで、「網羅率」自体は一度も
検算していなかったため、この欠落は単体テストでは検出できなかった。

**対応**: 線リストをKL2/KL3/KM2/KM3/KN2/KN3/KO/KPの8線に拡張。xraylibで
Ca(20)/Fe(26)/Cu(29)/W(74)/Pb(82)/U(92)につき実測したところ、全元素で
99.99%以上のカバー率になることを確認した。

**教訓**:
- 「有効な4線で99%以上を占める」のような**具体的な数字を伴う主張**は、
  実装時に一次データ（今回はxraylibのRadRate）で検算してから書くべきだった。
  検算しないまま書いた数字はコード内のdocstringであってもいずれ嘘になる
  （実際は95.05%であり、"99%以上"は誤りだった）。数字を書く箇所では
  「検算した」という事実そのものが担保になる。
- 単体テストは「実装が意図通り動くか」は検証できるが、「実装の設計判断
  そのものが十分か（この場合は線の本数）」は別軸で、テストがどれだけ通っても
  検出できない。**独立コードとの相互検証は、単体テストでは原理的に見えない
  「設計判断の甘さ」を暴く**（`docs/plan_egs5_crosscheck.md`が繰り返し
  述べている設計目的どおりの実例）。
- 相互検証で見つかった不一致（未説明ピーク）を「許容誤差の範囲内だから」と
  早々に切り上げず、ピークの位置・強度比まで定量的に説明できるまで追いかけた
  ことで、実装のバグを実装計画のバグ（docstringの誤った主張）ごと発見できた。

## EGS5のLATCH変数は、光電吸収で生成された蛍光光子に親光子のLATCH値を継承する（EGS5相互検証, 2026-07-18）

`tutor5`流のLATCH方式（コンプトンで+1、レイリーで+1000を加算し、LATCH==0のまま
脱出した光子を「一次（無衝突）光子」と数える）で、K殻蛍光を含むEGS5ユーザーコードを
書いたところ、蛍光ON条件の「一次透過率」が26.6%という明らかな異常値になった
（真の一次透過率はOFF/ON双方で~4.3%のはず、蛍光は光電吸収後の話なので一次透過には
影響しないはずだった）。

原因: 光電吸収で親光子が消滅し蛍光光子が生成される際、EGS5はLATCH変数を
**そのまま蛍光光子に引き継ぐ**。一度も散乱していない(LATCH=0)光子が光電吸収されて
蛍光光子を放出すると、その蛍光光子もLATCH=0のまま脱出し「一次透過」に誤分類される
（`egs5-operator`が対応、詳細: [egs5_crosscheck/fluorescence/RESULTS.md](egs5_crosscheck/fluorescence/RESULTS.md)
の「実行中に発見した重要な落とし穴」）。

**対応**: `iarg=19`（光電相互作用発生イベント、`egs5_user_manual.pdf` Table B.19）に
対し親光子破壊前に専用LATCHビットを立てることで、蛍光光子への継承を検出し、
蛍光/光電由来の光子を独立分類に分離した。

**教訓（次回のEGS5委任で必ず引き継ぐこと）**:
- EGS5でK殻蛍光（IEDGFL）を有効にしたユーザーコードを書くときは、LATCH方式の
  診断出力（一次/コンプトン/レイリー内訳）が蛍光光子のLATCH継承で汚染される
  ことを前提にコードを書く。`tutor5`のLATCH方式をそのまま蛍光ありのケースに
  流用する際は、この継承挙動を最初から想定しておくこと。
- 幸い、本検証の主評価量（脱出光子の全エネルギー透過率、脱出光子スペクトルの
  ピーク帯割合）はLATCH分類に依存せず`iarg=3`（脱出イベント）ごとの無条件加算
  だったため、この落とし穴は主要な数値結果には影響しなかった。ただし今後
  「一次/散乱内訳」を評価量に使う蛍光ありのEGS5検証では、この継承を踏まえた
  LATCH設計を最初から組み込む必要がある。
- 次回（copper・tungsten等でのEGS5相互検証）にこの教訓を確実に引き継ぐため、
  `.claude/agents/egs5-operator.md`にも同内容を追記した。

## PEGS5組込みデフォルト密度はChatCarlo基準密度と一致するとは限らない（EGS5相互検証, 2026-07-18）

鉛でのK殻蛍光相互検証（[egs5_crosscheck/fluorescence/](egs5_crosscheck/fluorescence/)）
では、PEGS5の鉛組込みデフォルト密度がたまたまChatCarlo基準（`materials.py:
_DENSITY_OVERRIDE["Pb"]=11.35`）と一致していたため、密度の指定漏れに気づかず
問題化しなかった。銅での相互検証（[egs5_crosscheck/fluorescence_copper/RESULTS.md](egs5_crosscheck/fluorescence_copper/RESULTS.md)）
でegs5-operatorが実行中に発見: **PEGS5の銅組込みデフォルト密度は8.9333 g/cm³**で、
ChatCarlo基準の8.96 g/cm³（`_DENSITY_OVERRIDE["Cu"]`）と一致しない（+0.3%差）。

**教訓**: 鉛での「偶然の一致」を一般則だと誤解しないこと。EGS5相互検証で新しい
材料を扱うたびに、PEGS5入力に`RHO=<ChatCarlo基準密度>`を明示指定し、
`pgs5job.pegs5lst`で実際に使われた密度を確認するステップを省略しない
（`vive-crosscheck`スキルの「想定される差異要因」表・`egs5-operator.md`にも
チェック項目として追記した）。タングステン検証では本教訓を反映済みで
RHO=19.3を明示指定し、問題は再発しなかった。**さらに `pgs5job.pegs5lst`
自体をリポジトリに保存し忘れると「確認した」という記述が検証不能な自己申告
になる**（銅検証でvive-auditorから指摘、監査時点で保存漏れが発覚した）。
密度確認ログは検証結果と同じ場所に必ずコピーして残すこと。

## 統計誤差は二項近似ではなく標本標準偏差から直接計算する（EGS5相互検証, 2026-07-18）

タングステンでのK殻蛍光相互検証（[egs5_crosscheck/fluorescence_tungsten/RESULTS.md](egs5_crosscheck/fluorescence_tungsten/RESULTS.md)）
で、蛍光ON条件（Step2）のEGS5側統計誤差を「脱出確率の二項近似 ×
平均脱出エネルギー/入射エネルギー」という簡易式で算出していたが、
vive-auditorの独立監査で「この式でもegs5job.outのヒストグラムからも
報告値(0.000375)を再現できない」と指摘され、実際にはσ数が3.416ではなく
3.729だったことが判明した（近似式が真の統計誤差を過小評価していた）。

**原因**: 蛍光ON条件では「脱出光子のエネルギー」が単純な二値
（透過/非透過）ではなく、蛍光光子由来の低エネルギー成分が混ざることで
分布の分散が二項近似の想定より大きくなる。脱出"確率"の二項分散だけを
考慮し、脱出光子の"エネルギー"自体のばらつきを平均値で代表させる近似は、
蛍光のように多峰的なエネルギー分布を生む物理過程が入ると精度が落ちる。

**教訓（次回のEGS5相互検証で必ず適用すること）**:
- 透過エネルギー割合のような量の統計誤差は、最初から「history毎の
  透過エネルギー（脱出しなければ0、脱出すればそのエネルギー）」の標本
  標準偏差を直接計算し`σ/√N`とする（ChatCarlo側は`final_energy`配列に
  `np.where(escaped, final_energy, 0)`を適用して`x.std(ddof=1)/√N`、
  EGS5側はエネルギーヒストグラムから`E[X²]-E[X]²`で分散を再構成する）。
  二項近似は「脱出する/しない」の二値だけで決まる量（脱出光子数そのもの等）
  には妥当だが、二値化できない連続量（エネルギー）には安易に流用しない。
- 蛍光OFF条件のような分布が滑らかな場合は近似と厳密値の差が無視できる
  程度だったため、この問題は蛍光ON条件で初めて顕在化した。「今まで
  問題なかった近似だから今回も大丈夫」と判断せず、新しい物理過程を
  含む条件では毎回、近似の妥当性を疑うこと。

## `Geometry`の既定bbox_margin_cm(50cm)がEGS5相互検証で低エネルギーの隠れた空気減弱バイアスを生む（20/150 keV相互検証, 2026-07-18）

`Geometry`は物体群のbboxに既定で全方向+50cmの余白（`bbox_margin_cm`）を
取り、その余白の外縁を「世界境界＝脱出」とみなす（[geometry.py](../chatcarlo/geometry.py)）。
物体の外側は`background`（既定`air`、真空ではない）なので、スラブを
`transport_photons`に直接渡す相互検証スクリプト（`docs/egs5_crosscheck/`配下）
でこの既定値をそのまま使うと、**光子はスラブを抜けた後もさらに約50cmの
空気中を飛行してから初めて「脱出」と判定される**。EGS5の`tutor5`系
ユーザーコードは通常スラブ外を真空とするため、この約50cm分の空気減弱は
ChatCarlo側だけに乗る隠れたバイアスになる。

**発覚の経緯**: 20 keV水スラブ透過率の相互検証（`water20kev/`）を
既存の60 keV版（`docs/egs5_crosscheck/run_chatcarlo_water60.py`、線源を
スラブ手前10cmに置き、bbox_marginは既定50cmのまま）と同じ書き方で作った
ところ、Beer-Lambert解析解29.68%に対しChatCarlo MC実測が28.08%と、
統計誤差(±0.06pp)の25σ相当という説明不能な乖離が出た。切り分けの結果、
線源とスラブの間の空気（10cm）とスラブ脱出後から世界境界までの空気
（既定bbox_marginにより約50cm）を合わせた「合計約60cmの空気路」による
減弱（20 keVでは`exp(-mu_air×60cm)`で約5.5%）が原因と判明。この減弱を
含めた解析解（`exp(-(mu_air×60 + mu_water×t))`）はMC実測と0.02pp差
（統計誤差以内）で完全に一致した。

**60 keV版は同じ問題を抱えていたが閾値内に埋もれていた**: 60 keVでは
`mu_air×60cm`の減弱が約1.35%しかなく、事前基準（解析解-MC差は2%以内）に
収まっていたため、`docs/egs5_crosscheck/RESULTS.md`のPhase 1では
「解析解12.762% vs ChatCarlo MC 12.589%」の差（相対1.36%）が
説明されないまま記録されていた。今回判明した空気路減弱がこの差の
主要因である可能性が高い（Phase 1の合否判定自体は変わらないため
遡って修正はしないが、この教訓として記録する）。100 keVの蛍光相互検証
（`fluorescence_copper/`・`fluorescence/`・`fluorescence_tungsten/`）も
線源ギャップ5cm＋既定bbox_margin 50cmで同様の構造を持ち、100 keVでの
60cm空気路減弱は約1.1%——これも各RESULTS.mdのStep1相対差(0.19〜1%程度)に
説明なく寄与していた可能性がある。

**対応（次回のEGS5相互検証で必ず適用すること）**: スラブ単体の透過率・
蛍光ピーク比較のようにEGS5側が真空境界を仮定する検証では、
`Geometry(geoms, bbox_margin_cm=<小さい値>)`を明示指定し、線源も
スラブ直近（数百μm〜数mm程度）に置いて、意図しない空気路を作らない。
`docs/egs5_crosscheck/water20kev/run_chatcarlo_water20.py`・
`water150kev/run_chatcarlo_water150.py`・
`fluorescence_copper_20kev/run_chatcarlo_fluorescence.py`・
`fluorescence_lead_150kev/run_chatcarlo_fluorescence.py`が
`bbox_margin_cm=0.01`を使う実装例。

**なぜ気づけたか**: 20 keVでは空気減弱が60 keV/100 keVよりずっと大きく
（光電効果のE^-3則）、統計誤差に対して説明不能なほど大きな乖離として
表面化したため。エネルギーを変えて同じ手法を再利用したことで、
既存の手法に潜んでいた小さいバイアスが顕在化した——「今まで閾値内
だったから問題ない」ではなく、パラメータ（エネルギー・幾何スケール）を
変えるたびに、既存の近似・簡略化が引き続き妥当かを疑うこと。

## 高速化でも「数値ロジックを変えない」だけでは不十分——暗黙の入力範囲制約に注意（輸送カーネル高速化, 2026-07-20）

`docs/plan_transport_speedup.md` Phase 1で断面積計算をxraylib直呼びからエネルギー
格子テーブル+補間に置き換えた。数値ロジック自体は変えていない（同じ物理量を返す）
つもりだったが、実装完了後にユーザー指示でセルフレビューしたところ、**エネルギー
範囲が暗黙のうちに[1, 200]keVへ制限される新規の回帰**が見つかった。旧実装
（xraylib直呼び）は入力範囲を一切チェックしておらず任意のエネルギーで動いていた
のに対し、新実装はテーブル外のエネルギーで`ValueError`を出す。しかも
`scene.py`はこの範囲を検証していなかったため、`source.spectrum`（物理検証用の
陽なスペクトル指定）で範囲外のエネルギーを指定すると`validate`は通過するのに
`run`実行時にクラッシュするfail-late問題になっていた。

**対応**: 上限を診断X線領域の設計スコープ「10–150 keV」（CLAUDE.md記載）に統一
（`_XS_GRID_MAX_KEV = 150.0`）。`scene.py`の`kvp`検証も20〜200から20〜150に狭め、
`source.spectrum`にも150 keV超をvalidate時にfail-fastで拒否する検証を追加した。

**教訓**: 「数値ロジックを変えない高速化」であっても、xraylib直呼びのような
「入力範囲を暗黙に無制限に許していた」コードをテーブル化・キャッシュ化すると、
テーブルの構築範囲という新しい有限の制約が生まれる。この種の変更をレビューする
際は「元々許されていた入力範囲が変更後も許されるか」を明示的にチェックリストに
入れること。境界値・範囲外入力は可能な限りvalidate層でfail-fastさせ、実行時の
fail-lateクラッシュにしない設計を徹底する。

## ベクトル化の最適化パターンは、ループの反復回数分布（長い裾があるか）を確認してから適用する（輸送カーネル高速化, 2026-07-20）

同じPhase 1/2の中で、`chatcarlo/materials.py`の断面積テーブル参照では
「複数元素混在時に検索(searchsorted)を1回にまとめる」最適化が有効だった（探索は
常に大きい均一バッチに対して行われるため）。この成功パターンを、構造が似ている
`sample_rayleigh_cos_theta`/`sample_compton_bound`の棄却サンプリングループにも
横展開したところ、**実測でむしろ悪化した**（soft_tissue 80 keVで176ms→253ms）。

原因を反復回数の直接比較で特定: 棄却ループは低受理率（特に軽元素・高エネルギーで
顕著、水80 keVで反復回数約5,499回）のため長い裾を持ち、後半`pending`が1〜数個
まで縮む。そこでは「複数元素をまとめて1回で検索する」利点がほぼゼロ（tiny batch
はほぼ単一元素）な一方、`np.unique`等の追加オーバーヘッドだけが乗る。

**教訓**: 「常に大きい均一バッチ」に効く最適化パターンを、形状の異なるループ
（棄却サンプリングのように反復ごとにバッチサイズが縮む・長い裾を持つループ）に
そのまま輸入すると失敗しうる。ベクトル化を適用する前に、対象ループの反復回数
分布（長い裾があるか、バッチサイズがどこまで縮むか）を先に実測してから最適化
方針を決めること。「一見筋が良い」変更でも、コード変更→再プロファイルの
サイクルを必ず回して実測で裏取りする（今回はrevertして事なきを得たが、
実測せず採用していたら性能が悪化したまま気づかない可能性があった）。

## 並列化の受入基準は「代表nを1点だけ選ぶ」のではなくスケーリング（nを振って）で判定する（輸送カーネル高速化Phase 3, 2026-07-21）

Phase 3（マルチプロセス並列化、`docs/plan_phase3_parallel.md`）の計画時、受入基準を
「chest_room.yaml n=1e6, workers=4で対serial 3倍以上」と1点だけ事前登録した。
実装後にこのnで実測すると2.36倍にとどまり目標未達だった。原因はワーカー起動固定費
（import＋断面積テーブル再構築＋SpekPy、1ワーカーあたり約0.84秒）が、n=1e6を
4分割した際の1ワーカー分の計算時間（約4.7秒）に対して約18%という無視できない比率を
占めるため。nを大きくして再実測すると、n=4e6で2.87倍、n=1e7で3.22倍（workers=8で
3.98倍）と、**nが大きくなるほど並列効率が単調に改善する**ことが分かった。

このプロジェクトの並列化の本来の動機は「n=1e5〜1e6では統計が不足する遮蔽評価に
n=1e7〜1e8を現実的な時間で回す」ことであり、まさにその大規模n域でこそ目標を
達成していた。にもかかわらず計画時に選んだ代表値n=1e6は、固定費オーバーヘッドが
相対的に大きく出る「並列化に不利な」点であり、実運用の主眼とズレていた。

**教訓**: 固定費（起動コスト・ウォームアップ）を持つ並列化・バッチ処理の高速化を
計画する際、受入基準の代表nは1点だけで決め打ちせず、**実際の運用レンジ全体で
スケーリング曲線（n vs 倍率）を取ってから、どのn帯で目標を達成すべきかを判定する**
こと。1点だけの代表値評価は、たまたま固定費比率が高い/低い点を選んでしまうリスクが
あり、「未達」という誤った結論にも「達成」という楽観的すぎる結論にも転びうる。
計画段階で「n=100倍」のような複数桁のレンジを事前登録しておくのが望ましかった。

**再発（2026-08-13、GPU相場観計測route1_mcgpu）**: 別プロジェクト（MC-GPU on Colab
T4の実測）でも同型の失敗が起きた。N=1e8のスループットを「3反復の中央値」という
1点の代表値で報告したが、実際には同一Nの連続実行で0.529→0.811→1.430→1.431秒と
単調に性能が低下しており（比2.71倍）、中央値1点は範囲の下端しか語っていなかった。
今回は**ウォームアップ実行の結果を捨てる設計**（`timed_run(n,'warmup',True)`の
戻り値を使わない）が追い打ちをかけ、最速値（189 M hist/s）の証拠がノートブックの
出力（`p3_measurements.json`）から完全に失われていた——`execution.log`という
副次的なログにしか残っておらず、しかもそのログ自体がセッション開始時に
truncateされる設計だったため、再実行していれば消えていた。**教訓の一般化**:
固定費だけでなく「増幅する側」（起動直後が速くて後で遅くなる、逆方向のドリフト）
も1点評価では捉えられない。ベンチマークコードを書く時点で、ウォームアップを
含む全実行の生値を主要な出力ファイルに残す設計にしないと、後から「実は全データが
あったのに一部だけ見ていた」という発覚をする。

## 完了報告の前に、受入基準とリスク欄を1項目ずつ照合する（2026-07〜08、再発 n=4 以上）

- **結論**: テスト全通過は受入条件の達成ではない。Phase 3 はメモリ実測を飛ばし（1 cm で 1.6 GB/ワーカー、0.5 cm で 12.6 GB/ワーカー）、タリー精密化は速度だけ見てメモリ基準を未測定のまま「達成」と報告した。Phase 0 は受入条件約30項目に新規テスト11件で、D-1・D-3 の回帰テストが無く、実装した判定の成果物 CSV も生成されていなかった。
- **Why**: 実装に集中すると、散文に書いた横断的な項目（メモリ、入力範囲、境界値、秘密情報）が抜ける。独立監査は渡されたデータの欠落や公開設定までは見ない。route1_mcgpu では事後の自己レビューだけが個人メールの混入と結果の欠落を見つけた。
- **How to apply**: 完了報告の前に、計画の受入条件とリスク緩和策を1行ずつ、実行した証拠（テスト関数名、測定値、`ls` した成果物）と突き合わせる。Codex の要約の「一部／全て」は生データで確かめ、環境固有とされた失敗は手元で再実行する。比較を扱う計画は `git status`、別 seed、`assert` の安全性、定数の重複、テストの経路まで見直す。メモリ測定もスクリプトに残し、数値が食い違ったら同じスクリプトで全アームを測り直す。

## 比較スクリプトの出力パスのハードコードが、正典検証データを黙って上書きする（レイリー/コンプトン棄却サンプリング再設計, 2026-07-21）

`docs/plan_rayleigh_compton_importance_sampling.md` Phase 3で、レイリー角度サンプリング
新実装(逆変換2段階方式)のPDD60相互検証結果が旧実装よりわずかに緩い(0.16% vs 0.018%)
ことが系統誤差でないか確認するため、`compare_pdd60_incoh1.py`を別seed用にコピーして
実行した。ところが同スクリプトは出力先`comparison_table.csv`を**絶対パスでハードコード**
しており、コピーを実行しただけで**tracked済みの正典比較結果CSVが新データで上書き**
された（正典JSON`chatcarlo_pdd60_results.json`自体は無傷だったが、CSVは黙って書き換わった）。
`git status`でtracked fileの変更に気づき`git checkout`で復元、正典JSONとのbyte一致を確認して
実害はなかったが、`git status`を挟まなければ気づかずコミットしていた可能性が高い。

これは前計画`plan_transport_speedup.md`の「EGS5再検証で正典JSON/ログを上書きしない」
という教訓が**主要スクリプト本体**については既に周知されていたのに、**それをコピーして
別データで走らせる派生スクリプトの出力パス**という盲点には及んでいなかったケース。

**教訓**: (1) `egs5_crosscheck/`配下の比較・検証スクリプトは出力パスが絶対パスで
ハードコードされているものがあり、別データで再実行する際はスクリプト本文を読んで
出力パスも書き換える（`sed`等で機械的に変えるなら対象に含める）。(2) 正典データに
触れる可能性のある操作（比較スクリプトの実行・コピー実行含む）の**直後**には必ず
`git status`で意図しない差分がないか確認する——「上書きしないように出力先を変えた
つもり」でも見落としはあるため、最終防御は`git status`。(3) 事故が起きなかったのは
たまたま確認したからであり、次に似た作業をするときは最初から「このスクリプトは
出力先をハードコードしているか」を実行前にチェックする。

## 「テストが通った」は「テストが壊れたコードを落とせる」の証明にならない——ミューテーション試験で見つけた無検証の核心項（統計不確かさPhase 1・2, 2026-07-22）

`docs/plan_statistical_uncertainty.md`のバッチ統計推定器 σ̂²=(Q-T²/N)/(M-1)
（Q=ΣS_b²/n_b）を実装しテスト27件を全通過させた後、「テストが本当に壊れたら
落ちるか」を確認するため主要4箇所を意図的に壊してテストを再実行した
（`ScalarMoments.add_batch`の`/n_b`削除、`M-1`→`M`、`standard_error`の`/√N`削除、
`VoxelGrid.end_batch`の`/n_b`削除）。前3つは複数件が確実に失敗したが、
**`VoxelGrid.end_batch`の`/n_b`削除だけは27件全てが通過し、検出できなかった**。

**原因**: グリッドのRの絶対値を検証していたテストが全てn_b=1（`/n_b`が恒等変換に
なる条件）で書かれていた——「バッチ内history数で正規化する」という、この計画で
最も新規性が高く不等バッチを成立させている当のロジックが、実質無検証のまま
「全テスト通過」を報告していたことになる。`ScalarMoments`側だけ検出できたのは、
n_b=1000とn_b=1を偶然突き合わせるテストを書いていたためで、設計判断ではなかった。

**対応**: (1) 実装の`Q=ΣS_b²/n_b`という式を使わずに、分散分析の群間平方和
SSB=Σn_b(x̄_b-x̄)²という独立な式から期待値を組むテストを追加、(2) 同一の
per-history列をn_b=1とn_b=Kでグループ化したときσ̂²が同じ母分散を推定して
いることを確認するテストを追加。両方とも、同じミューテーションを再投入して
「今度は落ちる」ことまで確認した。

**教訓**: (1) テストカバレッジは「行が実行されたか」ではなく「その行の**係数・
符号・分母**が間違っていたら検出できるか」で測る——n_b=1ばかりのテスト集合は
`/n_b`の有無を区別できない縮退ケースだった。(2) 新しい数式を実装したら、
実装と**同じ式変形をなぞらない独立した検算式**（今回はANOVA恒等式）で最低1件は
期待値を組む。実装をコピーして期待値にすると、実装のバグごと検算も通ってしまう。
(3) 「壊して確認する」（ミューテーション試験）は、複雑な数式の推定器を実装した
直後に安く効果が高い——今回は4箇所中1箇所で実際に穴が見つかった。

同じレビューで、Phase 2で既定を`track_uncertainty=True`にした際の実装上の
問題も3件見つかった: メモリ警告式（`__main__.py`）が新しい既定値を反映しておらず
実態より過小に見積もっていた（chest_room 1cm・workers=4で実態25.7GBを7.9GBと
報告）、設計判断で決めた逃げ道`--no-uncertainty`をPhase 3に先送りしたため
ユーザーがメモリ増加を回避できない期間があった、並列時に集約専用の親グリッドが
使わないスナップショット配列を確保していた（1cm解像度で約1.6GB死蔵）。
いずれも「動く」ことは確認済みだったが「既定値を変えた影響が他の場所に
正しく伝播しているか」は別軸のチェックが要る、という個別の教訓として記録する。

## 「動いて見える」canvas JSは目視確認だけでは検証にならない——look-atカメラの罠とミューテーション試験（光子軌跡アニメーション, 2026-07-22〜23）

`docs/plan_photon_animation.md`のPhase 0〜4を実装し、一度はブラウザのスクリーンショットで
「対向・リレー視点で入射・出射の両ベクトルが同一フレームに映っている」ことを確認して
完了と報告した。しかしユーザーに依頼されて自分の実装を批判的に読み直したところ、
実際には**出射ベクトルは常に不可視**だったことが発覚した——リレーカメラをレッグ自身の
延長線上に置いて光子の現在位置を注視する設計だったため、カメラ・干渉点・光子位置が
厳密に一直線（同じ画面座標に投影される縮退）になっており、スクリーンショットで
「見えた」ものは実は前のレッグの残像（trail）だけだった。目視確認は「それらしく
描画されている」ことしか検出できず、投影座標を実際に計算するまで気づけなかった。

その場しのぎで側方カメラ（side vector）に置き換えても、**光子の現在位置を毎フレーム
注視し続ける（`buildBasis(campos, state.pos)`を毎フレーム呼ぶ）設計そのもの**が
別の問題を生んだ——カメラが常に光子へ振れ直すため、光子が干渉点から数フレーム離れると
入射側の軌跡が視錐台の外（カメラ後方）へ出てしまう。最終的に解決したのは
**forward = normalize(dirOut − dirIn) を固定の注視方向とし、カメラ位置・姿勢を
レッグ内で完全に固定する**設計——この式を使うと、入射側軌跡 z_in(s) = offset −
s·dot(dirIn,forward) と出射側 z_out(s) = offset + s·dot(dirOut,forward) が
区間長sによらず常に正（カメラ前方）であることが代数的に導ける。

**さらに深刻だったのが一人称カメラのupベクトル**: `fpState.up`というモジュール直下の
可変状態を`draw()`が呼ばれるたびに書き換えて引き継いでおり、カメラ姿勢が「clockの
純粋関数」ではなく「draw()の呼び出し履歴」に依存していた（シークバーを逆再生・
ジャンプすると順再生と異なるロールになる）。修正は、光子選択時に一度だけ
`buildUpAtSegStart()`で各区間開始時点の決着値を事前計算し、以降は
`(traj, segStarts, upAtSegStart, clock, curSeg)`のみから姿勢を導く純粋関数に
書き換えること。ここで**最初に書いたミューテーション試験は検出に失敗した**——
同一方向への繰り返しGram-Schmidt射影は偶然「冪等」になるため、テスト用トラジェクトリの
2つの区間がたまたま同じ方向だったせいで、蓄積型バグを再現しても値が一致してしまった。
3区間を互いに直交させたトラジェクトリに差し替えて初めて、バグを確実に検出できた。

**対応**: `tests/test_animate_js.py`を新設し、出荷JSソースから対象関数をブレース
対応で直接抽出してnodeで実行、実際の計算結果を数値検証する方式にした（「関数名が
文字列として存在するか」ではなく）。加えて、テストを書いた直後に対応するコードへ
意図的にバグを再注入して「本当に落ちるか」を確認するミューテーション試験を
各修正で実施——上記のとおり1回はこの試験自体が不十分だったことも、この試験
プロセスによって気づけた。

**教訓**: (1) canvas/WebGL系のカメラ数学は、目視スクリーンショットだけでなく
実際に投影座標を計算して「どの点がどこに写るか」を数値で確認する
（縮退・視錐台外れは特定の角度でしか症状が出ないことがある）。(2) 「対象を
追い続けるカメラ」は数学的に見た目以上に危険——注視点を毎フレーム動かすと、
それ以外のものが視野から外れる速度も変わってしまう。カメラ姿勢は可能な限り
区間内で固定し、必要なら注視点ではなく描画対象の位置の方を動かす設計を優先する。
(3) 可変状態を挟むと「clockから姿勢への写像」が純粋関数でなくなり、シーク
バーの逆再生・ジャンプで簡単に壊れる——JS側でも「同じ入力に対して常に同じ
出力」を保てる設計を優先し、フレーム間で引き継ぐ状態は本当に必要か疑う。
(4) JSロジックのミューテーション試験は、試験データの選び方（今回は「同一方向を
含むか」）次第で偽陰性になりうる——ミューテーション試験を書いたら、その試験
自体も「本当に壊れたコードを落とせるか」を別の切り口のデータで疑うこと。

同じセッションで、デモ用シーン選定の見落としも見つかった: `chest_room.yaml`
（検出器背後に厚さ15cmのコンクリート壁）を転帰4分類（直接透過/散乱後脱出/
後方散乱/吸収）のデモに使ったところ、無相互作用透過率が約1.6×10⁻⁴と極めて
低く、n=5000でも「直接透過」が1本も出なかった。物理的には正しい結果だが、
確率的分岐を見せる教材としては4分類のうち1つが実質再現不能という欠陥。
**教訓**: 複数の離散的な転帰・分岐を見せる機能のデモシーンは、採用前に
実際の出現頻度を実測し、全分岐が妥当なnで再現できるか確認する。

もう1点、実装中に自分で作り込んだ罠: PythonのCATEGORY_LABELSプレースホルダー
置換で`str.replace()`（全出現を置換）を使っていたところ、コード内コメントに
プレースホルダーと同じ文字列`__SHARED_CANVAS_JS__`を人間向け説明として書いて
しまい、コメント内の言及まで実際のJSコードで置換されて二重埋め込みになった。
**教訓**: テンプレートのプレースホルダートークンと同じ文字列は、同一ファイル内の
コメントであっても書かない（`.replace()`は文脈を区別しない）。

## 統計不確かさPhase 4: 検証スクリプトのJSON成果物は「再実行すれば裏取り完了」ではない（2026-07-26）

`docs/egs5_crosscheck/run_chatcarlo_pdd60.py`の手書きSEM計算を`chatcarlo.tally`の
公開推定器に置き換えたあと、素朴に「再実行して`chatcarlo_pdd60_results.json`と
`PDD_RESULTS.md`記載値を比較」したところ、平均線量自体が最大2.6%動いていて
青ざめた——見積もりの置き換えでは平均値(T/N)は変わらないはずなのに。原因は
推定器の変更ではなく、このJSONが最後に生成されたコミット（`d597c66`、
2026-07-17）以降に`b732d35`/`88ee64b`（K殻蛍光X線）・`34a6313`（断面積の
テーブル化＋補間）・`e99a2b0`（レイリー/コンプトン棄却サンプリングの
逆変換2段階方式への再設計）が入っており、**同じseedでも
現在のtransport.pyは既に別の乱数消費列・別の物理結果を返す**ようになっていた
ため——JSONが最後に固定された時点からコード自体が動いていた（私の変更とは
無関係）。

**この特定作業自体でも自分がミスをした（2026-07-26の再点検で発覚）**: 上記の
生成コミットを最初は`7cb951a`と書いていたが、実際は`d597c66`だった。
`git log --oneline -- <file>`の出力（新しい順）を読むとき、**最上行を取る代わりに
「コミットメッセージが自分の想定した物語に一番合う行」を選んでしまった**
（`7cb951a`は"Phase 2b残差を−1.71%→−0.91%に縮小"という、まさにPDD_RESULTS.mdの
記載と対応するメッセージだったため）。さらに無効化要因の列挙も不完全で、
断面積のテーブル化＋補間（`34a6313`、断面積の数値そのものを変える変更なので
線量への影響は蛍光X線より直接的）を落としていた。
**教訓の追加**: 「いつ生成されたか」をコミットで特定するときは、`git log`の
**出力順序に従って機械的に最上行を取る**（`git log -1 -- <file>`で1行に絞れば
選択の余地自体をなくせる）。メッセージの内容で選ぶと、確証バイアスで
「話に合う方」を掴む。また「その後どんな変更が入ったか」は記憶で列挙せず、
`git log <生成コミット>..HEAD -- <関係するソースファイル>`で機械的に洗い出す。

このJSONは`compare_pdd60_incoh0/1.py`が読んで比較図（`pdd60_comparison.png`等）を
作り、`PDD_RESULTS.md`はその図から読み取った具体的なパーセンテージ
（「47ビン平均相対差−0.91%」等）を本文に埋め込んでいる。JSONだけ現在の物理で
再生成してコミットすると、これらの下流の図・パーセンテージとJSONが食い違う
「サイレントな不整合」を作ってしまうところだった。

**教訓**: (1) 推定器やSEM計算の置き換えを検証するときは、「チェックイン済みの
古い成果物と再実行結果を単純比較」ではなく、**旧実装コードそのものを現在の
コードベース上で動かした結果**と**新実装コードを現在のコードベース上で動かした
結果**を比較する——これで変数（推定器の実装差）を1つだけに絞れる（本件は
両者が浮動小数点誤差レベル(~1e-16)で完全一致し、置き換えが数値的に無害だと
証明できた）。(2) 検証スクリプトの出力JSON/PNGが別のドキュメント（本件では
`PDD_RESULTS.md`の具体的なパーセンテージ）に転記されている場合、そのJSONを
「今のコードで再生成すれば裏取り完了」と考えてはいけない——転記元のドキュメント
自体を今の物理で再検証（EGS5側も含めて）する、別スコープの大仕事になる。
本セッションでは範囲外と判断し、チェックイン済みJSONは元に戻し
（`git checkout`）、置き換えたのはスクリプトの推定器呼び出しコードのみに留めた。
`PDD_RESULTS.md`のEGS5相互検証結果自体が現在の物理コードに対して再検証が
必要な状態であることは将来の課題のメモに申し送る。

## タリー精密化: ドキュメントに書いた「原因の推測」は、推測のまま何年も残る（2026-07-26）

`accumulate_track_length`（カーマ/H*(10)のtrack-length estimator空間分配）を、
サブステップ+層化乱数点によるモンテカルロ分配から、区間とグリッド境界面の
交点を解析的に列挙する厳密グリッド走査（3D DDA、乱数不使用・分散ゼロ）へ
置き換えた（`_segment_grid_traversal`、EGS5相互検証スクリプトで監査済みの
単一直方体版`_segment_box_overlap_cm`をグリッド全体へ一般化したもの）。

このとき、CLAUDE.mdの"Known sharp edges"に**2026-07-17頃から**「解像度を
細かくすると最大値が増大するのは`max_substeps`クランプ由来の極値統計と
推定・未検証」と書かれたまま放置されていたものを、`max_substeps`クランプ
そのものを撤廃した新実装ができたことで初めて再検証できた。**結果はこの推測が
誤りだったというもの**: 新旧タリーを同一解像度で直接比較すると、平均値は
0.0625cmまで統計誤差内で完全に一致した（旧実装のRがやや大きいだけ——
空間分配自体のモンテカルロ分散が上乗せされている分）。実際の機構は
「ボクセルサイズがビーム/照射野の局所的な実効幅より大きい間の通常の空間平均化」
で、ボクセルが実効幅を下回るとプラトーに収束する物理的に正しい挙動だった
（照射野を4倍広げるとプラトーへの転換点もほぼ4倍粗い解像度側へ移動することで
定量的に確認、advisor指摘による追加実験）。

**教訓**: ドキュメントに「〜だと推定される（未検証）」と書いた原因の仮説は、
検証する仕組みが後から整うまで**何年でもそのまま真実のように読まれ続ける**
（実際、統計不確かさPhase 0〜4を挟んで1週間近く放置された）。「未検証」の
但し書きを付けたからといって免責されるわけではなく、次にその仕組みが手に入った
ときに**必ず再検証まで実施する**（本件は前回セッションで「再検証はまだ、
将来の課題のメモ候補3に申し送り」と明記していたおかげで、着手時に
存在を思い出せた——申し送りの効能）。

**もう一つの教訓（advisor相談で発覚した自分の実験設計の穴）**: 「線源近傍の
1/r²発散」を検証するつもりで作ったシナリオB（線源から3〜7cmの空気中）は、
実際にはfield=[35,43]cm@SID180の照射野がその距離でもまだ有限幅（~0.8cm）を
持っていたため、シナリオAと**同じ「ビーム幅とボクセルサイズ」の機構を
別の幅で再現しただけ**で、真の点線源特異点（r→0）は検証できていなかった。
自分では「線源に近いから1/r²のはず」という設計意図だけで満足しかけたが、
advisor相談で「その距離での実効ビーム幅を計算したか」と問われて初めて気づいた。
**教訓**: 「〜の近くだから特異的/極端なはず」という設計は、実際にその位置での
支配的なスケール（ここでは照射野の幾何学的広がり）を数値で確認してから
実験を組むこと。近さだけでは特異性は保証されない——真に検証するには、
照射野の広がり自体がゼロに収束する条件（線源のごく近傍、または照射野なしの
理想的点線源）を明示的に作る必要があり、これは本セッションでは未着手のまま
将来の課題のメモへ申し送る。

## 速度比較: 計測スクリプトが本番の実行経路を迂回していたのに「Nに対する傾向」と解釈した（2026-07-27、EGS5速度比較の翌ターンに発覚）

**症状**: EGS5との速度比較で、監査指摘（外挿区間のスループット未検証）に応えて
water60_freeをN=5,000,000で追加測定したところ、ChatCarloのスループットが
N=1e6の349,094 hist/sから333,860 hist/sへ4.4%低下した。これを「Nが大きくなると
ChatCarloは相対的に不利になる」という**物理的・構造的な傾向**と解釈し、
「外挿区間では比がChatCarloに不利な方向へ広がる（4.35x→4.53x）」と結論して
RESULTS.mdに記載・コミットした（vive-auditor監査も通過済みだった）。

**実際の原因**: 計測スクリプト`docs/speed_comparison/chatcarlo_timing.py`は
`transport_photons`を**直接**呼んでおり、CLIの本番経路である`run_transport`の
バッチ分割（`batch_size`既定200,000）を迂回していた。つまりN=5e6の測定は
「500万光子を単一バッチで処理」という、CLIでは決して発生しない条件だった。
低下の原因はNではなく**バッチサイズ**（キャッシュ効果）。独立にバッチサイズ
依存性を測ると 25k→325,834 / 100k→355,439 / 200k→347,996 / 2e6→333,177 hist/s
と、大バッチ側でのみ低下する。同じN=5e6をCLI既定の200kバッチで処理すると
356,645 hist/sで、低下は再現しない（むしろN=1e6より高い）。正しい比は4.24xで、
「広がる」ではなく「わずかに縮まる」だった。

**なぜ検出できなかったか**:
1. 変数を1つだけ動かしたつもりで、実は2つ動いていた（N=1e6→5e6と同時に
   バッチサイズも1e6→5e6に動いていた。両者が計測スクリプトの構造上、
   分離不能に結合していた）。「Nを変えた」という自己申告を、
   コードが実際に何を変えているかで裏取りしなかった。
2. 監査に出したときも、計測スクリプトが`run_transport`ではなく
   `transport_photons`を直接叩いていることを**依頼文に書かなかった**。
   監査人はスクリプトの計測範囲（perf_counterが何を挟んでいるか）は
   確認したが、「その呼び出し方が本番経路と違う」という観点は
   依頼に含まれていなかったため検出されなかった。監査は依頼の質を超えない。
3. 「EGS5は横ばい、ChatCarloは低下」という**結論が事前の予想と整合していた**
   （Python/NumPyはNが増えるとキャッシュ的に不利、という筋書き）ため、
   確証バイアスで追加検証せずに受け入れた。予想と合う結果ほど疑うべきだった。

**教訓**:
- **ベンチマークスクリプトは、本番の実行経路と同じ経路を通っているかを最初に
  確認する。** 迂回している場合（テスト容易性のためにカーネルを直接叩くなど）は、
  その差が測定対象の変数と交絡しないかを明示的に検討し、文書に書く。
- **「Nを変えた」つもりの実験で、Nに連動して動く他のパラメータがないか確認する。**
  スクリプトが `f(N)` を1回呼ぶ設計だと、Nとバッチサイズが原理的に分離できない。
- **監査依頼には「計測がどの経路を通っているか」を明記する。** 監査人はコードを
  読むが、依頼に無い観点は優先度が下がる。批判的レビューの方針の
  「自分の"修正済み"も同じ厳しさで再検証」と同根で、今回は"検証済み・監査済み"の
  ラベルが付いた後に誤りが残った。
- 関連する既存教訓: 「1回測定を報告するな」（2026-07-26）は反復回数の話だったが、
  今回は**反復しても直らない**種類の誤り（系統的な条件設定ミス）。反復・中央値は
  ジッタには効くが交絡には効かない。

## Phase B-1b: シナリオ名"water60_free"がEGS5側では別の物理モデル(IBOUND=0)を指していた（2026-07-28）

per-historyカーネル（`chatcarlo/kernel.py`）をEGS5確立値と再照合する層3検証で、
`docs/speed_comparison/chatcarlo_timing.py`のシナリオ名`water60_free`をそのまま
借用し、EGS5側の確立値として`docs/egs5_crosscheck/RESULTS.md`にある「EGS5
`water60_free/`（IBOUND=0, 12.02%）」を素朴に使ったところ、カーネル実測
（12.76%、Beer-Lambert解析解とも一致）との相対差が6.1%・14σという説明不能な
乖離になった。

**実際の原因**: `docs/egs5_crosscheck/RESULTS.md`は元々「第1回実行
（IBOUND=0）は事前基準を超過して不合格、原因は物理モデル差（自由電子KN vs
束縛コンプトン）と判明、第2回実行（IBOUND=1、`water60_bound/`ディレクトリ）で
物理モデルを揃えて合格」という経緯を記録済みだった。つまり**"water60_free"は
過去に「不合格と判明した」比較条件の名前**であり、現在ChatCarlo/カーネルが
使う束縛コンプトンと整合する確立値は"water60_bound"（12.70%）の方だった。
`chatcarlo_timing.py`（速度計測専用、物理モデルの一致は論点にしていない）が
この名前をそのまま採用していたため、名前だけを見て「確立済みの比較対象」と
誤認した。

**なぜ検出できなかったか**: 「EGS5相互検証は既に合格したはず」という前提を
下敷きに、シナリオ名が指すディレクトリの中身（IBOUND設定）を確認せず、
記憶にあった「water60_free=12.02%」という数値をそのまま転記しようとした。
14σという極端な値が出た時点で「これは変だ」と立ち止まり、元のRESULTS.mdを
読み直したことで発覚した——結果が事前予想と大きく外れたので疑った、という
点は批判的レビューの方針の教訓通りに機能した。

**教訓**:
- **シナリオ名は仕様ではない。** 過去のファイル名・変数名を再利用するときは、
  それが指すディレクトリ・パラメータの中身（この場合IBOUND値）を毎回確認する。
  名前が同じでも、命名した時点の文脈（ここでは「速度計測用に物理モデル一致は
  問わない」）と、今使おうとしている文脈（「物理モデル一致が前提の相互検証」）が
  食い違えば、名前だけでは正しい参照先を保証しない。
- **「以前不合格だった条件」の記録は、後から見ると「確立済みの値」に見えてしまう
  罠がある。** RESULTS.mdは経緯を時系列で書いているため、最初に出てくる数値
  （IBOUND=0の12.02%）を最終値と誤読しやすい。参照する時は「最終的にどの条件が
  合格したか」の結論部分だけを引用する（今回は`water60_bound`の12.70%）。
  他のシナリオ（water20kev/water150kev）はIBOUND=1で一発合格しており最終値=
  最初の値だったため、今回のようなすり替わりが起きるのはPhase 1（60 keV）だけ
  という点も、事前に他シナリオのRESULTS.mdを読んで確認しておくべきだった。

## Phase B-2: 計測規律を一部の測定にだけ適用し、同一ドキュメント内で守った数値と守っていない数値が混在した（2026-07-28、`/furikaeri`で発覚）

B-2（タリー統合）のスループット結果として「現行比1.64x（目標3倍未達）」と
`docs/plan_chatcarlo_speedup_post_egs5.md`・コミットメッセージに記録したが、
`/furikaeri`でこの数値を再測定したところ1.44xまで変動した。原因は、この
測定だけ参照実装3反復→カーネル1スレッド3反復→カーネル8スレッド3反復という
**逐次ブロック測定**（インターリーブなし、アーム順固定）で行っており、
本セッション自身がB-1a/B-1bのスループット表では守っていた規律
（`docs/speedup_baseline/tally_speedup_timing.py`と同じ「インターリーブ
3反復以上・中央値・アーム順を固定しない」、`order_variants`で反転順を使う等）
を、この1箇所だけ省略していたため。同じセッション内でDDAの内訳（75%、cProfile
3回で74〜76%と安定再現）は規律通り複数回確認していたのに、その直後に書いた
速度比の方は確認していなかった——**「この数値は重要だから慎重に」というときほど、
時間的余裕のなさから規律を飛ばしやすい**という逆説がある。

**なぜ検出できなかったか**: 測定自体は一応複数反復（3回）していたため「反復した
から大丈夫」という感覚があった。しかし反復回数と、反復の「順序を固定しない」
（インターリーブ）は別の規律であり、前者だけ満たして後者を満たさない測定は、
装置のウォームアップ・熱・他プロセスの影響等の系統誤差を拾いやすい
（本件がその系統誤差かどうかは未確認、単に測定間の分散が大きいだけの可能性もある）。

**教訓**:
- **「反復した」と「インターリーブした」は別の規律であり、片方だけでは
  不十分と自覚する。** 同一セッション内で片方の規律を守った測定（DDA内訳）と
  守っていない測定（速度比）が並ぶと、後から読んだ人（自分を含む）はどちらも
  同じ信頼度だと錯覚する。
- **結論を変えない程度の数値のブレなら実害は小さいが、それでも「参考値」と
  明記する。** 1.44x〜1.64xのどちらでも「3倍に遠く届かない」という結論は
  変わらなかったため実害はなかったが、もし基準値（3倍）に近い際どい数値
  だったら、規律の緩みがそのまま合否判定の誤りに直結していた。
- 関連する既存教訓: 「計測スクリプトが本番の実行経路を迂回していたのに
  『Nに対する傾向』と解釈した」（2026-07-27）と同根——**計測の「型」自体を
  都度チェックリスト化して確認する**（このセッションでは表を作った測定は
  型を守り、単発のプロファイリング検証として書いたコードは型を省略した）。

## njitスカラーDDA導入: 実装エージェント(Codex)の自己診断した根本原因が誤っていた（2026-07-28）

`docs/ai/plans/2026-07-28-njit-dda-e2e-measurement.md`の実装で、複数バッチ
（60k×3+20k）条件のみkerma/H\*(10)が参照実装（numpy）と最大絶対誤差
8.06e-06で不一致になった。実装したCodexはこれを「1バッチでは完全一致し
複数バッチでは非ゼロ集合も一致しているため、DDAの配線ミスではなく、
既に値を持つtargetへ次バッチを加える際のnumpy集約経路とnjitスカラー経路の
浮動小数点加算順の差」と自己診断し、この診断をそのまま報告した。

この診断を鵜呑みにせず、独立に4段階の診断スクリプト（scratchpadに保存、
`diag_batch.py`→`diag_perbatch.py`→`diag_bisect.py`→`diag_seg.py`）で
検証したところ、**単一バッチ（batch1）だけを新品のゼログリッドに対して
単独実行しても同じ誤差が再現した**——この時点で「累積加算の順序差」という
説明は成立し得ないことが確定した（累積が一切発生しない条件で再現したため）。
さらに二分探索でその原因区間を1本まで特定し、境界面インデックスが
`_EPS_PLANE=1e-7`以内（3.811e-08）にある終点を、参照実装は面として除外するが
njit試作は`tol=2e-12`という別目的（同時刻の同着判定）の桁違いに厳しい閾値
しか持っておらず除外し損ねていた、という境界セマンティクスの欠落が真因だと
判明した（電荷保存則は成立、ボクセル間の再配分のみが誤り——合計値は一致する
ため`sum`だけの検証では見逃す）。

**なぜ検出できなかったか（Codex側）**: 「1バッチ一致・複数バッチ非ゼロ集合も
一致」という限られた観測事実から、最も一般的で説明力の高そうな仮説
（浮動小数点加算順）に飛びつき、それ以上の切り分け（単一バッチを孤立実行する
だけで反証できた）を行わなかった。

**教訓**:
- **実装エージェントの「自己診断した根本原因」は、実装コード自体と同じ
  重みでしか信用しない。** 診断が最終テストにパスしているように見えても
  （このケースではタイミング測定に進む前に正しく停止したため一見「正しく
  安全側に倒した」ように見える）、原因の特定自体が誤っていれば、その後の
  修正方針全体が誤った方向に進みかねない。
- **反証実験は「最小の孤立条件」まで削ってから理論を採用する。** 「累積加算が
  原因」という仮説は、累積が起きない最小条件（単一バッチを新品グリッドへ）で
  即座に反証可能だった。仮説を採用する前に、その仮説が排除できる最小条件を
  自分で作れないか考える。
- **合計値・非ゼロ集合の一致だけでは、ボクセル単位の誤配分を検出できない。**
  今回のバグは総和が保存されていた（1つのボクセルへの寄与がわずかに隣接
  ボクセルへ漏れただけ）ため、grid-sum比較では原因はおろか不一致自体を
  見逃す設計だった——ボクセル単位の`np.array_equal`比較を検証の基本にする。

## numba `@njit`関数はモジュールグローバル値をコンパイル時に焼き込む——将来の値変更がキャッシュ経由でサイレントに乖離しうる（2026-07-29）

`chatcarlo/tally_njit.py`のnjitスカラーDDAは`chatcarlo.tally._EPS_PLANE`と
同じ許容値を使う必要があるが、当初案（プロトタイプ段階、
`docs/speedup_baseline/dda_njit_prototype_benchmark.py`）は
`from chatcarlo.tally import _EPS_PLANE`をnjit関数内で参照していた。
Codexの計画レビュー（read-only、実装前）が指摘: numbaの`@njit(cache=True)`は
コンパイル時にモジュールグローバルの**値**を関数本体へ焼き込む。将来
`tally.py`側で`_EPS_PLANE`の値だけを変更しても、ディスクキャッシュ
（`.nbi`）はソースコード＋シグネチャのハッシュで再利用判断するため、
グローバル値の変更だけでは再コンパイルがトリガーされず、古い値のまま
コンパイル済みコードが使われ続ける可能性がある——まさに本セッションが
上記の教訓で苦労した「境界セマンティクスの微小な乖離」と同じ症状クラスを、
テストなしに再発させうる経路だった。

**対応**: `_EPS_PLANE`をグローバル参照ではなく**njit関数の引数として毎回
渡す**設計に変更（`chatcarlo/tally_njit.py`の`_dda_njit`/
`_enumerate_intersections`）。呼び出し側の公開ラッパー
`accumulate_track_length_multi_njit`が`chatcarlo.tally._EPS_PLANE`を
実行時に読み取って渡すため、値の受け渡しがコンパイル時ではなく実行時に
なり、キャッシュ陳腐化の可能性を構造的に排除した。あわせて
`monkeypatch.setattr(tally, "_EPS_PLANE", ...)`で値を実際に変えて挙動が
追随することを確認するテスト（`tests/test_tally_njit.py`）を追加した
——固定値との一致チェックだけでは、引数化が機能している証明にはならない。

**教訓**:
- **`@njit`関数がモジュールグローバルを参照するコードは、それ自体が
  将来のキャッシュ陳腐化バグの種になる。** 定数・設定値は極力引数として
  渡す設計にし、グローバル参照は避ける。既にグローバル参照している
  既存コードを見つけたら、値を変更する前にキャッシュの再生成
  （`cache=False`での一度の実行、または`.nbi`ファイルの削除）が必要か
  確認する。
- この教訓は、実装前のCodexによる計画レビュー（read-only、コードを1行も
  書く前の段階）で発見された——批判的レビューの方針と同様、
  実装後ではなく計画段階での独立レビューが安価に効いた一例。

## 「性能問題」として立てた計画が、実は正しさの問題（2種類の材料コード体系の混同）だった（2026-07-29）

`kernel.py`の重み計算最適化（`residual_B`プロファイルで特定した最大成分の
削減）で、当初案は「`seg_mat_all`を`materials.py`の`material_groups`が持つ
整数コード高速経路へそのまま渡す」というものだった。表面的には性能改善にしか
見えない変更だったが、Codexのread-onlyレビューが実コードを確認して指摘:

- `kernel.py`の材料コードは`SceneMaterialTables.material_names`への
  **シーンローカルな0起点index**（docstringに明記済みだったが、計画作成時に
  見落としていた）。
- `materials.py`の整数コード高速経路が前提とするのは、`material_code()`が
  発行する**プロセス全体のグローバルインターンコード**（挿入順で採番、
  シーン間で共有）。
- この2つは無関係な体系であり、そのまま渡すとインターン表の状態次第で
  `IndexError`になるか、**別材料の名前へ誤変換されて静かに間違った線量を
  計算する**（silent data corruption）。dtypeを確認するspyテストではこの
  不一致を検出できない——dtypeは正しく整数でも、値の意味が違うため。

**対応**: 計画を「`material_groups`を経由せず、シーンローカルコードを
`np.unique`で直接グループ化する」設計へ全面書き直しした。結果的に
性能改善（重み計算median 1.446倍）と正しさの両方を達成した
（[docs/ai/plans/2026-07-29-material-groups-fast-path-kernel.md](ai/plans/2026-07-29-material-groups-fast-path-kernel.md)）。

**教訓**:
- **「既存の高速経路がある」という理由だけで飛びつく前に、渡そうとしている
  値の"体系"がその高速経路の前提と一致しているか確認する。** 同じ「int64の
  材料コード配列」という型情報だけでは、コード値の意味（シーンローカル添字
  なのかグローバルインターンコードなのか）までは分からない。dtype一致は
  安全性の証明にならない。
- **性能タスクだと思って計画を書いても、Codexのread-onlyレビューは正しさの
  観点でも実コードを読む。** 計画段階のレビューが「性能問題ではなく正しさの
  問題」というカテゴリ自体の誤りを検出した——批判的レビューの方針
  と同じく、実装前の独立レビューが安価に効いた一例。
- **1回のレビューで承認可にはならないことがある。** 今回は計画の全面書き直し
  後も2回の追加レビュー（worktree比較のプロセス分離、E2E計測のウォームアップ
  境界未定義、材料コード契約の拡充）で指摘が出た。「重要度の高い指摘があれば
  再レビューする」という運用どおり、指摘が収束するまで（計4回）往復した。

## `codex exec`が任意のMCPプラグイン（github等）の認証エラーで出力を欠落させることがある（2026-07-29）

このセッションの環境では、`~/.codex/config.toml`で`github@claude-plugins-official`
プラグインが有効になっており、`codex exec`実行のたびにGitHub Copilot MCPへの

`stdout`にもファイル出力にも記録されないまま実行が終わることがあった
（read-onlyレビューで2回連続発生。ツール呼び出しの結果は記録されるが、

**対応**: `codex exec -c 'plugins."github@claude-plugins-official".enabled=false'`

**教訓**:
- **`codex exec`の出力が「ツール呼び出しのログだけで結論が書かれていない」
  ときは、プロセスが正常終了していても実際には結論が生成されていない
  可能性を疑う。** 「ファイルが作られた＝タスク完了」と早合点しない。
- 今回はこのプロジェクト固有の設定ではなく`~/.codex/config.toml`（ユーザー
  レベル、全プロジェクト共通）が原因だったため、他プロジェクトの
  codex-kyodo作業でも同じ問題が起きうる。

## 「6シード・4σ」等の受入基準は形式的に満たしても検出力ゼロのことがある——ミューテーション検証で実測する（2026-08-01）

kernel.pyのCLI接続（Phase 1、`docs/ai/plans/2026-08-01-kernel-cli-wiring-phase1.md`）で、
Codexが実装したkernel/numpyクロスチェックテストは「独立6シード・結合4σ」という
`docs/plan_chatcarlo_speedup_post_egs5.md`のB-2節と同じ受入基準を形式的には満たして
いた（テストは実際にpass）。しかし`n_histories=2,000`という小さすぎる条件だったため、
コンプトン散乱の沈着エネルギーを意図的に1%過小にする変異を注入しても**テストは
検出できなかった**（検出できる最小バイアスは水8.9%・鉛5.9%と、独立に計測して判明）。

**原因**: 「6シード・4σ」という基準文だけを見ると厳格に見えるが、4σの絶対的な大きさは
`n_histories`に強く依存する（SEMは1/√n）。基準の文言をコピーしただけでは、実際に
その条件下で何%のバイアスまで見逃すかは分からない——**基準を満たすことと、
実際にバグを検出できることは別**。

**対応**: 意図的にバグを注入し、テストが実際に落ちるかを確認する（ミューテーション
テスト）運用を導入した。`_CROSSCHECK_HISTORIES`を50,000へ引き上げて検出限界を
0.7〜1.2%に改善し、「配線バグ類（prangeの集約破壊・fluorescence_enabledの握り潰し）
は確実に検出できるが、1%粒度の系統差はこの単体テストでは捕捉できずEGS5相互検証の
役割」という限界をテストのコメントに正直に書いた
（`tests/test_kernel_cli_dispatch.py`の`_CROSSCHECK_HISTORIES`コメント参照）。

**教訓**:
- **受入テストの「合格」を鵜呑みにせず、意図的にバグを注入してテストが落ちるか
  確認する運用を、独立検証の標準手順に加える。** 特にCodex等の実装エージェントが
  「受入条件をすべて満たしました」と報告してきたときこそ、この検証が効く——
  テストコード自体が受入条件を「形式的に」満たすよう書かれていて、実際の検出力が
  伴っていない可能性を排除できる。
- **統計的な受入基準（Nシード・Mσ）を書くときは、基準の文言だけでなく
  「この条件で検出できる最小バイアスは何%か」を実測してから確定する。**
  4σという厳格そうな数字に安心せず、nを変えて検出力曲線を1点でも取る。
- 同じ教訓が批判的レビューの方針（自分の"修正済み"も同じ厳しさで
  再検証する）の具体的な適用例になっている——ここでは「テストが通った」という
  自分（Claude）の判定自体を、ミューテーションという独立した手段で裏取りした。

## advisorが「実装しやすい方から手を付ける」という前提の誤りを着手前に検出した（2026-08-01）

kernel.pyのCLI接続をPhase 1（box限定・単色・parallel）で完了させたあと、次のPhase 2の

  価値がある。** 今回は「線源配列化」という工数のかかる作業に着手する前に

  advisorが指摘の根拠として使えたのは、直前のCodex実装報告（この会話の中の

  読み飛ばしていないか**、advisorへの相談は良いセカンドオピニオンになる。


## 原因の仮説は「同じ入力を与える対照実験」で確かめ、対策の選定とは別の問いにする（2026-10-08）

電子輸送の試作（`prototypes/mv_electron/`）は、EGS5との比較で線量の最大差が3.02%（許容3%）となり、
原因の仮説は「弾性散乱の断面積に使った遮蔽Rutherford近似」だった。最初の計画は、公開データ（EEDL）に
差し替えて差が縮むかで仮説を判定しようとしていた。Codexのレビューが「EEDLの2 MeVは256 keVと10 MeVの
角度表をつなぐ補間点で、精密な値ではない。縮まなくても仮説は否定できない」と指摘し、実験を2本に分けた。

- 問いA（原因）: EGS5と同じ断面積を試作に読ませる対照実験 → 差は0.54%に低減（低減率82%、95%区間67.5〜82.3%）。
- 問いB（対策）: EEDLに差し替える → 線量差103%。第1輸送断面積が1 MeVで約4.5倍、2 MeVで約9.5倍。

**教訓**（いずれも今回1回の経験。確度は中）:

- **「原因は何か」と「何に置き換えるか」を1つの実験で答えようとしない。** 置き換え先が悪いと、
  正しい仮説を誤って否定する。原因の確認には、比較相手と同じ入力を与える対照を先に置く。
  対照は研究専用でよく、本番に使う必要はない。
- **公開データの「エネルギー範囲」の記述は、その範囲全体での精度を保証しない。** EEDLは10 eV〜100 GeVを

## 精度の条件を、届くか見積もらずに書いた（2026-10-10／10-11／10-12／**11-05 の 4 回**。再発、`/furikaeri`で整理）

**How to apply:** 統計の条件を計画に書く前に、小さな試し計算（数万〜数十万履歴、数分）で同じ領域の誤差を測り、履歴数の平方根で換算して、1.5倍程度の余裕を持って届くことを確かめる。届かないなら、条件ではなく領域の幅か履歴数を変える。P3aのパイロットはこの形で行い、問題なく通った。計画の雛形（`docs/ai/PLAN_TEMPLATE.md`）にも書いた。

**3回目（2026-10-12、P3r）:** この項目と計画の雛形の注意書きがあったのに、確認の段階の条件（放射収率の相対SEM 1%以下）を、履歴数20万を見積もらずに決め、2 MeVが1.22%で「統計不足」になって止まった（80万履歴に増やして0.61%で通過）。雛形の注意書きを「本計算の条件」のこととして読み、事前の確認の中の条件に当てはめなかった。**How to apply（追加）:** 計画の中で「SEM」「相対誤差」「以下なら」と書いた箇所を、本計算か確認かを問わず全部拾い、それぞれに試し計算の値と余裕の倍率を横に書く。書けない条件は置かない。

**🔴 発火条件を広げる（4 回目の原因）:** この項目は索引の「**計画を書くとき**」にある。
4 回目（下記）は**事前登録**と**ユーザーへの選択肢の提示**に条件を書いたので発火しなかった。
**発火条件は「数値の条件や費用を書くとき」全部**（計画・事前登録・その追補・ユーザーに示す選択肢）。

**4回目（2026-11-05、G5-A4u、中心軸 PDD）:** 2 つの形で同時に踏んだ。

**(a) 条件が「合成」なのに片側で見積もった.** D7 の「相対 SEM ≤1%」は
**合成 SEM**（`hypot(EGS5_SEM, CPU_SEM)`、`a4u_h4_gate.analyse` の
`enough=(r>0)&(sem<=SEM_LIMIT*r)`）に掛かる。なのに EGS5 **片側**の ≤1% の本数（29/60）で
「EGS5 0 本＋CPU 23 分で約 29 bin 判定できる」とユーザーに費用を示した。
60 keV は EGS5 側だけで中央値 1.013% だったので、合成が 1% に届く余地はほとんど無く、
実際は 8/60 で統計不足に終わった。**片側が上限いっぱいなら、相手側を無限に良くしても
合成は上限を下回らない。各辺に要る精度は 1%/√2 = 0.707% で、片側の数字より約 1.4 倍きつい。**

**(b) bin 幅を目的から決めず、手元の配列の刻みをそのまま使った.** 中心軸 PDD を
**0.25 cm bin** で判定して統計不足になり、「履歴数が足りない」と誤認して
EGS5 を 2 本増やす計画変更まで提案した。ユーザーの指摘で一次資料を見たら、
プロジェクトの正典の PDD 照合（`revalidation_2026_10_07/comparison.csv`、
CLAUDE.md が参照として挙げるもの）は `pdd_z0-1`〜`pdd_z14-15` の
**1 cm × 15 本 × 0〜15 cm** だった。**1.0 cm に粗くした判定（K=15）はこの正典と同じ設計**で、
既存データで合格した。この誤りで EGS5 150,767,400 履歴（約 0.47 時間）を無駄に回した。

**How to apply（追加）:**
1. 数値の条件を書いたら、**その条件が片側か合成かを判定コードの式で確かめる**。
   合成なら各辺の必要精度（1%/√2 等）に直してから費用を見積もる。
2. **bin 幅・本数・範囲は、その量を既に照合している記録から取る。**
   手元の配列の刻みをそのまま使わない（配列の分解能と判定の分解能は別物で、判定は粗い方でよい）。
3. **ただし 1 つの幅を全条件に当てない。** 20 keV は ROI が約 4 cm しかなく
   （4.25 cm で山の 5% を切る）、1.0 cm では bin が 4〜5 本で
   `MIN_EVALUABLE_COUNT`=8 の床を下回り判定できない。0.25 cm なら K=17 で通る。
   **ROI の広さが違う条件には違う幅が要る。**
4. **仕組みで止める**（2026-11-05 に実装）: `a4u_pdd_gate.check_reference_precision` が、
   参照側だけの相対 SEM が `SEM_LIMIT/√2` を超える bin が K の 20% を超えたら
   判定の前に停止する。実測でこの検査は 20 keV の 0.25 cm（6/17）でも止まるので、
   **計算前に両エネルギーの設計の誤りを捕まえられた**。

**後出しで救うときの作法（この 4 回目で必要になった）:** 救済を採るなら
(1) **値を出す前に**追補として事前登録し冒頭に「後出しである」と書く、
(2) **その時点で何を知っていたか**を表で開示する、
(3) **他の幅を試して通る方を選ばない**と停止条件に書き、実装側でも拒否させる
（今回は `--group 2` を `ValueError`）、
(4) 報告は**事前登録どおりの判定と並べて**書き、片方だけ引用させない。
**ただし今回の 1.0 cm は正典と同じ標準だったので、弱点は「順序」だけで
「恣意的な幅を選んだ」部分は無かった** —— この作法が要るのは本当に恣意的な救済のときである。

## 差を見つけたら、原因を考える前に、同じ設定でseedだけ変えて1回流す（2026-10-11〜12、n=3）

1回の計算どうしの比較で見えた差を、3回続けて「実在する」前提で調べ始め、あとでゆらぎと分かった。(1) P2の6 MeVで、EGS5の2つの設定の差が+1.05 ± 0.29%（12の領域から事後に選んだ値）→ 5倍の統計で+0.23 ± 0.13%。(2) P3aで、試作が表面〜15 cmで+0.24 ± 0.07% → EGS5を新しいseedで流すと+0.11 ± 0.07%。(3) 同じく「全体で+0.1%」→ 試作を2本足すと+0.03と+0.05。

**Why:** 2〜3σの差は、領域をいくつも見ていれば普通に出る。片方のコードを1回しか流していないと、その1回のゆらぎを系統差と区別できない。

**How to apply:** 2〜3σの差が見えたら、まず同じ設定をseedだけ変えて流す（EGS5は約13分、試作は約40〜50分）。考察や追加の実装は、再計算でも差が残ったものに対して行う。残った例: ビルドアップの+0.3%（3本とも正、単色でも同じ向き）。一方、理論の見積もりを先に置いてから計算した飛行中の陽電子消滅（確率6.27%と6.26%、線量の変化0.2%）は、予想どおりの結果になった。

## 「結果が完全一致」の確認だけでは、速度の劣化を見逃す（2026-10-12、P3r、n=1）

制動放射の離散事象を足すために輸送ループを写して手を入れたところ、離散事象を切った状態でP3sと1ビットも違わない結果を出すのに、時間は204 → 261 µs/履歴（+28%）になっていた。本計算が終わってから気づいた。計画では「離散事象は1 cmに0.1〜0.2回で少ないから、計算時間への影響は小さい」と見込んでいた。

**Why:** 見込みは事象の頻度だけから出したもので、ステップごと・係数の更新ごとに増える処理（事象の順序を決める配列の確保、補間の重複）を数えていなかった。完全一致の確認は結果しか見ないので、通っても速度については何も言えない。

**How to apply:** 輸送ループを写して機能を足す計画では、完全一致の確認と同じ条件（新しい機能を切った状態）で時間も測り、「元の何%以内」という許容幅を受入条件に入れる。超えたら本計算の前に直す。

**追記（2026-10-12、P3t、n=1）:** 原因は次の段階で15分ほどで確定した。上のWhyに挙げた2つがそのまま当たりで、使っていない事象順序の関数の呼び出し（23〜28 µs）と、制動放射の表の二重参照（36〜57 µs）だった。外すと離散事象を切った状態はP3sと同じ速さに戻り、結果はバイト単位で変わらなかった（[結果](validation/mv/p3t/RESULTS.md)）。P3rでは「切り分けていない」と書いて持ち越したが、持ち越す理由は無かった。

- **結果が変わらない無駄は、疑わしい処理を1つずつ外して測ればすぐ切り分けられる。** 完全一致が合否になるので、外してよいかの判断に迷わない。原因の仮説が立っているなら、その段階の中で測る（5万履歴で1条件10秒ほど）。「未測定」と書いて次へ送らない。
- **「完全一致」はバイト列で確かめる。** `np.array_equal` や `assert_array_equal` は `+0.0` と `-0.0` を同じとみなすので、「1ビットも変わらない」の根拠としては弱い（Codexのレビューで指摘された）。型・形・`tobytes()` を比べる。あわせて、測定スクリプトは一致を確かめてから時間を保存・表示する順序にする（不一致なのに速度の数字が残るのを防ぐ）。

## 前の段階の手順を引き継ぐ前に、手元のデータで雑音の大きさを当てる（2026-10-13、P3b-3、n=1）

平板の比較（P2b〜P3r）で使ってきた「試し計算の曲線で、ピークの97%以上の連続した範囲を求め、その先を深部にする」手順を、照射野つきの比較（P3b-3）にそのまま使おうとした。計画を書く前に、手元にあった試作の200万履歴の結果で試したところ、範囲の深い側の端がバッチのブートストラップで2.25〜3.75 cmに散らばった。ユーザーに相談し、深部は5 cmから固定にした（[計画](ai/plans/2026-10-13-mv-p3b3-pilot-production-analysis.md)）。

**Why:** 集計の領域が板全体から2×2 cmの直方体になり、同じ履歴数で入るエネルギーが約25分の1になった。1区画の相対誤差（約2.8%）が、手順の中の閾値の幅（3%）と同じ大きさになり、領域の境界が種で動く。手順そのものは正しくても、手順の中の閾値と雑音の比が変わると使えなくなる。そのまま進めていれば、試し計算の種しだいで判定の領域が変わっていた。

**How to apply:** 前の段階の「領域や基準をデータから決める手順」を引き継ぐときは、計画に書く前に、(1) その手順の中の閾値（何%以上、最大の位置、など）を拾い、(2) 新しい条件での1区画の誤差を、手元の結果か数分の試し計算で測り、(3) 誤差が閾値の幅の3分の1より大きければ、ブートストラップで境界の揺れを見る。揺れるなら、データによらない固定の規則に変えるか、試し計算を大きくするかを、計算の前にユーザーに相談する。

## 長い計算の前に、起動スクリプトの「計算のあとの処理」まで既存の結果で通す（2026-10-13、P3b-2とP3b-3、対照1組）

## 計算機をまたぐバイト照合は、整数か明示の式に限る（G4・診断 Colab 経路、2026-10-22〜24、n=2）

- **結論**: 同じコード・同じ種でも、Mac（arm64、NumPy 2.4.6）と VM（x86_64、NumPy 2.1.3）で方向の配列 300,000 要素中 96,701 要素が違った（最大 13,077 ulp、`np.linalg.norm`）。平行ビームの起点でも `Generator.uniform` の最後の桁が違った。
- **Why**: 浮動小数の丸めは CPU と版で変わり、ハッシュは 1 ulp でも別物になる。手元で完結する偽物のテストやレビューでは見つからない。
- **How to apply**: 別の計算機で作り直すものは、整数と整数だけから決まる値に限る。浮動小数は同じ計算機で別経路の値と比べるか許容幅で比べる。VM と照合する乱数の抽出は NumPy の変換関数に頼らず `下限 + (上限 − 下限) × 乱数` の式で書く。新しい線源の型は小さな実行で origins・directions を先に確かめる。計画に「どの値を、どの計算機で作り直すか」の表を書く。

## 2026-10-23: GPU G2b — 偽物の CUDA は実物が渡す形をすべて入れる。許容の幅は手元の観測値と照らして決める。GPU の浮動小数の足し込みはビット再現しない

- **How to apply**: CUDA の経路を偽物で試すときは、実物の呼び出しが作る引数（`None` の代わりの `np.uint64(0)`、長さ 0 の配列など）をすべて偽物に入れる。VM で失敗したときにログを回収する経路を、最初の実行の前に作る。再現性・一致の幅を事前登録するときは、同じ量の既存の観測値（前の実行の差分など）を一度計算し、その数百倍の幅にする。GPU で `atomicAdd` を使う量は、再実行・再開でもビット一致を条件にしない（整数の記録はバイト一致、浮動小数は相対の幅、R・SEM はさらに広い幅）。確度: (1) は n=1、(2)(3) は実測。

## 2026-10-23: 点ごとの比較で規格化の基準を 1 ビンにすると、そのビンのゆらぎが全点に乗り「2σ 超」が増える

**結論**: 点ごとの（A − B）÷ B を、最大のビンや中心のビンなど 1 ビンで規格化して比べると、基準ビンの統計的なずれが全点に共通のずれとして乗る。その結果、2σ を超える点が偶然の見込みより大きく増える。基準の領域には、比べる点と同じかそれ以上の統計を持たせる。

**Why**: 10 MV 水ファントム PDD（0.25 cm 刻み、120 点）で、EGS5 と GPU を同じ定義で比べた。
- 両コード 4.6×10⁷ 個では 2σ 超が 18 点（偶然の見込み約 5.5）。基準ビンの比が 1.7σ ずれていた。
- 両コード 1.0×10⁸ 個にしても 21 点で、統計を増やしても減らなかった。基準ビンも点と同じ速さでしか良くならないため。
- 0.5 cm 刻み（2 ビンの平均）にすると 0/60 点になった。

4 MV の深さ 10 cm の OCR が全点 +3.4% 側にそろう件も、中心 1 点で規格化した同じ構造とみられる（中心 1 cm の平均で規格化すると +1.7% に半減。原因の切り分けは未了）。
詳細: `docs/validation/mv/stats10mv/RESULTS.md`、`docs/jsmp133/abstract_ja_draft.md` の注意書き。

**How to apply**: 点ごとの比較の結果で 2σ 超が多いときは、物理の差と決める前に、基準ビンの z と「全点の符号つき平均の差」を見る。符号つき平均が基準ビンのずれと同じ大きさなら規格化の問題である。基準を広げる（複数ビンの平均、またはビンを粗くする）か、基準なし（固定の `Dref` 比）の比較を並べて確かめる。確度: 中（10 MV で確認、n=1 条件。4 MV は見立て）。

## 2026-10-24: zsh では変数に入れたコマンドが単語に分かれない — 一括実行が「OK」だけ出して何もしなかった（再発）

- **結論**: `P=".venv/bin/python -u -m pkg"; $P.mod ...` のように変数に入れたコマンドは、zsh では 1 語のままで「no such file or directory」になる。T4 の手順の一括実行（書き出し → 再開の関門 2 台 → 本計算 → verify）が全工程で失敗し、`{ set -e; ...; echo OK; }` の `set -e` も効かず「OK」だけが並んで終了コード 0 になった。同じセッションの前半の `$CODEX_OPTS` で同じ失敗をしたのに記録していなかった（n=2）。
- **Why**: zsh は bash と違い、引用なしの変数展開を単語に分けない（`SH_WORD_SPLIT` が既定で無効）。さらに `{ }` の中の `set -e` は、`;` でつないだ文の途中の失敗で止まらなかった。
- **How to apply**: コマンドは変数に入れずに 1 行ずつ書く（引数の束は配列 `opts=(-m x -c y); cmd "${opts[@]}"` か、直接書く）。一括実行は `( set -e` のサブシェルに改行区切りで書く。「OK」の印ではなく、各工程が作った実物（ログに出た出力先、ファイル、`complete.json`）で進行を確かめ、起動直後に 1 回それを見る。
- **再発（2026-11-03、A4u S2、n=3 の別の形）**: 引用の事故が「変数の分割」ではなく「二重引用符の中のバッククォート」で起きた。Codex へのプロンプトに `` `t2_kernel.h` `` のようなバッククォートを入れて `codex exec ... "..."` で渡したため、zsh がコマンド置換として実行し、`permission denied: chatcarlo/gpu/generate_photon_tables.py`・`command not found: material` が並んだ壊れたプロンプトで起動した（すぐ止めて起動し直した）。**追加の How to apply**: Codex へのプロンプトは**必ずファイルに書いて `- < file` で渡す**（`codex exec resume ... - < prompt.txt`）。シェルの引用に頼らないので、バッククォート・`$`・改行をそのまま書ける。

## 2026-10-24／2026-11-07／2026-11-08: 使い捨ての出力は積み上がる。**ユーザーに容量を頼む前に自分の分を数え、空いた後の数字も測っていない消費量も予告しない**（n=4）

- **事実（2 回目、2026-11-07、G5-A4u H6 の T4）**: 容量が足りず **6 回**ユーザーにゴミ箱を空けてもらった。

  しかもその場では「空きはこの作業と無関係に 1 GiB ほどゆらぐ（APFS のスナップショットなど）」と

- **Why**: 自分が作ったものは「作業中だから要る」と見なしてしまい、棚卸しの対象に入らない。
  指定のスクラッチパッドではなく一段上の `/private/tmp/claude-501/` に 40 本以上書いたので、
  まとまりとして数えにくくもなっていた。容量の原因を外部に帰する推測は、自分の分を数えるまで立てられない。
- **How to apply（2 回目で足した分）**:
  **ユーザーに容量の確保を頼む前に、必ず自分の使い捨てを数えて退避する**——
  `du -sh "$SCRATCH"/* /tmp/claude-*/* 2>/dev/null | sort -rh | head`。

  どちらも判断には影響しなかったが、**ユーザーはこの数字を見て作業を止めるか進めるかを決める**。
- **Why**: 2 回目の How to apply は「自分の分を数える」までで止まっており、
  **数えた結果から先の空きを引き算してよいか**には触れていなかった。
  APFS では移動だけでは解放されず、スナップショットや他プロセスの増減も入るので、引き算は当たらない。
- **How to apply（3 回目で足した分）**: 容量を報告するときは、**`du` で測った退避の大きさだけを言う**。
  「空ければ約 N GiB になる」は書かない——空けてもらった**後に `df` で測ってから**数字を言う。

## 既存の核に物理を足すときは、構造の移植と物理の変更を 2 段に分ける（2026-11-03、A4u、n=1）

## 「どの量が設計上変わるか」の確認は、先に検出力を見積もる（2026-11-03、A4u H2、n=1）

## ライブラリの「線の一覧」は、名前の正規表現で拾うと静かに欠ける（2026-11-04、A4u H3b、n=1）

- **結論**: xraylib の輝線を `dir(x)` の名前の正規表現で列挙していたら、**遷移先が複数準位をまとめた名前**
  （`KO`・`KP`・`L3O45`・`L1O45`・`L1P23`・`L2P23`・`L1N67`・`L3P23`・`L3P45`）が全部落ちていた。
  落ちた重みは生成器が残りの線に再正規化するので、**鉛の K で 0.82%・L3 で 1.79% が強い線に乗り**、
  脱出スペクトルの 86–99 keV が −15%、13–14 keV が 1/12 になった。
  `KO1`・`L3O4` のような個別の線は Z=82 には**存在しない**ので、まとめた名前が唯一の表現だった。
  1005 件のテストを 1 つも落とさず本番の物理に入っていた（鉛の線の組を数値で固定した試験が無かった）。
- **Why**: 名前の綴りは API の都合で、物理の網羅性を保証しない。正規表現は「拾えたもの」しか教えてくれず、
  欠けは重みの再正規化で見えなくなる。
- **How to apply**: ライブラリから分岐比の一覧を組むときは、**物理の予算を検査に入れる**。
  xraylib なら 1 つの空孔の `RadRate` は全線で 1 に足されるので、`abs(sum-1)>1e-3` で止める
  （`generate_photon_tables.py:104`。これで欠けは必ず表に出る。実測の残差は 2e-5）。
  エネルギーが引けない線（割合はあるのに `LineEnergy` が無い）は**黙って再正規化せず**、
  落ちた重みを記録して予算に数える。

## 吸収端の節は「端のエネルギー」ではなく「跳びの位置」を挟む（2026-11-04、A4u H3b、n=1）

- **結論**: 断面積の表の節を `EdgeEnergy×(1±1e-7)` で挟んでいたが、**xraylib の `CS_Photo` の跳びは
  `EdgeEnergy` と一致しない**（鉛の L2 は端 15.200000 に対し跳びが 15.199989 keV ＝ 11 meV 下、
  K は 3.8 meV 下、ウランの L3 は 1.7 eV 以上下）。そのため「端の下」の節が跳びの上に来て、
  端の下側の節が消え、手前の区間が跳びをまたいで内挿された。
  鉛の L2O4（15.178 keV）の μ が **1.25 倍**、Kβ2・KO（87.4・87.9 keV）が **4.7 倍**になり、脱出が落ちた。
- **Why**: 端の位置はデータ提供側の内部格子の都合で、公表値と meV のずれがある。
  相対の決め打ちの窓は、そのずれより細かいと必ず片側に倒れる。
- **How to apply**: 跳びを**二分探索で見つけて**挟む（`bracket_edge`）。窓が丸ごと跳びの上に来る場合があるので
  下端を広げる経路も作る。そして**線のエネルギーでの μ を元の関数と突き合わせる検査**を入れる
  （`generate_photon_tables.py` の 3e-3。1025 点の対数格子の内挿誤差より上、欠陥の 25% より下）。
  挟んだ対の中に入る線は提供側も解像できない境目なので、止めずに記録する。

## 収束の判定を「差と限界の比較」で書くと、打ち消しで止まらなくなる（2026-11-04、A4u、n=1）

- **結論**: 窓を広げるループを `while 条件 and edge-low<limit: low=edge-min((edge-low)*4,limit)` と書いた。
  `edge-(edge-limit)` が浮動小数の打ち消しで `limit` をわずかに下回ると `low` が更新されず、**無限ループ**になる。
  Z=84・86・87・88（Po・Rn・Fr・Ra）で発生し、2 プロセスが CPU を 6 時間以上空回りした。
  ChatCarlo が使う元素では起きないので、**全数走査をしなければ寝たままだった**。
- **Why**: 大きな数から小さな差を引いて戻すと、差は元の値に戻らない。終了条件をその差に賭けると不動点ができる。
- **How to apply**: 広げる・縮めるループは**回数で打ち切る**（`for _ in range(12)`）。
  そして、使う範囲だけでなく**定義域の全数**（元素なら Z=5〜92）を 1 回走らせる。0.5 秒で済んだ。

## 検証の関門が落ちたときは、実装を合わせる前に「入力の生成」を疑う（2026-11-04、A4u H3b、n=1）

- **結論**: 保存済み EGS5 との L 帯の比較（H3b）が落ちたとき、原因は輸送でも物理モデルでもなく、
  **断面積・輝線の表を作る側**の欠陥 2 つだった（上の 2 件）。切り分けは、
  (1) 無衝突透過が 0.02% で合う → 幾何と μ の大枠は正しい、
  (2) 空孔を直接注入して出る光子を数える → 発光は表に忠実、
  (3) **表の値を元のライブラリと線のエネンルギーごとに突き合わせる** → ここで 1.25 倍・4.7 倍が出た、の順。
  最後に EGS5 を 1 本だけ足して起源（緩和・制動放射・一次）を LATCH で分け、制動放射を量で否定した（帯の 1.0%）。
- **Why**: 輸送のコードはテストが厚いが、表の生成は「作った表を正解とみなす」ので自己検査が効かない。
  関門は輸送の誤りより先に表の誤りを捕まえることが多い。
- **How to apply**: 相互検証が落ちたら、実装をいじる前に**表の値を一次のライブラリと点ごとに突き合わせる**。
  比較相手の側の値も読む（EGS5 なら `DFLX*`・`ELX*`・`F12/F13/F23` と、**その走行そのものの** PEGS5 の一覧。
  別条件の走行の一覧で代用すると PWLF の格子が違う）。

## 短い試し計算の `wall/N` は起動費が支配する —— 固定費と周辺費用を分けてから N を決める（2026-11-04、A4u H4/H5、n=1）

- **結論**: EGS5 の試し計算（100 万履歴）の `wall_seconds/N` は 88.9 µs/履歴（20 keV）・94.5 µs/履歴（60 keV）だった。
  本番（1,844 万・2,322 万履歴）で測ると 10.5・14.3 µs/履歴で、2 点から分離すると
  **周辺の費用 6.01・10.74 µs/履歴＋起動などの固定費 約 83 秒**。試し計算の値は **約 93% が固定費**だった。
  これを 1 履歴あたりの費用として本番の N の見積もりに使い、**9〜15 倍の過大見積もり**をした
  （「20 keV の OCR を判定に入れると 18 時間」→実際 0.81 時間、「60 keV を 30 cm まで判定すると 3.37 時間」→0.38 時間）。
  その数字を根拠にユーザーに判定範囲を狭める判断を仰いでいたので、**判断の前提を誤らせた**。
- **Why**: 起動費（PEGS5 のデータ生成・ビルド・表の読み込み）は N に依らないので、N が小さいほど
  `wall/N` に効く。関門の出力には `scope: 起動の差し引きなし` と書いてあったのに、
  書いた側（道具）は正しく、読んだ側（私）が 1 履歴あたりの費用として使った。
- **How to apply**: 履歴数を決めるための時間は、**必ず 2 つ以上の N から回帰して固定費と周辺費用を分ける**。
  1 点しか無いときは「固定費を含む上限」とだけ書き、N の見積もりに使わない。
  報告・記録でも `seconds_per_history` を単独で出さず、固定費と並べて書く
  （計画 F13 の MV の 127 µs/履歴も同じ割り算なら起動を含む疑いがあり、比較に使う前に確かめ直す）。

## 置き換える照合は、緩めるのではなく名前を付けて切り分ける（2026-11-04、G5-A4u）

## 空き容量の番人は、全テストの結果を黙って無意味にする（2026-11-04、G5-A4u）

**How to apply**: テストが落ちたら、回帰と呼ぶ前に

## 同じ量だと思った 2 つの配列は、同じ履歴を 2 通りに採点して確かめる（2026-11-05、G5-A4u）

**How to apply**: どちらの採点器か迷ったら、**同じ履歴を 1 回走らせて両方の配列を取り**、
bin をまとめて比べる。和の丸め（1e-15）で一致する組み合わせが答えである。

## 利用者が読む量を判定したか確かめる（2026-11-05、G5-A4u）

## 封印はソースのバイトを見るので、コメントの編集でも破れる（2026-11-05、G5-A4u）

## 計算を回す時間を論じる前に、封印済み参照が「何の正解」なのかを確かめる

<!-- impact: 実質 / seen: 2026-11-06 / scene: 保存済みの関門を新しい物理で取り直すか判断するとき / enforced: なし -->

**発火条件**: 既存の関門・判定を、コードや物理を変えた後に「取り直すか」を決めるとき。

G5 A4u で `seed_ratio`（116 分）と MV（33 分）を回すか否かを、**履歴数・bin・時間の見積もりだけで
1 日議論した**。実際に効いたのは参照の出どころで、`a2b_run/reference.json` の封印済み参照は EGS5 ではなく
**旧 P9c 試作そのもの**だった。A2b の関門は「新エンジンが旧試作を 0.1〜0.7% で再現するか」という
**同一物理の移植試験**で、物理を意図して変えた後に当てると不合格が正しい挙動になる——116 分かけても
正しさの情報は 1 ビットも出ない。逆に MV は参照が EGS5 だが、変更分の上限が解析的に 0.26%（許容 1%）で、
効きが最大の低エネルギー端は別の関門で EGS5 判定済みだったので、こちらも回す必要がなかった。

**Why**: 「取り直す価値」は〈参照が何の正解か〉×〈変更がその量にどれだけ効くか〉で決まる。時間・履歴数・
bin はそのあとの話で、先に論じると「削れない」という結論が出て**回すこと自体が前提になる**。
同じ日に、速さ測定の µs/履歴を本番 N へ外挿して 4.5 時間と誤報告した件（教訓「短い試し計算の」）と同型で、
どちらも**割り算の値や時間の数字を、その由来を確かめずに判断の土台にした**。

**How to apply**: 保存済みの関門を取り直すか決めるときは、見積もりより先に 2 つを grep で確かめる。
(1) 参照の `identity`/`sources`/`physics_set` を読み、**EGS5 か旧実装か**を書く。旧実装なら同一物理の
移植試験なので、物理を変えた後は参照の取り直しが先。(2) 変えた過程が、その量のエネルギー領域で
全断面積の何 % を占めるかを xraylib で数秒で出す。許容より桁で小さければ GPU は回さず、前段の合格を
引き継いで根拠を 1 段落残す。
