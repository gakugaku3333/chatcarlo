# P3u — 試作のバッチを複数のプロセスで実行する（2026-10-12）

計画: [docs/ai/plans/2026-10-12-mv-p3u-parallel-batches.md](../../../ai/plans/2026-10-12-mv-p3u-parallel-batches.md)（受入条件と閾値は測定の前に固定。Codexレビュー1巡、致命0）。実装はCodex、検証と時間測定はClaude。生データは `timing.json`。

## 結論

同じ設定（核、条件、粒子数、種、バッチ数、ソース・入力・実行環境の指紋）のもとで、**プロセス数が1でも2でも、途中で止めて再開しても、全バッチと集計結果の配列がバイト単位で同じ**になる。2プロセスで、所要時間は1プロセスの1/1.90になった。物理と乱数の使い方は変えていない（核は `photon_transport_p3t.py` のまま）。

## 時間測定

Mohan 10 MV、30 cmの水、`elsepa`、制動放射の光子を輸送、200万粒子（100バッチ × 2万粒子）、seed 20291630。1プロセス、2プロセスの順に1回ずつ（どちらも新規の実行）。

| | 1プロセス | 2プロセス |
|---|---|---|
| 所要時間（起動・保存・集計を含む） | 491.9 s | 258.3 s |
| バッチの計算時間の合計 ÷ 粒子数 | 242.6 µs | 256.7 µs |
| バッチの計算時間の中央値 ÷ 2万粒子 | 235.6 µs | 242.0 µs |
| 各ワーカーの最初のバッチ | 18.5 s | 19.6 s、19.7 s |
| 子プロセスの最大メモリ（最大値） | 786 MB | 749 MB |

- 各ワーカーの最初のバッチには、コンパイルと表の生成（約14 s）が入る。2行目はそれを含み、3行目は含まない。
- 2プロセスにすると、1コアあたりは約3%遅くなる（235.6 → 242.0 µs）。原因は切り分けていない。
- 1プロセスの中央値 235.6 µs は、P3tの測定（228.2 µs、5万粒子を1回で実行）より約3%大きい。バッチごとに入力の指紋（表のファイルのハッシュなど）を計算する時間が含まれ、これは起動後のプロセスで1回0.11 s（測定の後に別に実測）、2万粒子のバッチでは5.5 µs/粒子にあたる。差7.4 µsの大半はこれで説明できる。バッチあたりの固定の費用なので、1バッチの粒子数を小さくすると割合が増える。
- 両方の実行で、制動放射の放出は151,920回（0.0760回/粒子）、全バッチの集計の和も一致している（バイト単位の一致の一部）。

## Claudeによる独立の確認

- Codexが作ったのは新規の4ファイルだけで、既存のファイルは書き換えられていない（`git status`）。試験はClaudeが再実行した。
- 本番と同じ条件（Mohan、`elsepa`、光子を輸送）の小さい実行（4バッチ × 200粒子、2プロセス）で、各バッチが `photon_transport_p3r.run_coupled` を同じ種で直接呼んで同じ縮約をかけたものと、15項目すべてでバイト単位に一致した（作業用のスクリプト、リポジトリの外）。試験のU3は同じことを10 MeV単色・`mf` で確かめている。

## 使い方

```python
from prototypes.mv_electron.batch_runner_p3u import run_batches
path = run_batches(work, 'p3t_slab', dict(E=10., backend='elsepa', brems_mode=2, spectrum='mohan'),
                   N=2_000_000, seed=20291630, workers=2, nbatch=100)
```

- `work` は作業フォルダ（リポジトリの外に置く）。`batch_000.npz` … と `result.npz`（各項目がバッチ番号の順に積まれた配列）ができる。Gyへの換算やブロックの解析は呼ぶ側で行う。
- 止まっても、同じ引数でもう一度呼べば続きから再開する（プロセス数は変えてよい）。計算結果の異常（非有限、収支の違反）が出た実行はやり直せない。
- 新しい核（P3bの照射野など）は `batch_kernels_p3u.py` の `KERNELS` に足す。

## 言えないこと・注意

- **プロセス数は2までしか測っていない。** 上限は運用ルール（2個）のままで、3個以上は `ValueError` になる。高性能コアは4個なので4までは伸びる見込みだが、未測定。
- **約束は「同じ設定で、プロセス数と中断の位置だけを変えたとき」に限る。** バッチ数や条件を変えた場合、別のOS・CPU、ライブラリの版が違う場合は対象外（版が違う再開は拒否される）。
- **親プロセスを強制終了した場合**、ワーカーが計算を続けることがある。ワーカーはファイルを書かないので結果は壊れないが、再開の前に残っていないことを人が確かめる。
- **時間の測定は各条件1回。** 比1.90のばらつきは見積もっていない。
- EGS5側の並列実行は扱っていない（P3bの計画で扱う）。
- 途中で止まった実行の一時ファイル（`*.pending.npz`）は自動では消えない。
