## 実装

- 新規 `p8g2_kernel.h` に P/C/E/H/D の状態と遷移を分離。P の光子飛行・緩和は一まとまりに保ち、C は 1 ステップ。
- CPU は逐次、snapshot による 32/64 スロットの実際の再利用、共有出力への直接加算を実装。
- GPU はレーンの局所状態、仕事前に確定する全段階の ballot、next=0 からの初回取得と補充を実装。GPU スタック容量は 18。
- H は結果と記録の確定のみ。D の書き出し・ゼロ化・補充は駆動側が担当。スタック全体は初回も補充時もゼロ化しない。
- 検査ビルドの GPU atomicAdd の数え上げ先は、呼び出し元が cp.zeros で確保するグローバルメモリ。
- 小さい上限・容量でも凍結した P8g-1 と比べる CPU/GPU 参照ラッパーを新規ファイル側に設置。

状態・ポインタの寿命、ゼロ化範囲、元の break/continue 全箇所の行番号と対応は
[state_variables.md](state_variables.md)。必須分岐の固定入力と到達回数は [paths_gate0.json](paths_gate0.json)。

## 関門 0 の内容

SEED2、20,000 履歴（start=0）と 2,000 履歴（start=7,000）について、
逐次・32 スロット・64 スロットのすべてで P8g-1 CPU と履歴ごとの全出力がバイト一致。
各履歴の出力回数がちょうど 1 であり、生の 100 群を `check_group_records` で再構築して照合。

[histories_20000_0.json](histories_20000_0.json)、[histories_2000_7000.json](histories_2000_7000.json) に
比較範囲・出力数・ビルド指定と指紋を記録。
maxsteps=1 と容量 3 の各 2,000 履歴でも、同じ上限・容量の凍結参照とバイト一致。
共有出力への直接加算経路も、seconds を除いて P8g-1 とバイト一致。
通常ビルドと検査ビルドの 2,000 履歴もバイト一致。

固定例は、複数層の光子飛行、低エネルギー光子の局所吸収、緩和の複数光子と容量失敗、
硬衝突・制動放射の親粒子の退避と再取り出し、陽電子の停止時消滅・飛行中消滅・脱出、
E の容量失敗、異なる材料の境界後の再計算、境界散乱で元の領域に残る経路を網羅する。
9 種類の指定遷移はすべて到達。回数は JSON を正とする。

## 故障ビルド

| 故障 | 指定値 | 到達入力 | 拒否 |

| g3b | 6 | 同上 | 出力回数 0 ≠ 1 |
| g4 | 4 | 同上 | 群 0 の浮動小数点の和・最大値の検査 |
| g5 | 5 | 同上 | 群 0 の浮動小数点の和・最大値の検査 |

## 実行した検証

検証コマンドと実行結果は [verification.json](verification.json)。
`p8g local` と `p8f local` は旧段階の記録を出力するので、同じソースを一時ディレクトリにコピーして実行。
入力は既存の読み取り専用データを参照し、回帰検査の出力は一時コピー内に保存した。
元の P8g-1/P8f/P5 等の GPU ファイルと p8g1/p8f_prof 記録、計 156 ファイルの SHA256 は不変。

CUDA ソースは全故障指定を含め clang++ のホスト用スタブで構文検査した。
これは NVRTC コンパイル・GPU 実行の代用ではない。Colab/CLI は構文検査のみ。
全プロトタイプの pytest は計画どおり Claude の最終段階に残す。
git add / commit は行っていない。既存の計画、STATUS、規約や旧段階の記録は編集していない。

関門 2 は 40×128 / 40×256 / 80×128 すべてで同一 VM の P8g-1 40×256 との履歴比較、
生の群別集計、出力回数、総スロット数の直前・一致・直後と start≠0・連続呼び出しを検査する。
必須経路に未到達、バイト不一致、出力回数の異常、検出できない故障があれば計時へ進まない。
計時の history=False も同じ遷移・確定・群への加算経路を検査する。

計時は同一 VM で P8f 40×128、P8g-1 40×256、P8g-2 の 3 構成を交互に 3 回、
20,000 / 200,000 履歴。初期化・ウォームアップは分けて記録する。
倍率は「P8g-1 から B 全体への変更」。資源の減少や局所メモリ増加は対処せず記録する。
`ncu --set full` の 40×256 の生の ncu-rep/CSV はダウンロード後に解析し、P8f と P5k F と並べる。
有効スレッド・占有率に加え、ローカルメモリの読み書きと関連する待ちを確認する。
採否・A2 に進むかの判断は使用者が行う。

## Claude による関門 1・2 と測定（2026-10-24）

**結論: 関門 0〜2 にすべて合格。P8g-2 は検査した履歴で P8g-1（したがって P8f）と履歴ごとにバイト一致し、採用の方針に従って P8f の判定 A・B の合格を引き継ぐ（全履歴の同一性の証明ではない。P8f の合格範囲を広げない）。T4、20 万履歴で P8g-1 の 4.7 倍、P8f の本番の起動の 6.5 倍。**

- 関門 1（M3、約 3 分、`gate1.json`）: CPU の P8g-2 と保存済み P8f 参照（`p8f_ref_gate2` の履歴ごと、`p8f_ref_batch_000/050/099` の集計、`seconds` を除く）がバイト一致。CPU の集計の経路は状態機械の遷移から共有の出力へ直接足す形（`p8g2_cpu.cpp` の `p8g_run`）で確認。故障の再現（pytest `-k fault`）合格。
- 関門 2（T4、`t4/`）: 40×128・40×256・80×128 の 3 構成すべてで、同じ VM の GPU の P8g-1 との履歴ごとのバイト一致・群ごとの集計（`check_group_records`）・出力回数 1・補充の境目に合格（`gate2_*.json`）。まれな経路（`gate2_paths.json`）合格。故障（`gate2_faults.json`）: g2 は履歴 7,254 で不一致、g3a は出力回数 2、g3b・g4・g5 もそれぞれ拒否。
- ncu（報告のみ）は起動の誤りで取れていない: プロファイル用の子プロセスが `prototypes` を import できなかった（作業ディレクトリ・`PYTHONPATH` の未指定）。関門と計時は ncu の前に終わっており影響なし。

### 速さ（T4、同じ VM で交互に 3 回、核の時間の中央値、µs/履歴）

| 構成 | 20,000 履歴 | 200,000 履歴 | 200,000 での P8g-1 比 | P8f 本番の起動比 |
|---|---|---|---|---|
| P8f 40×128（本番の起動） | 332.3 | 277.7 | | 1 |
| P8g-1 40×256 | 237.1 | 198.9 | 1 | ×1.40 |
| P8g-2 40×128 | 85.0 | 51.9 | ×3.83 | ×5.35 |
| **P8g-2 40×256** | 94.7 | **42.5** | **×4.68** | **×6.53** |
| P8g-2 80×128 | 96.1 | 42.8 | ×4.65 | ×6.49 |

- 倍率は「P8g-1 から B 全体への変更」による（P8g-1 はすでに完了後の補充をしていた）。
- 2 万履歴では 200,000 より遅い: 最後に残った長い履歴を待つ時間（末尾の効果）が、状態機械では相対的に大きい。本計算の大きさ（20 万履歴のバッチ）の値を使う。
- 資源: P8g-2 は 234 レジスタ（P8g-1 と同じ）、ローカル 39,360 B（P8g-1 34,112 B）、常駐ブロック/SM は 128 スレッドで 2、256 で 1（P8g-1 と同じ）。比較の基準の経路（凍結した 1 履歴の関数）を実行時の旗で同じ核に持つが、レジスタ数は増えていない。
- 1×10⁸ 履歴の核の時間の見込み: 40×256 で約 1.2 時間（P8f の本番の起動では約 7.7 時間）。
