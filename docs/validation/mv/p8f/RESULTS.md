## 結論

**関門 0〜3 をすべて通し、T4 の本計算（2.0×10⁷ 履歴）は判定 A・B とも 19 ブロックすべて合格した**（|差| ≤ 1% かつ SEM ≤ 0.33%、固定 `Dref` = 0.060387587985606006 比、上流から順）。
言えるのは、P8e と同じ配置（水–肺–水–骨–水–鉛の積層、Mohan 10 MV 平行ビーム、深さの 19 ブロック）で GPU の核が採用基準に合格したことまで。同等性の検定ではなく、照射野・単体の板・境界の近くの bin は判定していない。

- 判定 A（保存済みの EGS5、6×10⁷ 履歴）: 最大 |差| は水 20–21 cm の +0.394 ± 0.132%。鉛の層は +0.087 ± 0.067%。
- 判定 B（保存済みの P8e の CPU 試作 MT、8,564,600 履歴。CPU→GPU の移植全体の比較）: 最大 |差| は肺 5–6 cm の −0.562 ± 0.289%。鉛の層は +0.018 ± 0.109%。

報告だけ（合否なし）:
- **差 ÷ SEM の 2 乗の和**: A は 50.3、B は 18.9（どちらも 19 ブロック）。B は偶然の範囲（GPU と CPU の試作の間に差は見えない）。**A は偶然だけで期待される 19 前後より明らかに大きく、試作の物理と EGS5 の間に、ブロック平均で 0.1〜0.4% 程度の小さな系統的な差があることを示唆する**（合否は基準 v2 のとおり合格のまま）。
  - A の |差| ÷ SEM が 2 を超えたのは 6 ブロック: 肺 5–6 cm（−2.2）、肺 7–8 cm（−2.1）、水 11–12 cm（−2.0）、骨 15–16 cm（+2.4）、水 17–18 cm（−2.4）、水 20–21 cm（+3.0）。肺と、骨の後ろの水で負、骨と鉛の手前の水で正。
  - P8e の CPU 試作の判定（8,564,600 履歴、χ² 21.7）では見えていなかった。履歴数を 2.3 倍にして試作側の誤差が小さくなったので見え始めたと読む（B が偶然の範囲なので、GPU 移植の誤差ではない）。A と P8e の判定の差のブロックごとの相関は 0.45。
  - 原因は調べていない。候補（事前に挙げてある近似）: 境界の扱い (a) と偏向の省略、陽電子に固有の物理なし、Auger の連鎖の省略、制動放射の高 Z の形。水だけの比較（P3a〜P7）でも +0.2〜0.3% のビルドアップの差を報告している。
- 関門 3（同じ Philox の 10⁷ 履歴を CPU と GPU で、対応する外側バッチの差）: 19 ブロックの差は `Dref` 比で 10⁻¹⁶ の桁。
- 境界と蛍光の数の 1 履歴あたりの比（GPU 本計算 / P8e 本計算）は 0.996〜1.034（まれな枝の終端・10 keV 未満を除く）。
- T4 の本計算は 5,513 s（276 µs/履歴、5,120 スロット）。手元の C++ CPU（1 スレッド）は 462 µs/履歴、P8e の Numba は 2,551 µs/履歴。速さの工夫（状態機械など）は入れていない。

## 経過で起きたこと

- **Codex のコードの誤り 2 件（実行して初めて分かった）**: (1) 関門 1 が P8e に無い関数名 `legacy_water_material` を呼んでいた（正しくは `legacy_bundle`。1a は通ったあと 1b で停止）。(2) Colab の結果の JSON に NumPy の真偽値を書いて止まった（`write_json` に変換を足した。起動用のファイルで、関門の指紋には入っていない）。どちらも Claude が直した。直したあとに全体の pytest を回し直し、1,376 件合格・2 件スキップ（Codex の報告と同じ数）。Codex の sandbox は `~/.cache` に書けず、関門 1 と Colab の経路を一度も通していなかった。
- **T4 は Colab CLI で回した**（ユーザー決定 2026-10-21。ブラウザと Drive を使わない）。150 MB を超えるファイルは `colab upload` が失敗したので 50 MB に分けて送り、VM 上でつないでハッシュを照合した。ノートブックの手順どおり `cupy-cuda12x` を入れると既存の `cupy-cuda13x` と重なったので、既存の 14.0.1 だけにして回し直した。
- **1 回目の VM は約 40 分で返却され、関門 3 の途中の結果を失った**。計算は VM 上で `nohup` で動かし、手元からの確認を止めていたため、カーネルが使われていないと判定されたと推定。2 回目は 4 分ごとに `colab exec` で確認しつつ結果を回収し、最後まで保たれた。使ったユニットは合計 約 3。

### 確認したこと

- 4 材料の関数・再利用した P5 の関数を、乱数の 100,000 入力と節点・吸収端・結合エネルギー・CUT などの端で照合した。戻り値がバイト一致。
  MT の配列・添字・続く 16 個の乱数も一致し、C++ が報告した消費数で NumPy の MT を進めた状態とも一致した。
- 4 成分の和、殻の行・全体・正規化、履歴内の和、touched_sum、整数乗・分数乗の演算順を Numba 0.66 と照合した。
- 100,000 線分と端の採点、全ての面の両側・両方向・w=0 の境界をバイト照合した。
- 状態固定の殻・緩和・CUT・棄却・境界・反転・事象の優先順位を照合した。実際の履歴では、運ばれた蛍光の CUT 未満の吸収、境界と energy/hard の競合、鉛中の最初の制動放射と親の再開を P8e と照合した。
  GPU 用の固定状態の出力には、粒子の種類・材料・領域・スタックの深さ・事象の種類の整数列も持たせた。
- 正常な履歴の健全性を確認した後、付与を 1 回落とす・群への加算を落とす・補充時の局所配列の初期化を落とす、の 3 故障を別ビルドで検出した。
- 100 履歴（種 2026102101）の小さな鎖 0 は、P8e の 12 出力と、生の coarse・fine・220 bin の全 100 群がバイト一致した。
- GPU の実際の駆動コードを CPU 上でエミュレートし、40×128 スロット・15,377 履歴で欠落・重複のない補充と末尾を確認した。
  全履歴の出力が CPU Philox とバイト一致し、集計が付与数に基づく許容内で一致した。局所配列の初期化を落とした故障も拒否した。
  **これは T4 の関門 2 の代わりにはならない。**
- 保存済み P8e の指紋の依存ソース 17 個は SHA256 が全て一致。既存 `gpu/p5*`・`p6*`・`p7*`、F11 の凍結ファイルを編集していない。
- D4 の常設ルールを更新。束の入力値はハッシュつきのデータとして送る。正典が輸送中に計算する値は装置上で計算する。
