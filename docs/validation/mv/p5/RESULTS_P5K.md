## Q 系の地図（2026-10-17、報告のみ。ユーザーの指示「Q 系がなぜ遅いのかを地図で確かめる」）

`p5kq_colab.ipynb`（F・Q1・Q8 の ncu の生の記録だけ。関門は通さない）。Drive `viveMonte/p5/p5kq/results/`。集計は Claude が手元で。ncu の下の時間は F 3.23 s、Q1 4.61 s、Q8 4.09 s。

| | F | Q1 | Q8 |
|---|---|---|---|
| ワープ命令 | 1.536e10 | 1.429e10 | 1.319e10 |
| 参加レーン（全命令／倍精度） | 9.94 / 10.19 | 12.98 / 11.85 | 11.11 / 11.00 |
| 倍精度のワープ命令 | 3.76e9 | 3.20e9 | 3.45e9 |
| 命令を出せている割合（issue active） | 5.29% | 3.40% | 3.53% |
| 1命令あたりの待ち: 同期（barrier） | 0 | 25.9 | 27.7 |
| 1命令あたりの待ち: メモリ（long scoreboard） | 30.0 | 26.9 | 22.8 |
| 待ちの標本のうち同期の割合 | 0 | 46.6% | 37.0% |
| 読み込み1要求あたりのセクタ（F は local、Q は global） | 2.25 | 9.09 | 7.86 |
| L2 の当たり | 73.9% | 79.8% | 87.1% |

- **結論: Q 系が遅いのは、ブロックの同期での待ちのため。** Q は F より命令が少なく（−7%・−14%）、参加レーンも多い（12.98）が、命令を出せている割合が 5.29% → 3.40% に下がった。待ちの標本の 37〜47% が同期で、その 99% が各回の終わりの `__syncthreads`（回のループの戻りの分岐に付く。Q1 で 1ブロックあたり約9,300回）に集まっている。各回の時間が「ブロックの8ワープのうち一番遅いワープ」で決まり、ほかのワープが待つ。
- 時間の比の見積もり: 命令の比 0.93 × 命令を出せている割合の比 1.56 = 1.45。実測（ncu の下）の Q1/F = 1.43 と合う。
- メモリは主な原因ではない。Q の読み込みは散らばり（1要求あたり 9.1 セクタ、F は 2.25）、DRAM の読み書きも同程度あるが、メモリでの待ちは F より少ない（L2 の当たりが高い）。
- C を続けて進める Q8 は同期の回数が減り（同期の割合 37%）、Q1 より速い。ただし1回あたりの待ちが長くなり、同期の待ちはなくならない。
- 次の候補（Claude の案、未計画）: ブロックの同期を使わず、ワープの中だけで詰め直す（1ワープが自分のスロット 32×m 個を `__syncwarp` だけで状態ごとに並べる）。F の「同期なし」と Q の「詰め直し」の両方を持つ形。模擬では、詰め直しの範囲が小さいと稼働率が下がるので（R=256 で 0.74、R=128 で 0.64）、m を決める前に模擬で確かめる。
