## 診断（報告のみ）

- D1 資源: `p5b_run_kernel` は **255 レジスタ/スレッド（上限）**、**ローカルメモリ 30,144 B/スレッド**、共有メモリ 0、1ブロックの最大スレッド 256。履歴ごとの核も 255・30,112 B。T4: 40 SM、SM あたり 1,024 スレッド・65,536 レジスタ。
- D2 集計の方式: 2万履歴で、原子的加算でまとめる本番の核 1,694.6 ms、履歴ごとに書き出す核 1,696.4 ms（出力 131 MB）。差は 0.1% で、どちらの方式でも時間はほぼ同じ。
- D3 ブロックの大きさ: 64 → 78.8、128 → 79.2、256 → 80.8 µs/履歴。差は 2.6% 以内。

## 考察（Claude の解釈。測定で確かめた原因ではない）

- **原子的加算の集計は律速ではない**（D2 で差が 0.1%）。
- **レジスタの割り当てと作業領域が最も疑わしい。** 255 レジスタ × 128 スレッド = 32,640 で、65,536 の SM には2ブロック（256 スレッド = 8 ワープ）しか同時に載らない（上限 1,024 スレッドの 1/4）。さらに 1 スレッドあたり 30 KB がローカルメモリ（実体はグローバルメモリ、L1/L2 でキャッシュ）にあり、同時に載る 10,240 スレッドで約 300 MB になって L2（T4 は 4 MB）に収まらない。線量の表への書き込み（`hs[150]`・`fine[600]`）や粒子のスタックへの出し入れが、そのままメモリの往復になる。ブロックの大きさを変えても時間が変わらない（D3）ことも、同時に載る数がレジスタで決まっていることと合う。
- **倍精度**: T4 の倍精度の性能は単精度の 1/32（公表値。今回は測っていない）。同時に載るワープが少ないと、倍精度の遅さもメモリ待ちも隠しにくい。どちらが大きいかは、この測定では分けられない。
- **履歴の長さのばらつき**: 1万 → 10万 → 100万で 88.4 → 79.2 → 76.6 µs と速くなる。最後に残った長い履歴を待つ時間（末尾の効果）が、n が大きいほど薄まるため、と考えると合う。
- 速くするなら、作業領域を減らす（線量をスレッドの局所に貯めず直接集計する、スタックを小さくする）、レジスタの上限を指定する、などが候補。いずれも合格した構成を変えるので、別の計画で鎖2の検査に戻る必要がある。

## 経過

- Colab の最初のスモークで、g++ が凍結した核 `p5_kernel.h:402` の修飾なしの `isfinite` を通さずビルドが止まった（clang・NVRTC は通す）。凍結ファイルは編集せず、`p5d_gxx_compat.h`（`using std::isfinite;`）を g++ の経路だけで `-include` した（計画の修正1）。手元の clang でこの指定でも `p5a.CPU` と10出力が一致することをテストで確認。
- 再実行のとき、残っていたランタイムの複製に新しいコミットが無く `checkout` が失敗した。ノートブックは `fetch` をしない（次に使うときに直す）。
- C の関門は実行中に判定され（不合格なら停止）、`colab.json` の `checks` には記録されない。Claude が npz から独立に再計算して上の表に載せた。
