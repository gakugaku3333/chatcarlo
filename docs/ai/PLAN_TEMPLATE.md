# 計画テンプレート

このテンプレートをコピーして `docs/ai/plans/<日付>-<slug>.md` を作る。Codexに実装を委任する場合、**このファイルが意図の全量**になる（Codexは会話履歴を持たない）。書いていないことは実装されない前提で書くこと。

ファイル名例: `docs/ai/plans/2026-07-28-dose-plot-cli-option.md`

---

```markdown

- 状態: draft | codex-reviewed | approved | implemented
- 作成者: claude
- 実装担当: codex | claude

## 目的（1〜3行）

- 変更禁止: <明示的に触ってはいけない範囲。特に data/ や migrations/ 等>

## 受入条件（検証可能な形で列挙）

- [ ] <具体的な条件。「動くこと」ではなく「Xを入力するとYになること」のレベルまで>
- [ ] <...>

## 運用メモ

- **凍結・ハッシュの対象に、計画ファイルと報告ファイルを入れない。** 計算の途中や後で追補を書き足すと、照合で止まる（P1dで停止、P3sで再発しかけた）。対象はコードと入力データに限ると計画に明記する。
- **統計の条件は、試し計算で誤差を測ってから決める。** 測らずに書いた条件に届かず「統計不足」になった例が2回ある（P2のQ7、P3sのS4）。

- **計画レビュー(Codex)**: `codex exec` で計画ファイルを読ませ、実現可能性・抜けたテストケース・より単純な代替案を指摘させる。指摘を反映したら「状態: codex-reviewed」に更新。
- **承認**: 人間が読んで「状態: approved」にする。ここまでで疑問点は収束させる。
- **実装(Codex)**: approved の計画ファイルのみを渡す。`docs/ai/plans/` 以外の文脈は前提にしない。
- **差分レビュー(Claude)**: 実装後、この計画の受入条件・対象範囲との適合性を検査し、以下に分類する:
  - 即対応 / 追加調査 / 将来改善 / 意図した仕様 / 誤解による指摘
- 完了したら「状態: implemented」にして残す（削除しない — 次回の参考になる）。
