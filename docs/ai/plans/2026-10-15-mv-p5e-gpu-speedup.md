## 目的

1. **凍結した核（`p5_kernel.h`）を編集せずに**変えられるもの（割り当て方式・スタックの上限・レジスタの上限）の効果を、同じセッションで測る。どれが効くか・効かないかは測定事項で、原因の特定は主張しない（0.272 は「ステップ数を同じ費用とした固定の組の充填率」で、実際のワープの効率ではない）。
2. 採用した構成で、P5c と同じ検査（鎖2）をやり直し、合格したら新しい「合格した構成」とする。

## 0. 前提事実（検証済み、2026-10-15）

- **ワープの効率（Claude が手元で計算）**: 束の2万履歴の参照 `history_steps`（P5a の CPU、履歴ごと）で、P5b の対応（スレッド i → 履歴 start+i、32本で1ワープ）のとき、`Σsteps / (32 × Σ_ワープ max steps)` = **0.272**。128本のブロック単位では 0.224。1履歴のステップ数: 最小1、10% 点 1、中央値 522、平均 666、90% 点 1,600、99% 点 2,736、最大 4,340。**ステップ数はコストの代理**（光子と電子の1ステップの重さは違う）だが、仮説を分けるには足りる。
  → いまの入口は、各ワープが「いちばん長い履歴」が終わるまで待つ。1スレッド1履歴の固定の割り当てが、数え方の上で約 3.7 倍の無駄を生んでいる可能性がある（実際の時間での効果は測るまで不明。分岐の発散はこの方法では直らない）。
- **資源（P5d の D1）**: 255 レジスタ/スレッド（上限）、ローカルメモリ 30,144 B/スレッド。T4: 40 SM、SM あたり 65,536 レジスタ → 128 スレッドのブロックが SM に2個（256 スレッド、8 ワープ）。作業領域の内訳（ソースから計算）: スタック 64 段 × 184 B = 11,776 B、`hs`+`fine` 6,000 B、`P5bLocal` 約 6,556 B、`nspec_work` 5,120 B。
- **スタックの深さ**: 板の計算で観測した最大は7段（P5c の100バッチ、P5d の100万履歴）。核のあふれの判定は `top+3>=P5_STACK_CAP` で、あふれは `counts[6]` に数えられ健全性の検査で止まる。**深さ7は板に固有**（照射野・層では確かめ直す）。
- **集計の費用**（P5d の D2）: 原子的加算でまとめる核と、履歴ごとに大きく書き出す核の時間の差が 0.1%（原子的加算の単独の費用を分けて測ったものではない）。ブロックの大きさ 64/128/256 の差 2.6% 以内（D3）。
- Philox の乱数は（seed, 全体の履歴番号）で決まり、行は `p5b_row(h, n)` で履歴番号から決まる。**どのスレッドがどの履歴を計算しても、各履歴の乱数と行は変わらない**（`p5b_wrap.h` の `p5b_history(t, seed, start+i, …)` と `p5b_row(i, n)`）。

## 1. 変種（探索。報告のみ。核のソースは編集しない）

3つの要素の全組合せ 2×2×3 = **12 変種**を同じノートブックの実行で測る（組合せのために2回目の Colab を要さないため）。

| 要素 | 水準 |
|---|---|
| 割り当て | `S`: 静的（P5b と同じ、スレッド i → 履歴 k=i）／ `D`: 動的（下記） |
| スタックの上限 | `64`（P5b）／ `16`（`-DP5_STACK_CAP=16`） |
| レジスタの上限 | なし／ `--maxrregcount=168`／ `--maxrregcount=128` |

V0 = (S, 64, なし) は P5c で合格した構成そのもの（P5b の `p5b_run_kernel`・`p5b_per_history_kernel` と同じソース・同じ指定でコンパイルしたものを使う）。

**動的な割り当て**（新しい入口 `p5e_gpu.cu`。`p5b_wrap.h` をそのまま使う）:
- 呼び出しごとに 0 にした `unsigned long long` のカウンタ1個。各スレッドは `for(;;){ k=atomicAdd(cnt,1); if(k>=n) break; h=start+k; p5b_history(t,seed,h,maxsteps,&L); 行=p5b_row(k,n); … }`。範囲の判定の後で `start+k` と行を計算する。
- 本番の核（集計）と履歴ごとの核（履歴ごとの出力は**位置 k に書く**）の両方を動的にする。
- 起動するスレッド数 T = SM 数 × 常駐ブロック数 × 128。常駐ブロック数は、CuPy に占有率の API があればそれ、なければ `num_regs`（ワープ単位 256 個に切り上げ）と `local`・スレッド上限から計算する。どちらの方法か、値、各変種の `attributes`（`num_regs`・`local_size_bytes`）を記録する。

**理想の並べ替え（診断のみ・採用しない）**: 保存済みの CPU のステップ数で履歴を並べた順序配列 `order`（`[0,n)` の置換であることを検査）を静的の入口に渡し、スレッド i が k=order[i] を計算する（乱数・行・保存先は k）。n=20,000（束の `history_steps` がある範囲）だけ。「実際のコストを知っている理想の順序」として報告し、実用の速さとは分ける。

## 2. 正しさの関門（測る前に固定）

**探索の各変種**（どれか1つでも不合格ならその変種の時間を記録せず、採用候補から外す。停止はしない。ただし V0 が不合格なら停止）:
- (E1) **V0 との履歴ごとの全出力のビット一致**: 同じ T4・同じセッションで、n=20,000・start=0 の履歴ごとの核の出力（`p5b_core.HISTORY_ORDER` のすべて）が V0 の同じ出力と `np.array_equal`。動的なら位置 k で比べる。（ソースが同じでも機械語が変わり得るので、主張は測って示す。不一致なら「履歴が変わらない」とは言わず、その変種を採用候補から外し、事実を記録する。）
- (E2) n=100,000・start=0 の本番の核で、`nspec`・`counts`・`step_batches` が束の `c4_*[0]` と完全一致、深い5ブロック `core.relative` ≤ 1e-8、健全性0件（P5d の D-g(ii) と同じ）。
- (E3) 動的のみ: 訪問の検査。検査用の核（同じ入口で、履歴の計算の代わりに `visits[k]+=1` を原子的に行う）で、n < T、n = T−1、T、T+1、T の倍数でない大きい n、start ≠ 0、同じカウンタの2回続けての呼び出しのそれぞれで、全 k の訪問回数がちょうど1。

**採用した構成**（§3 で選んだもの）: P5c の C0〜C4 を、P5b 計画 §3 の基準を変えずにやり直す。そのために `p5e_core.py` が新しい構成の指紋を持つ: 組み立てたソースの sha256、コンパイル指定、入口の名前、ブロックの大きさと T、割り当て方式、束の sha256、GPU の環境。違う構成の途中保存は拒否する（C0 相当）。コンパイル指定が V0 と違うなら C1 もやり直す。スタック 16 を採用する場合は、手元で CPU の `-DP5_STACK_CAP=16` ビルドが保存済み P5a Philox 100バッチと全出力でバイト一致することも確かめる（2プロセス、約10分）。「あふれ0」は**試した板・履歴範囲について**の事実として記録する。

## 3. 計時と、採用候補の選び方（固定）

- 同じセッションで、暖機（各変種 n=1,000 を1回）の後、**3巡の交互の測定**: 各巡で 12 変種を決まった順（巡ごとに順番を逆にする）に n=100,000・start=0 で1回ずつ。時間は P5d と同じ境界（`kernel_ms` はイベント、`call_s` はホスト）。動的のカウンタの 0 化は開始イベントの前（`call_s` には入る）。
- 選び方: E1〜E2（動的は E3 も）に合格した変種のうち `kernel_ms` の中央値が最小のものを候補とする。ただし、その3回の最大値が V0 の3回の最小値以上なら（範囲が重なるなら）、**V0 のまま（採用なし）**として、C2〜C4 はやらない。候補と範囲が重なる変種が他にあるときは、V0 から変えた要素の数が少ないものを選ぶ。数が同じなら、レジスタ ＜ スタック ＜ 割り当て の順に「変えると重い」とみなし、重い要素を変えていないほうを選ぶ。それでも同じなら中央値の小さいほう。
- 候補と V0 だけ、n=1,000,000 を各1回測る（報告）。
- 理想の並べ替えは別の表で報告し、選ぶ対象に入れない。

## 8. 2巡目のレビューの反映（§1〜§7 と食い違うときは本節が優先）

1. **T の決め方**: 各入口（本番・履歴ごと・各変種）ごとに、CuPy の `cupy.cuda.driver.occupancyMaxActiveBlocksPerMultiprocessor(RawKernel.kernel.ptr, 128, 0)`（または同等の CuPy 14.0.1 の経路）で常駐ブロック数を取り、T = SM 数 × その値 × 128。軽い検査用の核の値を本番に流用しない。API が呼べなければ**停止**（自前の見積もりはしない）。値・`num_regs`・`local_size_bytes` を記録する。
2. **割り当ての共通ループ**: `p5e_gpu.cu` に、静的・動的・順序配列の割り当てを1つのデバイス関数で持ち、本番・履歴ごと・訪問検査の3つの入口がすべてそれを使う。訪問検査（E3）は輸送の代わりに `visits[k]`、`global_h[k]=start+k`、`rows[k]=p5b_row(k,n)` を書く。E3 の条件に、start ≠ 0 で `global_h` と `rows` が期待どおりであることを加える。さらに小さい実輸送（n=2,000、start=7,000）で、動的の履歴ごとの出力が静的の同じ出力と `core.bits` で一致することを E3 に含める。`p5b_row` の引数は呼び出しの中の k（全体の履歴番号ではない）。
3. **選び方の修正**: まず「max(変種の3回) < min(V0 の3回)」を満たす合格変種の集合 A を作る。A が空なら V0 のまま（採用なし）。空でなければ A の中で中央値が最小のもの a* を取り、A の中で a* と範囲が重なるもの（a* を含む）の集合 B を一度だけ作り、B の中で §3 の単純さの規則で選ぶ。反例（V0＝10〜11、A＝8〜9、B＝8.5〜10.5 → B は集合 A に入らないので選ばれない）を単体テストに入れる。
4. **E1 の比較は `core.bits`**（`np.array_equal` ではない）。テストに符号付きゼロ、形・型の違い、非有限値を加える。V0 と V0 の E1 は自明なので、V0 自身の妥当性は E2 で見る。
5. **保存の契約**（Drive `viveMonte/p5/p5e/explore/`）: 各変種の E1 の履歴ごとの出力（V0 を含む）、E2 の本番の出力、E3 の `visits`・`global_h`・`rows` と小さい実輸送の出力、各回の生の計時（P5d と同じ記録の形）、構成の指紋、選び方の入力と結果。履歴ごとの出力（約 131 MB/変種）は変種ごとに保存してから GPU とホストのメモリを解放する。
6. **失敗の分類と処理**: (a) 数値の不合格（E1/E2/E3） → その変種を除外して続ける。(b) コンパイルできない・起動できない（資源不足など CUDA のエラーではないもの） → その変種を除外して続ける。(c) 検査の実装の故障（例外） → 停止。(d) CUDA の実行エラー → 停止し、ランタイムの再起動を案内する。V0 が (a)〜(b) なら停止。除外した変種は3巡から外す。候補がゼロでも探索の記録は完成させて終了する。既存の `timed_gpu` の `core.Stop` を変種の除外に使うときは、捕まえて (a) として扱う。
7. **スタック16の CPU 照合**: `p5e.py` に、凍結の `p5_cpu.cpp` を `clang++ -O2 -ffp-contract=off -std=c++11 -shared -fPIC -DP5_RNG_PHILOX -DP5_TRANSPORT_FAULT=0 -DP5_STACK_CAP=16` でビルドする経路を新しく作る（`p5d_core.CPU` の固定値は変えない）。比較は `p5a.OUTPUTS` の10出力を `p5a.compare_outputs` で、相手は `~/.cache/chatcarlo/p5/p5a/philox/` の100バッチ（`p5b.saved_batch` で config の指紋を照合）。健全性も確認。n=2,000 の小さい実ビルドの検査をテストに入れる。
8. 軽微: `p5e_colab` は「import した時点で」`cupy` を読み込まない（関数の中の import は可）。採用した構成では C0〜C4 をすべてやり直し、C1 も常に行う。C3 の故障の注入版は新しい本番の入口に作る。スタックの判定には `top+3` と `top+2` の両方がある。
9. 理想の並べ替えの診断: (S,64,なし) の静的の入口に順序配列を渡す。並べ方は束の `history_steps` の降順、同じ値は k の昇順。n=20,000、3回。順序配列の作成と転送は計時の外（記録はする）。履歴ごとの出力を V0 と `core.bits` で照合し、合わなければ診断値を採用しない。
10. 探索は**同じセッションで完走した場合だけ**選び方に使う。途中で切れたら、保存済みの正しさの検査は再利用してよいが、3巡の計時は新しいセッションで最初から取り直す。
