結論は、**方式自体は成立しますが、現骨子の「隣区画＋前後1点の余裕」だけでは、すべての入力で同じ添え字を返す保証にはなりません。** 候補範囲を実行時に元の比較で検証し、外れた場合は元の探索へ戻す形が、保証と実装量の釣り合いに優れます。

親・当該 AGENTS.md、CLAUDE.md の P5 節、計画、指定の5ファイルを読みました。以下は、P5g を合格構成として保存し、物理・補間式・乱数順序を変えず、速さは報告のみとする方針内での評価です。ファイル変更・計算の実行はしていません。**骨子段階の致命的な問題はありませんが、実装前に詰めるべき「実質」の事項があります。**

1. **【実質】固定の余裕幅に、正解を含む根拠がない。**  
   [計画41–43行付近](docs/ai/plans/2026-10-16-mv-p5h-table-lookup.md:41)では、区画番号のずれが隣まで、`log` の差による添え字のずれが1点まで、という前提が暗黙です。P5a0 の観測は、その誤差上限の証明にはなりません。密集点や重複点では、小さな値の差が多数の添え字の差になる場合もあります。

   **推奨修正は、表を「正解範囲の保証」ではなく「候補範囲の予測」にすることです。** 元の探索の開始位置を `s`、比較値を `A(i)`、候補範囲を `[L,H)` とすると、非減少の比較値について、

   ```text
   s ≤ L ≤ H ≤ n
   L == s または A(L-1) < x
   H == n または !(A(H) < x)
   ```

   が成立すれば、この範囲での lower_bound は元の `[s,n)` と同じ答えになります。`A(i)` は元どおり、生の格子値または**実行端末の** `log(es[i])` です。条件を満たさなければ元の全範囲探索へ戻す。これなら、区画の丸めや手元の `log` の差は速度にだけ影響します。

2. **【実質】重複点・探索終端・pair の開始位置を、添え字契約として明文化する必要がある。**  
   [元の実装](prototypes/mv_electron/gpu/p5_kernel.h:63)は `<` による lower_bound で、同値点の**先頭**を返します。生の格子が異なっていても、`log` 後に同値になる場合があります。「近い区間」「補間結果が同じ」では代替できません。

   また、答えは `n` にもなります。候補表の「終わり」が、最後に読める要素なのか、排他的な探索終端なのかを固定してください。`p5_pair_interp` は `[start,n)` の探索なので、全体の先頭へ戻してはいけません。生の返却添え字を比較し、その後の `-1`・clamp・同値判定・範囲外処理は元の順番を維持する必要があります。

3. **【実質】NaN・無限大・範囲外は、整数化より前に扱う必要がある。**  
   元の `lower_bound(NaN, ...)` は、すべての `<` が偽なので `0`、開始位置つきなら `start` を返します。新方式で先に区画番号へ整数変換すると、その意味を維持できません。巨大な有限値でも変換範囲を超え得ます。

   非有限値と区画範囲外は、**変換前に元の探索へ戻す**のが簡単です。ただし、[元の `interp`](prototypes/mv_electron/gpu/p5a0_common.h:44)自体は NaN で `j=-1` になり得ます。したがって保証は「探索関数の添え字」と「元の補間が定義される入力での出力」に分けるべきです。元が未定義動作となる入力まで、出力のビット一致を要求する必要はありません。

   格子側についても、有限・非減少・必要点数を生成時に確認してください。NaN を含む格子など、比較が順序を作らない場合には上記の保証は使えません。

4. **【実質】CPU の関門0だけでは、端末固有の境界誤りを狙って検出できない。**  
   [関門0・2](docs/ai/plans/2026-10-16-mv-p5h-table-lookup.md:52)に、**T4 上でも直接探索を呼ぶ境界テスト**を追加するのが妥当です。2万履歴の自然発生入力では、狭い境界を踏む保証がありません。

   テスト集合には次を含めてください。

   - 重複列の先頭・末尾、`0`・`n`・`start` を返すケース。
   - 生の `es` の隣接値に加え、端末で計算した `log(es)` とその `nextafter`。
   - 区画座標の境界と、その直前・直後。入力値と対数値のどちらを区画化するかも固定する。
   - NaN、±∞、±0、巨大値、対数を取れない入力。
   - 意図的に狭くした候補範囲によって、検証・フォールバックが実際に働くケース。

   100万乱数は補助として有用ですが、これで「全入力の保証」を置き換えることはできません。

5. **【実質】検査用・本番用ビルドと、生成表の同一性を関門に含める必要がある。**  
   検査用ビルドは、比較追加によって最適化や資源使用が変わります。現在の本番ビルドのビット一致検査は維持し、検査用ビルドでも出力一致を確認してください。誤った探索先で読む前に検出できるよう、候補範囲の検証は補間より前に置きます。

   指紋には、実際に使う**生成区画表・元の格子・pair のしきい値と `start`・コンパイル設定・計算ソース**を含めます。生成器を指紋から除くとしても、生成物を除いてはいけません。測定スクリプトを除く既存方針とは両立します。GPU の不一致検出は、warp 内の一部だけを途中 return させず、ホストが確実に失敗を確認する構造にしてください。

6. **【実質】ワープ命令比率から計算した ×1.255 は、時間短縮の上限ではない。**  
   [計画32行](docs/ai/plans/2026-10-16-mv-p5h-table-lookup.md:32)の値は、「命令数が時間に比例する」という仮定下の目安です。探索命令と他の命令では、実行資源・遅延・参加レーン数が異なります。また探索変更がレジスタ数、spill、再収束を変える可能性もあります。

   「命令数に基づく参考試算」と表記するのが適切です。速度の交互測定に加え、探索の**絶対命令数**、参加レーン、レジスタ・local memory を記録すると、割合だけの変化を誤読せずに済みます。

7. **【参考：代替案】前回添え字の検証＋近傍探索は、エネルギー表では具体的に有望。**  
   前回の生の lower_bound 添え字 `j` について、

   ```text
   j == s または A(j-1) < x
   j == n または !(A(j) < x)
   ```

   を確認し、成立すればそのまま返します。外れたら数点だけ移動し、それでも見つからなければ元の二分探索へ戻す構造です。

   | 対象 | 利点 | 費用・注意 |
   |---|---|---|
   | `brems_e`・`rates`・`loget`・`ts` | エネルギー更新が小さい間は、同一区間や近隣に当たりやすい。区画表が不要 | 表ごとの添え字を状態に保持する費用。既に `cached_ev` があるため、追加効果は測定が必要 |
   | `pes` | 同じ光子の継続では利用できる可能性 | 粒子切替で大きく飛ぶ。pair の探索開始位置にも注意 |
   | `us` | 実装は可能 | 一様乱数が毎回変わるので局所性を期待できず、前回位置からの線形移動は不利 |
   | `ks` | 小さい表なので状態保持を省ける | 9点の元の二分探索を残す方が簡単な可能性が高い |

   P5g は親の中断・子の処理・親の再開があります。**前回添え字を常に検証するヒントとして使えば、粒子切替時のリセット漏れは正しさに影響しません。** 一方向にしか移動しない方式は、粒子切替や異なるエネルギー変数をまたぐため避けるべきです。無制限の線形探索より、移動回数を制限してフォールバックする方が GPU の長い裾も抑えられます。

8. **【参考：代替案】最初から全表へ広げず、小さく分けると比較しやすい。**  
   `pair start` の事前計算は、同じ binary64 の格子・しきい値を使えば直接比較だけで確定でき、状態追加も不要です。ただし観測された対象命令は0.36%で、大きな短縮は期待しにくいです。

   次に、`us` は区画表＋検証、エネルギー表は前回添え字＋検証、`ks` は現状維持、という組合せが考えられます。方式が複数になる保守費用と引き換えに、各表の入力の性質に合います。単一方式で揃える区画表案も合理的なので、採否を分けて測れる実装にすると判断しやすくなります。
