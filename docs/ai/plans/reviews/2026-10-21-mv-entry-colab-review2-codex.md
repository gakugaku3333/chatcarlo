1. **【実質】§1-3の `scorer_vectors(extent=9.)` は、GPU採点器へ直接渡せる入力ではありません。**

   [`p7.scorer_vectors`](prototypes/mv_electron/gpu/p7.py:125)は16列で、単体のクリップ・ビン採点用です。GPUの[`p7_score_kernel`](prototypes/mv_electron/gpu/p7_gpu.cu:51)は9列の付与記録を読みます。`CPU.score()`の出力も、GPUの `regions/sums` とは構造が異なります。`extent=9.`を指定するだけでは2d相当は成立しません。

   **修正案:** 入口側で既存の[`scorer_fixture`](prototypes/mv_electron/gpu/p7.py:486)と同じ変換を行い、`p6`用の端点を追加する。期待値は `layout='p6'` のCPUの `p7_sinks` から作り、GPUの `regions/sums` と比較する。±9 cm、粗・細ビン境界、各深さ帯、点付与・線分付与を含め、容量の未使用部分 `1836:3420` がゼロであることも受入条件にしてください。

2. **【実質】§4の3D表示の採点位置が、深さと表示zを取り違えています。**

   計画の表示では板表面が `z=30`、線源が `z=130` なので、深さは `d=30-z` です。一方、[`geometry('p6')`](prototypes/mv_electron/gpu/p7_core.py:50)の座標は表面から増える深さです。

   深さ5/10/20 cmの帯を表示する正しいz範囲は、順に **24.5–25.5、19.5–20.5、9.5–10.5 cm**。計画の4.5–5.5、9.5–10.5、19.5–20.5では、誤った表示を合格させます。

   **修正案:** 表示変換 `z_display=30-depth` を一か所に固定し、帯のラベルと頂点を対応させて試験してください。

3. **【実質】§1-5では、解析前の線量換算が抜けています。**

   `p7_core.reduced(r,'p6')` は、1回の起動の領域付与エネルギーを内部100群について合計した値を返します。100回分を積めば形は整いますが、単位はまだMeVです。

   [`analysis_p3b3.compare/reports`](prototypes/mv_electron/analysis_p3b3.py:134)は線量換算済み配列を受け取り、内部では換算しません。既存P6解析は明示的に[`stats.dose()`を通しています](prototypes/mv_electron/gpu/p6.py:434)。

   **修正案:** 次の契約を明記してください。

   - 外側100バッチを積み、`N=総履歴数`、`nbatch=100`を付ける。
   - GPU・EGS5の両方を `analysis_p3b3.dose()` に通す。
   - その出力を `compare/reports/slab_ratios` に渡す。

   期待形状は `axis_coarse/slab_coarse=(100,120)`、`axis_fine=(100,300)`、`profile=(100,2,3,72)`、`profile_fine=(100,2,3,144)`です。既知のMeV入力から既知の線量差が出る試験が必要です。同じ履歴数なら比で換算漏れが相殺されるため、`slab_ratios`だけの試験では検出できません。

4. **【実質】§1-2の「固定の位置表」と、完全なハッシュを再構築する規則が未完です。**

   GPUの位置はコードから確定できます。0始まりで、現行の[`measure`](prototypes/mv_electron/gpu/p7_colab.py:41)は次の対応です。

   | GPU引数位置 | 内容 |
   |---|---|
   | 0–32 | 基本表のポインター・寸法・スカラー |
   | 25・26 | `edges`・`cum` |
   | 33・34 | デバイス生成の `logs`・診断カウンター |
   | 35 | 幾何 |
   | 36–39 | seed・start・n・maxsteps |
   | 40–43 | field・field_half・ssd・regions |
   | 44・45 | next・history |

   CPUの[`p7_run`](prototypes/mv_electron/gpu/p7.py:96)は別の並びで、表は引数にありません。先行する **`p5j_configure` が共有設定へ格納**します。したがって、CPUのrun境界だけを観測しても資材は観測できません。

   また、承認JSONにはスペクトル名・元ファイルSHA・engine・総履歴数がありますが、1バッチの引数だけから全部を復元できるわけではありません。資材側も、P7の `describe(data)` に含まれる `single/nist_E/nist_muen` は核の実引数ではありません。`logs`は実引数ですが、各デバイスで生成する値です。

   **修正案:** GPU用・CPU用・CPU設定用の位置表を固定し、各JSON項目を「実引数から観測」「観測値から導出」「照合済み資材から取得」に分けてください。総履歴数は100バッチの検証済み範囲から導出する。生成ログは承認時のCPUバイト列との完全一致対象にせず、既存方式で生成来歴を記録する。この規則がないと「両ハッシュ完全一致」という受入条件を一意に実装できません。

5. **【実質】`__main__.py` の分岐は可能ですが、明示オプションの検出と `plot` の入口が未指定です。**

   現行[`main()`](chatcarlo/__main__.py:384)は共通parserで全引数を解析してから各コマンドへ渡します。MVの `--out` は現行run parserにありません。また、解析後のNamespaceだけでは「省略した既定値」と「同じ値を明示指定」を区別できず、例えば `--workers 1` を確実に拒否できません。

   `plot`の位置引数はsceneではなくNPZで、sceneは任意の `--scene` です。「最上位domainを見る分岐」をそのまま適用できません。

   **修正案:** 生のargvを保持して、診断parserへ入る前にMV専用parserへ委譲する。`plot`は `--scene` がある場合の拒否方法と、ない場合に識別するかどうかを明記してください。受入試験には、明示既定値の拒否、診断sceneへのapprove、MVのtrace/animate/plot、診断側runの既存オプション維持を追加すべきです。

6. **【実質】入口アダプターと来歴照合の試験が、現状の受入項目では不足しています。**

   **追加すべき試験:** 非ゼロstartでのCPU履歴一致、CPU本番経路の既存 `CPU.run()`との一致または `c3`照合、幾何・edges/cum・表スカラー・寸法の誤結合検出。さらに、回収した出力だけの変更、観測記録だけの変更、別seed・別条件の再開バッチ混入を拒否する試験が必要です。これは前回4の設計の再要求ではなく、追加された照合仕様を試験で担保する不足です。

**コードで成立を確認できた点と、単純化案**

配置`p6`のGPU受け渡し自体に障害はありません。P7はP6と同じ1,144バイトの幾何ABIを使い、採点側も渡されたoffset・sizeを参照します。1,836ビンを容量3,420の中で使えます。`check_kernel_diff()`も今回の読み取り専用実行で3ファイルすべてpassでした。`p7.CPU(work,data,'philox',layout='p6').histories(2048,seed,5.,100.)`も正しい引数指定です。`c3`は全容量を比較するので再利用可能、`c2`は健全性・線源・乱数呼出し数を再利用し、領域報告だけp6配置で作り直せます。

実装は次のように絞れます。

- **GPU初期化は新規アダプター、`measure/output/scorer`は既存メソッドを再利用する。** 観測のために必要な起動部分だけを入口側で実装し、出力生成・取得まで複製しない。
- **p6専用の集約関数を一つ置く。** `reduced(...,'p6')`→外側100バッチのstack→`stats.dose()`を共通化し、P7のA/B/C専用contractを持ち込まない。
- **核に渡る入力と補助資材を分けて目録化する。** 実引数の照合と、未使用の補助配列・元ファイルのSHA検査を別の規則にすれば、無理なハッシュ再構築を避けられます。
