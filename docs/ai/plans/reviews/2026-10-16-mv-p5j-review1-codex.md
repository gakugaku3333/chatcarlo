**現案だけでは「すべての入力でビット一致」とは言えません。** 通常の輸送で到達する入力について実装・関門で確認する方針は妥当ですが、一般入力への保証、定数畳み込み、例外入力の扱いを明文化する必要があります。指摘は以下です。致命に該当するものはありません。

1. **【実質】同じ翻訳単位・同じコンパイル指定だけでは、定数化前後の一致の証明になりません。**  
   [計画31行](docs/ai/plans/2026-10-16-mv-p5j-constant-terms.md:31)。元の `p5_hard` がインライン化されれば、A・Bの対数自体や、その周囲の定数演算が畳み込まれ得ます。一方、新版は配列から読み出す値になります。`-ffp-contract=off`／`--fmad=false` は、この差まで禁止する指定ではありません。特にBの `log(.5)+1/(1-.5)` 周辺が要確認です。  
   元の演算順序を保持し、**通常版・検査版それぞれの最終関数出力**で判定してください。元版に定数畳み込み禁止などの変更を加えて比較すると、凍結済み構成との比較になりません。有限の試験合格は、全入力の証明とも区別する必要があります。

2. **【実質】Cのガードは、元の引数をそのまま評価する形まで固定すべきです。**  
   [元式](prototypes/mv_electron/gpu/p5_kernel.h:19) に合わせ、例えば次の形です。
   ```cpp
   double arg = -d/tau;
   double L = (arg == -0.5) ? K2 : log1p(arg);
   ```
   `-(d/tau)`、`-tau/2/tau` などへの書き換えや、`tau-d`・`tau/(tau-d)` の定数化は範囲外です。`if(arg != -0.5) fallback; else ...` もNaNでは正しく戻りますが、`fabs(arg+.5)>許容値` のような判定はNaNを取り逃がします。有限の `-0.5` との厳密な `==` なら、ここではビット比較を別に導入する必要はありません。

3. **【実質】Dの引数ビット確認を「してよい」ではなく、一般入力を扱う関数の契約として確定してください。**  
   [計画28行](docs/ai/plans/2026-10-16-mv-p5j-constant-terms.md:28)。実際の更新経路では、`p5_max(.01,a[7])` は `a[7]` がNaNでも `.01` を返すため、`ev>=.01` の説明は成立します。`ev==cut==.01` でも同じビットです。  
   ただし低水準の `quantities` は任意の `t,cut` を受けます。`t<cut` や `t=NaN` では `t>cut?t:cut` は `t` と異なります。**各対数の実際の引数**と、`Lev` を作った入力を比較し、不一致なら元の `log` に戻す必要があります。数値の `==` は符号付きゼロを区別できず、NaN同士にも使えません。NaNは再利用せず元式に戻す契約が明確です。`disabled`／`t<=cut` の早期returnも保持してください。

4. **【実質】特殊入力の「未定義」の分類と、NaN出力の合否が未確定です。**  
   [計画41行](docs/ai/plans/2026-10-16-mv-p5j-constant-terms.md:41)。`log(0)` や `log1p(NaN)` の浮動小数点結果と、配列の範囲外アクセスは別です。[`interp`](prototypes/mv_electron/gpu/p5a0_common.h:49) はNaN入力で検索位置が0となり、`--j` 後に負の添字へ進み得ます。したがって、NaNを丸ごと `p5_collision`／`quantities` に渡す試験は安全ではありません。  
   Cの引数計算・分岐を独立して検査し、全関数比較は有効な入力に限定してください。「未定義なら戻った回数だけ確認」は全出力一致の代わりになりません。NaNの符号・payloadまで要求するのかも明記が必要です。`core.bits` はそれらも区別します。

5. **【実質】「元の式が残っていない」という静的テストは、必要な経路と矛盾します。**  
   [計画68行](docs/ai/plans/2026-10-16-mv-p5j-constant-terms.md:68)。Cのフォールバックには元式が必要です。Dも引数不一致時、および `sample_k` 内・制動放射後には元の対数計算が必要です。A・Bも下端 `x=.01/T` のprimitiveには残す必要があります。  
   「指定した呼出し位置だけ置換され、必要なフォールバックと非対象経路は残る」という検査に変更すべきです。primitive全体を定数化してはいけません。

6. **【実質】関門0の構成とカバレッジ条件が不足しています。**  
   CPU・T4とも**通常版と検査版の両方**を正式対象にしてください。P5iの既存 `gate0` 呼出しを踏襲するだけでは検査版だけになり得ます。また、A〜D各1カウントでは、Bの2種類、Dの3箇所、Dの非再利用経路を確認できません。  
   以下を個別に確認すべきです。

   - `cut` の直前・一致・直後、`disabled` の両値。
   - 各置換位置の通過と、C・Dのフォールバック。
   - 非正規数のうちCが成立するもの／成立しないもの、±0、±∞。
   - `.5-x<1e-7` が実際に真偽を切り替える隣接binary64入力。
   - `quantities` の4出力に加え、低水準関数の `idx`・`raw` 全要素。

   正常な輸送でCのフォールバックが0回でも問題ありません。特殊入力の関門0で通過を要求する形が適切です。

7. **【実質】P5iからの継承時に、比較先と指紋を明示的に更新する関門が必要です。**  
   [P5iのGPU駆動](prototypes/mv_electron/gpu/p5i_colab.py:22) の `baseline=True` はP5gです。コピー後に残すと、関門2・速度・地図の比較先が計画と異なります。P5iを比較先にしたことを検査してください。  
   また、[P5iのidentity](prototypes/mv_electron/gpu/p5i_core.py:28) の `generated` は配列配置情報で、端末で生成した対数値自体ではありません。P5jではK0〜K2と継承した対数配列の**実データのハッシュを、関門記録・再開時照合まで接続**する必要があります。通常版・検査版双方の構成と、関門0合格記録も後続関門から検証してください。

8. **【軽微】T4関門0失敗時の停止規定が曖昧です。**  
   [計画58行](docs/ai/plans/2026-10-16-mv-p5j-constant-terms.md:58) の「関門0不一致→GPUに進まない」はCPU側には適用できますが、T4側には適用できません。T4関門0失敗時は関門2・3・速度測定へ進まず、不採用として記録する、と分けてください。

9. **【参考】対象の対数に、追加必須の漏れは見当たりません。**  
   Dの3箇所は正しく特定されています。`p5i_table_rates` の `log(T/e0)`、GSの `log(T/ts[i])`、衝突阻止能のその他の対数、`sample_k` の `log(T/.01)` は `log(ev)` で代用できません。K1とK2も別々の元関数で生成すべきです。AではK0がゼロでも `-b*K0` を削除せず、Bでも項の結合・並べ替えを避けてください。
