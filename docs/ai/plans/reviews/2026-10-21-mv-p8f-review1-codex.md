**修正が必要な指摘**

1. **【実質】D5の加算順が正典と違い、鎖0のバイト一致を崩す。**

   [計画D5](/Users/oishifamily/Projects/viveMonte/docs/ai/plans/2026-10-21-mv-p8f-gpu-materials.md:65) は「付与ごとに100群へ直接足す」としていますが、正典は次の順です。

   `付与 → history_bins／hs／fine → 履歴終了時に群へ加算 → Pythonで縮約`

   `p8_max` も、群へ加算する前の `history_bins` から計算します。CPUにも履歴配列を持たせ、`p8_batches[b] += history_bins` と `add_clear` の順を再現してください。`brems[1]` は別に、正典どおり事象発生時に累積すればバイト比較できます。

2. **【実質】D2で再利用する `boundary` は積層に対応していない。**

   [既存C++の `p5_boundary`](/Users/oishifamily/Projects/viveMonte/prototypes/mv_electron/gpu/p5_kernel.h:298) は面位置が0・30 cmに固定されています。P8eの `boundary(z,w,region,faces)` の代替にはなりません。

   `p8f_boundary` を新設し、正典と同じ面配列・領域番号・ゼロ距離処理を実装する必要があります。各内部面と外面について、両方向、`w=0`、面上、面の直前直後を試験対象にしてください。

3. **【実質】「本番の旗だけ」と関門1bが両立していない。**

   関門1bが参照する既存テストは `binding_enabled=False, fluorescence_enabled=False` です。本番の旗だけを実装すると、この条件を再現できません。

   **試験専用の無効化経路を対象範囲に明記する**か、水の系統への接続試験を別の比較に変更してください。旧来の束を渡すだけでは、殻選択・緩和の乱数消費まで同じにはなりません。

4. **【実質】F10と関門0dには、乱数消費を変える枝と遷移の試験が不足している。**

   次を事前登録することを勧めます。

   | 対象 | 追加するケース |
   |---|---|
   | 殻選択 | 確率和ゼロ、累積確率ちょうど、最後の正確率要素へのフォールバック |
   | 緩和 | 非放射、殻4で即終了、線がCUT未満・ちょうど・直上、子空孔の連鎖 |
   | 制動放射 | 初回受理、複数回棄却、包絡超過で受理乱数を引かず終了 |
   | 境界 | 反転後の同じ面からの再通過、ゼロ距離、終端状態 |
   | 事象競合 | 境界→エネルギー→散乱→hard→brems→消滅の優先順位、`step+1e-13` の内外 |
   | 再開 | hard／bremsで親をスタックへ戻した後の率・時計・材料の復元 |

   とくにF8の「3回」を担保するには、**蛍光タグ付きのCUT未満光子を処理する試験**が必要です。「CUT未満の蛍光線」の緩和試験だけでは代用できません。

   既存の [境界・エネルギー・hard競合試験](/Users/oishifamily/Projects/viveMonte/prototypes/mv_electron/tests/test_p8e.py:768) は、そのまま比較条件の出発点になります。強制状態はCPU間だけでなく、少数をT4でも実行してください。

5. **【実質】0eの故障箇所と、検出に使う量が対応していない。**

   「`p8_batches` への加算を落とす」としても、正典の `p8_max` は加算前の履歴配列から計算されるため、値は変わりません。現状の条件では、その故障を `p8_max>1e-12` で検出できません。

   故障を分けてください。

   - 履歴内付与の欠落：履歴配列と `dep` の収支で拒否。
   - 群への加算欠落：履歴出力の再集計と群出力の比較で拒否。
   - 補充時の消し忘れ：**実際に出力する局所配列**と当該履歴の `dep` の収支で拒否。

   2bはbin差が報告扱いなので、消し忘れを拒否する収支条件を明示すると、故障検出が実装依存になりません。

6. **【実質】関門3の「届かない」という判断は、採用するSEMと違う計算に基づく。**

   [P6 `c4`](/Users/oishifamily/Projects/viveMonte/prototypes/mv_electron/gpu/p6_core.py:236) は、同じ種・履歴番号で作った**対応する外側バッチの差**からSEMを求めます。

   ```
   Δb = GPUのブロック線量b − CPUのブロック線量b
   SEM = std(Δb, ddof=1) / √100 / Dref
   ```

   計画の `0.757/√10×√2` は独立計算の見積もりです。同じPhilox履歴を使う比較ではCPU・GPUの共分散が効くため、これから「1,000万では届かない」とは結論できません。3,000万への増量も、SEM条件の緩和も、現時点では根拠不足です。

7. **【実質】判定Bへ `judge_batches` をそのまま使うと固定Drefが変わる。**

   [既存判定関数](/Users/oishifamily/Projects/viveMonte/prototypes/mv_electron/run_p8e.py:374) は、第2引数の参照線量からDrefを計算します。第2引数を保存MTにすると、EGS5由来の固定値ではなくなります。

   現物では、EGS5のDrefは **0.060387587985606006**、MTから同じ窓で計算した値は **0.06047850726023682** でした。

   凍結ファイルを変更せず、`block_statistics` と `classify_blocks` を再利用した薄いラッパーをP8f側に置き、A・BともEGS5の固定Drefを明示的に使ってください。

8. **【軽微】演算順の試験を `np.sum` だけに限定しない。**

   0bの方針は良いですが、行ごとの殻確率和、全体和、正規化後の確率和、`history_bins` の和、`touched_sum` は別々の演算です。また、補間の探索側、重複節点、整数乗・分数乗、`material_hard` の近接閾値分岐も対象になります。

- **【参考】** 基準v2の「差とSEMの二重閾値」は、統計的な同等性証明ではありません。ただし常設の採用基準なので、変更を要求する指摘にはしません。結論は「対象配置・19ブロックで採用基準に合格」としてください。
- **【参考】** P6の `c2_calls` は、全履歴の総乱数回数完全一致を要求していません。最初の診断地点での一致率99%以上を使います。「P6の規則をそのまま使う」の具体的な意味を記載すると誤解を防げます。
- **【参考】** 新しい境界・蛍光カウンタの履歴ごと完全一致は、P6より厳しい条件です。同じ模型でもCPU/GPUの丸め差で枝が変わる可能性はあります。厳格条件として採用すること自体は問題ありませんが、不一致が出たら即座に物理の違いと断定せず、最初の分岐を調べる扱いが適切です。
- **【参考】** スタック容量を実測最大の2倍とし、実行時あふれを必ず拒否する方針は、この試作の枠内で妥当です。1履歴約6 KBは採点配列だけの値で、粒子スタックや状態を含む総量ではありません。

**同じ目的をもっと単純に達成する具体案**

速度目標がないため、最初のP8fでは**P8eのループ構造を保った「1履歴を完走する共通C++関数」**を推奨します。

- `p8f_history(materials, geometry, rng, sink)` にP8eの本番ループを移す。P5jのフェーズ状態機械への変換は行わない。
- CPU鎖0は、MT状態を維持して順番に呼ぶ。履歴内集計と群への加算順、事象途中の `brems` 加算を正典どおり保持する。
- GPUは各スレッドが履歴を完走し、次の履歴番号を取得する。Philoxは履歴番号で初期化する。
- CPU Philoxも同じ関数・履歴出力形式を使い、鎖2の参照を作る。
- 物理関数、採点、群への縮約を分ける。検証用の出力モードは変えても、輸送ループは共通にする。

これなら、物理移植と状態機械への変換を同時に検証せずに済みます。履歴間の配列初期化試験は必要ですが、フェーズ別の保持状態・中断・補充の検証が減ります。P5k F相当のスケジューリングは、P8fが通った後の速度改善計画にできます。速度がどの程度変わるかは測定事項です。

既存案を維持する場合でも、**MT用とPhilox用で物理遷移は一本にし、乱数初期化と出力先だけを切り替える**構造にしてください。

**§7への意見と、計画が問いに答えられる範囲**

関門3は、まず **1,000万履歴・100外側バッチ、差≤0.5%、対応差のSEM≤0.2%を維持**する案を勧めます。CPU/GPUで種・履歴範囲を固定し、計算時間の事前見積もりを行ってください。精度不足時は、その事実を記録して追加計算を判断します。現在の独立SEM見積もりだけを理由に、0.35%へ緩和したり3,000万へ増やしたりする必要はありません。

本番は、既存基準 `.0033` に合わせた**約2,000万履歴**が説明しやすい案です。1,900万も予測上は条件内なので、費用との判断で選べます。
