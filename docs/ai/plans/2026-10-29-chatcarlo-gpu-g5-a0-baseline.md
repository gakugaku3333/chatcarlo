**新しく作るもの**（すべて `docs/validation/gpu/g5/` に置く）:

- 手元の起動役: `colab` の呼び出しに時間の上限をつけ、heartbeat を書く。

**手順**（すべて 1 つの T4 セッションの中で行う）:

1. **準備**: 6 構成のオブジェクトをすべて作り、コンパイルを終える。各構成の構築・コンパイルの時間は、別の欄に記録する（報告だけ）。
2. **温め**: 各「構成 × 大きさ」で 1 回だけ実行して捨てる。捨てた回の時間も記録するが、コンパイルを含む時間としては扱わない。
3. **有効な 3 巡**: 1 巡で全部の「構成 × 大きさ」を 1 回ずつ回す。巡ごとに開始の位置を 2 つずつずらす（順番は `a0_configs.json` に事前に書く）。大きさは、本番の 1 回の大きさと 10 万履歴（記録並び用、報告だけ）。
4. **健全性**: 各回の後、計時の区間の外で検査する。
   - P7: `core.require(h.health(r), ...)`（既存の計時と同じ。`p7_colab.py:181`）
   - P8g-2: `check_visits()` と `run_health()`（`p8g2_colab.py:138`）
   - 診断: `Core.run()` の既存の検証（有限値・形）と、エネルギーの収支

   結果を JSON に残してから出力を捨てる。1 回でも落ちたら、その構成の基準は採らない。
5. **記録する時間**:
   - `kernel_s`（核の時間。許容の比の計算に使う）
   - `call_s`（呼び出し全体）
   - µs/履歴
6. **資源**: 各核について次を記録する。
   - CuPy の `RawKernel` の属性から読む値: レジスター数・共有メモリー・最大スレッド数
   - T4（sm_75）の割り当ての粒度で手で計算した SM あたりのブロック数と、CUDA の occupancy API の値を並べる
7. **ncu**: 通常の計時をすべて終えてから、別のプロセスで各核 1 回ずつ `--set full` を取る。各回で次を保存する。
   - 構成、起動の条件、対象のカーネル名
   - 取得のコマンド、終了コード
   - 生のファイルの SHA256

   取れなかった核は「未取得」と書く。ncu は報告だけで、合否には使わない。

**許容の比の決め方**（測る前に固定）:

1. 各構成で、本番の大きさの有効な 3 回の `kernel_s` から、(最大 − 最小) / 中央値 を計算する。その最大を s とし、どの構成のものかも書く。
2. 許容の比は次のとおり。
   - s ≤ 0.025 なら **1.05**
   - 0.025 < s ≤ 0.05 なら **1 + 2s**（最大 1.10）
   - **s > 0.05 なら基準は未確定**とし、その構成だけ新しいセッションで 6 構成すべてを測り直す。2 回目も s > 0.05 なら、止めて報告する（許容を広げすぎて遅れを見逃すのを防ぐ）
3. 決めた比は `A0.md` に書き、A1〜A3 で変えない。

## 5. 実装方針

- **既存のクラスをそのまま使う**: P7・P8g-2・診断の core を、各段の本番と同じ起動の形で使う。速くするための設定の変更はしない（A0 は今の本番の速さの基準なので）。P7・P8g-2 は既存の計時の値を読み、計時の処理を新しく写さない。
- **診断だけ薄い委譲を使う**: 既存の計時（`elapsed_s`）は `Core.run()` 全体で、配列の準備・転送・観測のハッシュ・同期・回収・検証を含み、核だけの時間ではない（`colab_driver.py:137`、`core.py:124`）。そこで native 呼び出しだけを包む。
- **束**:
  - 治療の核（P7・P8g-2）の束は、既存の export の手順で作る（`run_p7 export`、`p8g2` の束）。既存の束が `~/.cache` か Drive にあれば、それを使う。そのときは manifest のハッシュを照合する。
  - 診断の束は `chatcarlo.gpu.bundle.create` で作る。VM に xraylib・SpekPy が無い前提は今の G1 と同じで、線源はホストで抽選して束に入れる。
- **VM での実行**: 計測は 1 つのジョブとして VM で `nohup` で回す。構成ごとの結果をすぐ JSON に書き、見張りのたびに回収する。終わりの目印は `G5A0_DONE`。
