## 1. やり方（骨子）

**区画の表＋短い探索**（各表について）:
1. 手元（Python）で、比較の値の範囲を等間隔の区画に分け、区画ごとに「探す範囲の始まりと終わりの添え字」を整数の表として作る。範囲は、その区画に入り得るどの入力に対しても、本来の `lower_bound` の答えを含むように取る。区画の境目で端末の計算が隣の区画にずれる場合と、端末の `log` が手元と最後の1ビット違う場合に備えて、**隣の区画の分と前後1つの余裕**を加える。
2. 端末では、区画の番号を計算し、その範囲の中だけで**元と同じ比較の式**（`a[m]<x`、`log(es[m])<x`）で二分探索する。
3. 返る添え字が元と同じなら、その後の演算はすべて元と同じなので、結果はビット単位で同じになる。**手元で計算した `log(es)` の値を比較に使わない**（P5a0 で、端末と手元の `log` は最後のビットが違うことがあると分かっている）。
- `ts` は、式で添え字を推定し、元の比較で前後を直す形でもよい（区画の表と同じ扱いにしてもよい。詳細で決める）。
- `p5_pair_interp` の線形の数え上げ: しきい値ごとの `start` を手元で同じ比較（`es[start]<=th`）で求めて渡す。
- `ks`（9点）は、効果が小さければ対象から外してよい（詳細で、呼び出しの回数を数えて決める）。

**ファイル**: 新規 `p5h_*`。P5g の遷移の関数と同じ並びのまま、探索の部分だけを新しい関数に替えたコピーを持つ。**探索以外の式は、字句まで同じに写す**（式の書き方を整えない。整えると丸めが変わる）。

## 6. 詳細（1巡目の反映。§1〜§5 と食い違うときは本節が優先）

**添え字の契約（指摘1・2・3）**: 区画の表は「答えを含む保証」ではなく**候補の範囲の予測**として使う。元の探索の範囲を `[s,n)`（`p5_pair_interp` は `s=start`、他は `s=0`）、比較の値を `A(i)`（生の格子の値、または `pes` では**端末で計算した** `log(es[i])`）、候補を `[L,H)` とし、端末で次を確かめる。
```text
s ≤ L ≤ H ≤ n
L == s または A(L-1) < x
H == n または !(A(H) < x)
```
成り立てば `[L,H)` の中で元と同じ二分探索をし、その答えは `[s,n)` の `lower_bound` と同じになる（`A` が減らない列なので）。成り立たなければ**元の全範囲の探索に戻す**。区画の丸めや手元と端末の `log` の違いは、速さにしか効かない。
- 返すのは `lower_bound` の生の添え字（`0`〜`n`、同じ値が並ぶときは先頭）。その後の `-1`・端の切り詰め・同値の判定・範囲外の処理は元の順番のまま。`H` は排他的な終わり。
- `x` が有限でない、または区画の範囲の外のときは、整数に変換する**前に**元の探索に戻す（NaN では元は `s` を返す。元の `interp` が定義されない入力まで出力の一致は求めない。探索関数の添え字の一致は求める）。
- 表を作るとき、格子が有限・減らない・必要な点数があることを確かめ、満たさなければ止める。
- 対象: `us`、`brems_e`、`rates`、`loget`、`pes`（`p5_log_interp`・`p5_pair_interp`）、`ts`。`ks`（9点）は元のまま。`pair` の `start` は手元で同じ比較で求めて渡す（`es[start]<=th`、binary64 の同じ値）。
- 前の添え字から探す案（指摘7）は今回は採らない。方式を1つにして関門を単純に保つ。効果が足りなければ次の計画で測る。

**関門の追加（指摘4・5）**
- 関門0 を CPU と **T4 の両方**で行う。端末の核から新旧の探索関数を直接呼ぶ。入力: 全格子点とその `nextafter` の両隣、同じ値が並ぶ列の先頭と末尾、答えが `0`・`n`・`start` になる場合、`pes` では端末で計算した `log(es[i])` とその両隣、区画の境目とその両隣、NaN・±∞・±0・非常に大きい値・対数が取れない値、**わざと狭くした候補の表**（戻す経路が実際に働くこと）、乱数 100万個（補助）。
- 検査のビルド（全部の表引きで新旧の添え字を比べる）は、比較を補間より前に置き、不一致を数えて最後にホストが確かめる（ワープの一部だけを途中で `return` させない）。検査のビルドでも出力の一致を確かめる。本番のビルドのビット一致の関門はそのまま残す。
- 判定の記録の指紋に、**作った区画の表**・元の格子・`pair` の `start`・コンパイルの指定・計算のソースを入れる（作る Python は道具なので入れない。作られたものは入れる）。

**速さの報告（指摘6）**: ×1.255・×1.136 は命令の数からの参考の試算で、時間の上限ではない。交互の測定に加えて、探索の行の**命令の絶対数**、参加レーン、レジスタ・ローカルメモリの量を並べる。

## 7. 2巡目の反映（§6 と食い違うときは本節が優先）

**呼び出しの経路（指摘1）**: 探索の本体は `p5g_kernel.h` ではなく、凍結した `p5_kernel.h`・`p5a0_common.h` の関数の中にある（`p5_coefficients`→`p5_log_interp`/`p5_pair_interp`、`p5_table_rates`、`p5_gs_mu_cached`→`p5_bracket`/`lower_bound`、`quantities`（制動放射）、密度の `interp`、ほか P5g から到達するもの）。そこで:
- 探索を含む関数と、それを呼ぶ関数を、P5g の核から探索に届くまで**呼び出しの経路ごとにすべて** `p5h_` の名前で新しいファイルにコピーする。変えてよいのは、名前・区画の表を渡す引数の追加・探索の1行だけ。凍結のヘッダーは読み込んでよいが、探索を含む旧関数を P5h の経路から呼ばない。
- 手元で、P5h の CPU ビルドのソースから旧関数（`lower_bound`・`interp`・`p5_log_interp`・`p5_pair_interp`・`p5_table_rates`・`p5_bracket`・`p5_gs_mu_cached`・`quantities` の旧名）への呼び出しが P5h の経路に残っていないことをテストで確かめる（`ks` の `p5_bracket` のように、意図して元のまま残すものは一覧で明示）。
- 検査のビルドで、表ごと・呼び出しの場所ごとに「新しい探索を通った回数」と「元の探索に戻した回数」を数え、対象のすべての場所で通った回数が 0 でないことを関門0〜2の条件にする（数は報告する）。
- CPU は `p5h_cpu.cpp` が `p5h_kernel.h` を、GPU は `p5h_gpu.cu` が同じヘッダーを読み込む（P5g と同じ組み立て）。

**行の情報付きのビルド（指摘2）**: P5g と P5h のそれぞれで、行の情報のありとなしの出力・SASS・資源を比べる（P5f-1 の V0 と同じ手順）。同じと示せなければ、地図は「行の情報付きの構成の測定」と書く。採否の条件にはしない。
