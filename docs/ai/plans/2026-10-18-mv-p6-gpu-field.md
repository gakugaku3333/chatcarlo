## 1. 目的（この計画が答える問い）

1. P5k F（GPU の合格構成、板の深さ線量だけ）を、P3b の照射野（発散する 10×10 cm² の線源、全粒子の xyz、領域への線分按分）まで広げられるか。
2. 広げた GPU の核が P3b の Numba の核と同じ計算をしていることを、P5 と同じ検証の鎖で示せるか。
3. GPU の計算で P3b-3 の 11 量（事前に決めた量と許容）が EGS5 と合うか。照合には保存済みの EGS5 の結果を使い、EGS5 を新しく回さない。
4. 速度は報告だけ（目標値は置かない）。

物理は変えない（カットオフ 10 keV、陽電子専用の物理なし、制動放射の光子を運ぶ、ステップの規則は P3s）。

## 2. 中心になる設計の判断

ユーザーの決定（2026-10-18）: D1 は案A、鎖1 は「兼ねる」。

### D1. どの核から広げるか

- **案A（推奨）**: P5j の遷移を写した新しいファイル（`p6_*`）に、発散線源（スペクトルの抽選のあと x、y の順に乱数を引く。P3b どおり）と、付与の箇所での採点の呼び出しだけを足す。既存の xyz 処理と物理の関数は再利用する。根拠は行数ではなく「線源・付与箇所・出力」の対応表（詳細計画で作る）。場なしでは P5k F とビットまで一致させる。
  - 利点: F の補充の方式を引き継ぐ（速度は引き継げない: 領域の配列は詰めても 1 履歴 14,688 バイト。実測する）。
  - 鎖0（MT）用には、P5j の CPU 入口（`p5j_cpu.cpp`）と同じく **MT の状態を持ったまま履歴を番号順に完走させる逐次の駆動**を別に置く。F の駆動は Philox 側だけで使う（F は履歴ごとに `rng_init` を呼ぶので MT では使えない）。
- 案B: P5a のような 1 履歴ずつ回す核で先に P3b を移し、そのあとで状態機械にする。二度手間になるので推奨しない。

### D2. 検証の鎖（P5 と同じ型）

- 鎖0（ビット）: C++ の CPU 版を MT19937 で回し、**保存済みの P3b-3 本番のバッチをバイトまで再現する**（P5a が P3r の本番バッチを再現したのと同じ方法）。全 15+6 個の出力すべて。数バッチ（例: 0 と 2）で行う。場なしでは P5k F の関門（保存済みの 100 バッチの Philox）とビットまで一致することも確かめる。
- 鎖1（統計）: C++ の CPU 版の Philox ↔ MT。違いは乱数だけ。
- 鎖2（履歴ごと）: C++ の CPU 版 ↔ T4 の GPU、同じ（種、履歴番号）で履歴ごとに比べる（P5 の関門2・3と同じ）。
- 最後: T4 で Philox 4,600 万履歴を回し、P3b-3 の 11 量で保存済みの EGS5 と比べる。判定の規則・許容・精度の条件は P3b-3 のものをそのまま使う（新しく決めない）。

鎖1 の扱い（ユーザーの判断）:
- **兼ねる（推奨）**: 最後の GPU の 4,600 万履歴を、保存済みの試作（MT）と保存済みの EGS5 の両方と比べる。計算は 1 回。ただしこの比較は「乱数の変更だけ」ではなく **CPU→GPU の移植全体の比較**と位置づけ、乱数の変更を分けて確かめたとは結論しない。先に領域つきの鎖2 を通す。
- 分ける: CPU の Philox で 4,600 万履歴を別に回す（P3b の Numba は M3 の 2 プロセスで 7,659 s。C++ は板で Numba の約半分だった（P5d: 122 対 257 µs）ので、約 1 時間の見込み。詳細計画で実測）。原因を切り分けやすいが計算が増える。

### D3. 採点の置き場

- 領域を切り出して付与量を求める関数は CPU と GPU で共通にし、足す先だけを切り替える。
- CPU の鎖0: P3b と同じく付与ごとに内部の 100 群へ直接加算し、最後に同じ順で縮約する（履歴内でまとめると加算の括り方が変わり、バイトで一致しない）。
- GPU: 履歴内の配列に足して履歴の終わりに atomic で合わせる（P5b の方式）か、付与ごとに直接 atomic で足すか（状態は小さくなるが atomic が増える）。詳細計画で決める。同じ付与列を両方へ流す小試験で、切り替えが正しいことを確かめる。
- P3b の `deposits`/`sources`（1 回ごとの付与の記録）は検査用。CPU の検査版だけに置き、GPU の本番版には置かない。

## 3. 事前登録の判定（骨子の段階）

- 鎖0: 指定したバッチで、全出力が保存済みのバッチとバイトまで一致する（`brems[1]` は P5b の注記のとおり、計算した範囲で一致すればよい）。
- 場なしの回帰: P5k F の関門1と同じ比較がビットまで一致する。
- 鎖2: P5 の関門2・3と同じ規則（履歴ごとの対の差で合否、一致した割合は報告だけ）を、**追加したすべての領域出力**（平均する前の符号つき・x/y 別の側方分布を含む）に広げる。atomic の集計との照合、非有限値の検査も同じ。11 量は方向を平均するので、左右や x/y の取り違えは鎖2 で落とす。
- 採点器の決定論的な試験: 境界の上、負の方向、箱の横断、点の付与。故障を入れた検出: 側方のビンをずらす、領域の付与を落とす、F の補充で配列を消し忘れる。
- 最後の照合: P3b-3 の 11 量、同じ許容（線量 1%、位置 0.1 cm）、同じ精度の条件（SEM 1/3%、0.033 cm）、同じ固定 `Dref`。別の乱数なので精度の条件に届く保証はない。届かなければ「統計不足」と記録し、履歴数を足すかどうかはユーザーが決める（基準は動かさない）。

## 7. 詳細: 作るもの

すべて新しいファイル。既存のファイルは編集しない。

1. `gpu/p6_field.h`: P3b の `clip`・`score_box_point`・`score_box_bins`・`deposit_segment`・`deposit_point` の C++ 版（演算の順を写す。`np.floor` → `floor`、`np.all(p0==p1)` → 3 成分の `==`）。足す先は「シンク」で切り替える:
   - 群シンク: `region_scores[b][j][i]` に直接足す（鎖0 用。P3b と同じ）。
   - 局所シンク: 1 履歴の局所の配列（1,836 個）に足す（鎖2 と GPU 用）。
   - どちらも `region_sums[15]` を足し、履歴の終わりに P3b と同じ判定（板の領域 j=2 は `abs(sum−dep)`、ほかは `max(0,sum−dep)`、入射エネルギーの 1e-9 を超えたら `region_ledger[j]` を 1 増やす）をする。`region_ledger` が 0 でないバッチは健全でないとして、保存・解析の入口で拒否する。検査用に付与の記録（h, kind, p0, p1, loss。P3b の `records` と同じ列）を任意で残す。
2. `gpu/p6_kernel.h`: `p5j_kernel.h` を `#include` し、`P5jState` を P6 の状態のメンバーとして持つ。初期化は `p5j_init` のあとに発散線源を設定する薄い関数（初期化のトレースは線源の乱数を引いたあとに記録）、終わりは `p5j_end` を再利用し、`p5j_finish` には領域の収支の判定を添える。写すのは主に `particle` と `charged`（付与の 5 か所を含む）。付与の箇所ごとに、旧来の深さの採点の**直前**か**直後**か、P3b の順を写す（P3b では領域の付与が旧来の採点より先）。照射野と領域が無い設定では、P5j と同じ乱数の消費・同じ演算になる。
   - 対応表（P3b の行 ↔ P5j の行 ↔ p6 の行）を `docs/validation/mv/p6/MAPPING.md` に書く。
3. `gpu/p6_cpu.cpp`: CPU の入口。(a) MT・逐次・群シンク（鎖0）、(b) Philox・履歴ごと・局所シンク（鎖2 の CPU 側）、(c) 付与の記録、(d) 1 履歴の追跡（P5j の `p5j_trace` と同じ形）。
4. `gpu/p6_gpu.cu`: P5k F の駆動を写した GPU の駆動（`p5k_driver.h` を `#include` できなければ `p6_driver.h` に写す）。スレッドの局所の出力に領域の配列を足し、履歴の終わりに atomic で全体の 100 群へ合わせる。
5. `gpu/p6.py`、`gpu/p6_core.py`、`gpu/p6_colab.py`、`gpu/p6_colab.ipynb`: 手元の関門・Drive の束・Colab の「すべてのセルを実行」1 回・解析の入口。P5k の形を写すが、駆動は F だけにし、Q 系・最速候補の自動選択・ncu の処理は引き継がない。
   - 乱数と保存の契約（関門3・本番・再開で同じ定義を使う）: 種は引数で渡す（`core.SEED` を直接使わない）。本番は種 20291764、外側のバッチ b の履歴は `[460000·b, 460000·(b+1))`。関門3 は種 `core.SEED` 相当、`[100000·b, 100000·(b+1))`。各起動の中の 100 群は縮約して外側の 1 バッチとして保存する（`analysis_p3b3.dose` の前提）。
6. `tests/test_p6_*.py`: 下の関門の手元の部分。

GPU の足し方は「履歴内の局所の配列 → 履歴の終わりに atomic」に決める（P5b と同じで、履歴ごとの比較がそのまま使える）。付与ごとの直接の atomic は採らない（理由: 鎖2 の履歴ごとの比較の作りが変わる。速度は報告だけなので局所の配列の重さは問題にしない）。

## 8. 詳細: 関門（すべて事前登録。順に通す）

共通: 故障を入れたビルドの検査は、**正常なビルドが同じ検査に合格したあとで**、故障のビルドが数値の比較で失敗することを求める。ビルドの失敗や入力の不一致は「検出した」に数えない。

関門0（手元、決定論）
- 0a 採点器: `scoring_p3b` の関数と C++ 版を、乱数の入力 10 万個と端の入力（境界の上ちょうど、負の向き、箱を横断、軸に平行、`p0==p1`、箱の外の同じ側）で比べ、戻り値と配列がバイトで一致。
- 0b シンク: 同じ付与の列を群シンクと局所シンクに流す。`region_sums` はバイトで一致。局所を足した値と群の値は、**各ビンごとに** |差| ≤ 足した履歴数 × 2^-52 × そのビンの絶対値の和（`core.c3` の式）。
- 0c 付与の記録: C++ MT（鎖0 の経路）と P3b の Numba（`record_deposits` あり）を同じ種・2,000 履歴で回し、付与の記録と線源の記録がバイトで一致。あわせて付与の記録のあふれ 0、線源の記録 2,000 件、線源のあふれ 0。付与の 5 か所それぞれを通ったことを、箇所の番号を付けた C++ 側の記録で示す（5 か所すべてが 1 回以上）。
- 0d 収支の検査: 付与を 1 か所だけ領域から落としたビルドで、`region_ledger` が 0 でなくなり、健全性の検査が拒否すること。
- 0e 失敗と再利用: P5k と同じ小さい `maxsteps` の試験（失敗した履歴の直後に同じスロットを使う）を、領域の状態を含めて行う。

関門1（手元、鎖0）
- 1a 保存バッチの再現: 保存済みの P3b-3 本番のバッチ 0、2、99（各 460,000 履歴、種は保存ファイルの値）を C++ MT で回し、`batch_kernels_p3b.reduce` と同じ縮約をして、21 個の出力すべてがバイトで一致（`brems` も含む。逐次・群シンクで P3b と同じ加算の順なので例外を置かない。§3 の `brems[1]` の例外は GPU の集計にだけ当てる）。入力（表・スペクトル・コード）のハッシュは保存時の記録と照合してから回す。
- 1b 場なしの回帰（CPU）: 照射野と領域を切った p6 の CPU（Philox）が、P5j の CPU と同じ種で 2 万履歴、全出力でバイトで一致（骨子の「P5k F の関門1 と同じ比較」は、場なしの CPU の経路が P5j と同じであることの確認として 2 万履歴に縮める。GPU 側は 2e）。
- 1c 故障の検出: (i) 側方分布のビンを 1 つずらす、(ii) 付与の 1 か所を落とす、(iii) x と y の乱数を入れ替える。比較の相手は、同じ種で P3b を 2 万履歴回した参照（このために作る）。正常なビルドが一致したうえで、3 つの故障がそれぞれ失敗すること。

参照の生成（手元）
- 関門3 用の CPU Philox の参照: 照射野ありで 10 万履歴 × 100 バッチ（計 1,000 万。M3 の 2 プロセスで約 20 分の見込み = 160 µs × 1,000 万 ÷ 2）と、関門2 用の 2 万履歴の履歴ごとの出力。Drive の束に入れる。

関門2（T4、鎖2）
- 2a 履歴ごと: 同じ（種、履歴番号）で CPU（Philox・局所シンク）と GPU を 2 万履歴。`core.c2` の規則をそのまま使う（健全性・線源・乱数の呼び出しが合否、ビンの対差は報告だけ）。健全性には領域の収支を加える。報告するビンには領域の 15 個すべて（平均する前の、符号つき・x/y 別）を含める。
- 2b 補充の経路: 総スロット数より多い履歴（少ないブロックで総スロット数の 3 倍）を流し、2a と同じ比較。故障 (iv) 補充で領域の配列を消し忘れる、のビルドが 2b で失敗すること。
- 2c 集計: atomic で合わせた 100 群と、履歴ごとの出力を足した値を、`core.c3` の式を領域の各要素に広げて比べる。非有限の値が 0。
- 2d GPU の採点器（決定論）: 付与の位置と先が既知の点・線分の組（0a の端の入力を含む）を GPU の採点器に流し、CPU の結果とバイトで一致（採点器は四則と `floor` だけで、`--fmad=false`）。GPU 側だけに入れた故障 (v) ビンずらし、(vi) 付与の欠落、(vii) 軸または符号の入れ替え、がそれぞれ失敗すること。
- 2e 場なしの回帰（GPU）: 照射野と領域を切った p6 の GPU と P5k F の GPU を、同じ（種、履歴番号）で 2 万履歴、全項目ビットで比べる（P5k の関門2 と同じ比較）。

関門3（T4、規模）
- GPU で参照と同じ 10 万履歴 × 100 バッチを回し、`core.c4` の規則（平均の差 ≤ 0.5%、SEM ≤ 0.2%、`Dref` 比）を、深い 5 ブロック（旧来の深さ）に加えて、直方体の 5 cm ブロック（5〜30 cm）と側方分布の中央（±4 cm）の平均（5/10/20 cm）に当てる。領域の線量への換算と `Dref` は `analysis_p3b3` のものを使う（体積で割る換算、pilot lock の固定 `Dref`）。

本番（T4）
- 4,600 万履歴、外側 100 バッチ、種 20291764、範囲は §7 の契約。GPU の Philox。
- 判定 A（主）: 保存済みの EGS5（`docs/validation/mv/p3b/egs5/main_egs/result.npz`）と P3b-3 の 11 量・許容・精度の条件・固定 `Dref`。
- 判定 B（鎖1 を兼ねる）: 保存済みの P3b-3 の試作（MT、100 バッチ）と同じ 11 量・同じ規則。CPU→GPU の移植全体の比較と記す。
- P6 の合格は A と B の両方が合格。どちらかの精度の条件が届かなければ「統計不足」と記録し、履歴数の追加はユーザーが決める。
- 全バッチの `region_ledger` が 0 であること（0 でなければ判定しない）。
- 判定の入口 `gpu/p6.py analyse` は `analysis_p3b3.py` の関数を再利用し、判定の前に入力（両方の保存データのハッシュ、履歴数、種、範囲、設定）を照合する。判定のコードは Claude が書く場合、判定を出す前に Codex のレビューを通す。
- 報告だけ: 速度（同じセッションで場なしの P5k F と交互に測る、µs/履歴）、ビルドアップ 0–2 cm、20–80% の幅、対称性（P3b-3 と同じ方法）。

## 追補1（2026-10-18、関門0b の停止を受けて。線量の比較の値はまだ一つも出ていない時点）

- 事実: 0b で 17 ビンが上限を超えた（最大の差 5.3e-15 MeV、321 履歴・20,000 付与・100 群、`docs/validation/mv/p6/sinks_diagnostic.json`）。`region_sums` はバイトで一致。
- 原因: 計画の式の誤り（Claude）。丸めの誤差は**加算の回数**で決まる。群シンクは付与ごとに足す（群の中の付与の数だけ加算）ので、`core.c3` の「群の中の履歴数」を当てたのが誤り。m 個の和の丸めの誤差は 2 通りの順の差でも (m−1)·2^-52·Σ|x| 以下に収まる。
- 変更: 0b と 2c の領域の要素の上限を「**そのビンに群の中で加えた付与の数** × 2^-52 × そのビンの絶対値の和」にする（2c は GPU の局所シンク→atomic なので、付与の数 + 群の中の履歴数）。旧来の出力の 2c は `core.c3` のまま。それ以外の関門・判定は変えない。
- 失敗した入力（種 2026101801）は同じまま、新しい上限で再判定する。

## 追補2（2026-10-18、関門0c の停止を受けて。線量の比較の値はまだ出ていない）

- 事実: 0c の 2,000 履歴で、付与の箇所 1〜5 の件数は 2 / 3,641 / 1,314,408 / 21,004 / **0**。付与の記録（1,339,055 件）と線源の記録は Numba と C++ でバイトで一致、あふれ 0。
- 原因: 計画の条件の誤り（Claude）。箇所5（P3b 415 行、実エネルギーの終点）は、ステップが残りの運動エネルギーで決まり、エネルギーのヒンジ（箇所4）より先に来たときだけ通る。まれな枝で、2,000 履歴で通る保証はない。Numba の側でも 0 件なので、移植の誤りではない。
- 変更: 0c の通過の条件は箇所 1〜4 が 1 回以上。箇所5 は (a) 関門1a の 3 バッチ（計 138 万履歴）で C++ の箇所ごとの件数を報告し、(b) 件数によらず、状態を固定して箇所5 を必ず通る小試験（P3b の `source_state` で荷電粒子を与える）で、Numba と C++ の付与の記録がバイトで一致することを 0c に加える。
- ほかの関門・判定は変えない。
