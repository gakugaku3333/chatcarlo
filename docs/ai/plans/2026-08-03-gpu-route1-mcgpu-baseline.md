## この計画の位置づけ

研究テーマ「モンテカルロ計算の高速化可能性の探索」の第一歩。EGS5の枠内の上限
（-O2 +8%、独立seed 8プロセス並列5.4x、RNG置換で単スレッド1.71x → 累積~10x、
2026-08-03セッションで実測済み）は把握済みであり、その先の最大レバーである
GPU化の**相場観を、自作を始める前に既存コードの実測1点で確定させる**。

- 本計画は測定であり、リポジトリの輸送コードには一切手を入れない。
- 後続の路線2（`kernel.py`のCUDA移植）を計画するかどうかは、本計画の実測値を
  見てから判断する。**本計画の結果が「GPUの上積みは小さい」であれば路線2を
  起こさない**——それも正しい結果として記録する。
- 散乱線補正ロードマップとは独立のワークストリーム（成果は将来合流し得るが、
  本計画はロードマップのPhaseゲートに関与しない）。

## 目的（1〜3行）

診断領域の光子輸送MCが、無料枠のGPU（Colab T4）で実際に何 histories/s 出るかを、
既存のEGS5/ChatCarlo実測と**同一シナリオ・同一観測量**で測り、3コード比較
（確立CPU参照 / 最適化CPU / GPU）の実測1点を得る。

## 使用コードと選定理由

**MC-GPU v1.3**（Badal & Badano, FDA/DIDSR公開のCUDA光子輸送コード。診断X線
イメージング用、光子限定・検出器像タリー・一次/散乱弁別あり）を**主測定**として
採用する（2026-08-03、ユーザー判断により「自作の最小CUDAカーネルを主測定にする」
代替案は不採用と確定）。選定理由:

- 無償公開・査読論文あり・診断領域光子限定という土俵が本プロジェクトと同一
- 検証論文が存在するので「自作カーネルの検証」という荷物を背負わずに相場観が取れる
  （Codexレビューが指摘した代替案はこの利点を失う代わりにビルド失敗リスクを
  ゼロにするトレードオフだったが、既成コードでの実測という当初の狙いを優先する）

**重大なリスク（Codexレビューで判明・実装前に必ずP1で解消する）**: MC-GPU公式
リポジトリ自身が「現行CUDAでは関数名変更によりoriginal codeのコンパイル問題がある」
と明記しており、配布済みビルド例は`compute_20/sm_20`・`compute_30/sm_30`を指定
している。T4はcompute capability 7.5で、CUDA 12系はcompute capability 3.0/3.2を
サポート対象外にしているため、**配布物そのままのMakefile／コマンドでは高確率で
ビルド失敗する**。

**P1の分岐判定（事前登録・後から動かさない）**:
1. `-arch=sm_75`へのビルド設定差し替え（ソース本体は無改変）だけでビルド成功
   → 続行（「MC-GPU本体を改造しない」の範囲内）
2. 現行CUDA API対応のソース修正（関数名変更等）が必要
   → **本計画は不合格として終了**。修正版を正式な測定対象にするかどうかは
   別途の新規計画とする（配布元・commit・差分・検証方法をその計画で固定する。
   本計画のスコープでは行わない）
3. （2の一種として）互換パッチを当てて本計画のまま続行する、という選択肢は
   **取らない**——「本体を改造しない」という対象範囲の制約と衝突するため

**追記（2026-08-04、実行時に判明した未登録の分岐）**: 実際のColab実行（T4、CUDA 12.8）で
`-arch=sm_75`ビルド自体は正しく試行されたが（`source_unchanged: true`）、失敗理由は
事前登録した分岐1・2のどちらでもなかった。エラーは`fatal error: helper_functions.h:
No such file or directory`——MC-GPU本体のコードではなく、**NVIDIA公式のCUDA Samples
（別リポジトリ`NVIDIA/cuda-samples`）が提供する第三者ヘッダ**が見つからないだけだった
（MC-GPU v1.3は2012年当時、CUDA ToolkitにCUDA Samplesが同梱されていた前提で書かれており、
現在のCUDA 12系ではSamplesは別配布になっている）。

この失敗様態は事前登録した「MC-GPU自身のCUDA API不整合」とは性質が異なり
（MC-GPU本体の書き換えは一切不要）、計画は想定していなかった。**ユーザーに確認の上**、
以下の対応を追加の分岐4として採用する:

4. ビルド失敗の原因が`helper_functions.h`等、MC-GPU本体ではない第三者ヘッダの不足で
   ある場合に限り、NVIDIA公式`cuda-samples`リポジトリの`Common/`を`--depth 1`で取得し、
   `-I`パスに追加して**1回だけ**再ビルドを試みる。MC-GPU本体の`.cu`/`.h`ファイルの
   ハッシュ一致チェック（分岐1と同じ機構）は継続して課し、これが崩れれば
   （＝本体への書き換えが実は必要だった場合）分岐2の不合格終了に合流する。
   `cuda-samples`側はこの依存自体が計画時点で想定外だったため事前にcommitを
   固定できず、**実際に取得できたcommit SHAを事後的にstate.json/RESULTS.mdへ記録**
   することで再現性を担保する（MC-GPU側のcommit固定という原則とは扱いが異なる点を
   明示する）。

**追記2（2026-08-04、より根深い問題が判明——リポジトリ切り替え）**: 追記1のビルド
分岐判定を通過した後、P1の「配布サンプルが実行できること」ゲートで別の失敗が発生した:

```
!!init_energy_spectrum ERROR!! Error trying to read the energy spectrum input file "../90kVp_4.0mmAl.spc".
```

原因を`DIDSR/MCGPU`リポジトリの実物（GitHub API経由でツリー一覧を取得）で確認したところ、
**このリポジトリにはソースコードのみが含まれており、README自身が言及している
サンプルデータ（スペクトルファイル・材料ファイル・ボクセルファントム）が一切存在しない**
ことが判明した。2012年のGoogle Code配布当時は同梱されていたデータが、GitHubへの移管時に
落ちたとみられる。

**さらに、この時点で route1_mcgpu_colab.ipynb 自身の実装ミスも発覚した**（Claudeが実物を
確認せず作成した箇所）: 材料ファイル名`materials/water__5-120keV.mcgpu.gz`等は実在しない
架空のファイル名だった。ボクセルファイルのヘッダーキーワードは正しくは
`[SECTION VOXELS HEADER v.2008-04-13]`（`HEADER`が抜けていた）。コリメータ開き角の
符号の意味も誤認しており、負の値は「検出器全体をカバーする広いビーム」を意味する
（狭いビームではない）。これらは値を手打ち・未検証のまま実装した結果であり、
このプロジェクトの「値を手打ちしない」原則にClaude自身が反していた。

**ユーザーに確認の上**、固定リポジトリを`DIDSR/MCGPU`（v1.3、ソースのみ）から
**`DIDSR/MCGPUv1.3_PCD`**（同じFDA/DIDSR組織のv1.3系フォーク、CC0ライセンス、
Photon Counting Detector向け拡張版）に切り替えて続行することとした。選定理由:

- 実在する鉛筆ビームサンプル（`Sample_Pencil_Beam/`）・ファンビームサンプル
  （`Sample_Fan_Beam/`、水・空気材料ファイルを直接参照）が完備されている
- 水・空気の材料ファイル（`Sample_Fan_Beam/inputs/{water,air}.mcgpu`、PENELOPE 2006
  由来の実データ、約900KB）が実在し、コピーして再利用できる
- PCD向け拡張は`IMAGE DETECTOR`セクションに`Emin Emax Nbin`の1行が追加されただけで、
  **`Nbin<=0`を指定すると素のv1.3互換のEnergy-Integrated-Detector（EID）動作に
  フォールバックする**ことをソース（`report_image()`関数）で直接確認済み。
  そのため本計画は常に`Nbin<=0`を使い、PCD固有のエネルギー分解出力構造には
  一切触れない
- pinned commit: `af5fa2888ebbc71ed3aaaf73e8ea8c1b24aea846`（`main`ブランチ、
  2026-08-04時点。tagは存在しないため、この時点のHEADを固定する）

**この切り替えに伴い、ソース（`report_image()`・`init_energy_spectrum()`関数）を
直接読んで検証し、以下の誤りをすべて修正した**（値を手打ちせず実物で裏取りする、
という原則に立ち返った）:

1. 出力ファイルの実際の場所は`{cwd}/output/EID/{ファイル名}.raw`
   （プログラム自身が`mkdir`で自動作成するサブディレクトリ）であり、
   入力ファイルと同じディレクトリの直下ではない
2. RAWファイルの値は**既に`total_histories`で正規化済み**（eV/cm²/history）。
   旧実装はこれをさらに`N`で割っており、二重正規化のバグだった
3. スペクトルファイルの単位は**eV**（keVではない）。単色線源は同一エネルギーの
   2行（1行目に確率1.0、2行目に確率-1の終端マーカー）で表現する
   （`init_energy_spectrum()`のWalker-alias補間ロジックで確認——ゼロ幅ビンは
   常に厳密にそのエネルギーをサンプリングする）
4. アパーチャ角は`0 0`が厳密な鉛筆ビーム（発散ゼロ）。旧実装が使っていた
   小さな負の値は「検出器全体をカバーする広いビーム」を意味し、狭いビームとは
   正反対だった。これに伴い、コーンビーム前提で作っていた幾何学的通過長の
   誤差予算（P2物理ゲートの許容範囲への算入）は不要になり削除した
5. RAWバイナリの5ブロック順序（total/primary/Compton/Rayleigh/multiscatter、
   各ブロックはpixels_per_image個のfloat32）は`report_image()`のEIDブランチで
   直接確認し、旧実装の想定（`raw[1]`=primary）は結果的に正しかったが、
   根拠を実装コメントに明記した

**注意（以下2点は追記2で解消済み——線源形状は「アパーチャ0 0で厳密鉛筆ビーム」、
単位は「eV/cm²/history、既に正規化済み」と実ソースで確認した。当初の懸念事項として
経緯を残すため原文のまま保持する）**: 上記以外のMC-GPUの仕様理解（入力形式・物理
モデル・タリー定義・線源形状）も記憶ベースの部分があり、**Phase P1で配布物の実物・
ドキュメントに当たって確認してから先へ進む**こと。特に以下2点はCodexレビューで
疑義が出ており、P1で確認が取れるまで未確定として扱う:

- **線源形状**: MC-GPUは平行鉛筆ビームではなく点源からの矩形コーンビームである
  可能性が高い。確認できた場合、**検出器中心1ピクセルへの狭角ビーム**に固定し、
  最大開き角から生じる幾何学的な通過長のずれ（10 cmからの乖離）を解析値との
  比較誤差予算に明示的に含める（P2の物理ゲートの許容範囲にこの項を含める）。
- **一次像タリーの単位**: photon countではなく`eV/cm²`（エネルギーフルエンス）
  である可能性が高い。確認できた場合、単色60 keVでのcount換算式を固定し、
  **空気のみファントム・N=1e6実行で換算後の一次透過率が1.0と一致するテスト**を
  P2の物理ゲートの前段に追加する。

確認の結果、上記以外にも想定と大きく異なる点が見つかった場合（例: 単色源が
組めない）は代替コード（GGEMS等）の検討に戻り、本計画を改訂する。
勝手に別コードへ差し替えて続行しない。

**追記3（2026-08-05、空気コントロールテストの物理的誤り）**: 追記2の修正版
（revision 3）を実行したところ、空気のみファントムの換算検算テスト
（`assert abs(air_T-1.0) <= 3σ`）が`air_T=0.99771`で失敗した。原因調査の結果、
これは**MC-GPU側の不具合ではなく、テスト自身の物理的想定が誤っていた**ことが
判明した。

60 keVでの空気の**全相互作用断面積**（xraylibで`CS_Total_CP`実測: μ/ρ=0.1875
cm²/g）はコンプトン散乱が支配的で、しばしば暗記されがちなエネルギー吸収係数
μ_en/ρ（~0.03 cm²/g程度、光電吸収主体）とは別物であり、ずっと大きい。10 cm・
0.00120479 g/cm³の空気層では:

```
μt = 0.1875 × 0.00120479 × 10 = 0.002259
T_analytic (Beer-Lambert) = exp(-μt) = 0.99774
```

実測`0.99771`との差はわずか`0.00003`で、統計誤差（SE≈4.8e-5）の範囲内に収まり、
**analytic Beer-Lambertと実質的に一致**している。つまりMC-GPUは正しく動作しており、
「空気は透過率1.0のはず」という空気コントロールテストの前提（route1 revision 3が
埋め込んでいた）が誤りだった。

**修正**: 空気コントロールのassertを、水スラブの物理ゲートと同じ方式
（xraylib由来のanalytic Beer-Lambert値との3σ比較）に変更した
（`air_analytic = exp(-mu_air_total * rho_air * 10.0)`、`mu_air_total`は
`CS_Total_CP('Air, Dry (near sea level)', 60.0)`）。この修正をrevision 4として
Driveへ再アップロードする。P1〜P1サンプル実行までは前回実行で既に合格しており
再現性のため変更していない（P2セル本体のみの差し替え）。

**追記4（2026-08-05、水スラブP2ゲート自体のxraylib比較を再設計）**: revision 4を実行したところ、
空気コントロールは合格したが（`T=0.99771` vs `analytic=0.99774`、統計誤差内）、水スラブの
ゲートが`z_analytic=13.5σ`で不合格になった（`z_egs5=1.67σ`は合格）。

原因を、MC-GPUが実際に使っている水材料ファイル（`Sample_Fan_Beam/inputs/water.mcgpu`、
PENELOPE-2006由来、pinned commitから実物をGitHub経由で直接取得して確認）に収録された
60 keV付近の全相互作用平均自由行程（TOTAL MFP列）から検証した:

```
water.mcgpuのTOTAL MFP（60000 eVへ線形補間）: 4.832511 cm（名目密度1.0 g/cm3）
→ mu_penelope = 1/4.832511 = 0.206932 /cm
→ T_self (PENELOPEの自己整合予測) = exp(-0.206932*10) = 0.126272
MC-GPU実測: T = 0.126197 ± 0.000105（N=1e7）
→ z_self = 0.71σ（統計誤差内で完全一致）
```

一方xraylibの`CS_Total_CP('Water, Liquid', 60.0)`は`mu=0.205873/cm`（`T=0.127615`）を返し、
PENELOPEの値と約0.5%異なる。この0.5%が10cm通過長で1.1%の透過率差に複利し、N=1e7という
高統計でMC-GPU自身の統計誤差が極めて小さい（相対0.08%）ため、13.5σという巨大な不一致として
現れていた。事前登録した4つの原因候補（線源形状・単位換算・幾何離散化・断面積データ差）の
うち前者3つは実測で否定済み（鉛筆ビーム確認済み、空気コントロール合格、直進ビームで幾何
離散化誤差なし）であり、残る「断面積データ差」（PENELOPE-2006 vs xraylib/EPDL）が原因と
特定できた。

**ユーザーの承認を得て**、この診断をCodex独立レビュー（`codex:codex-rescue`）にかけ、
物理計算（mean-free-path→mu変換、Beer-Lambert適用、xraylib比較の計算）とcell 9のコード
（単位換算式・材料ファイルの取り違えの有無・pixel_area・SEの分母N）の両方に欠陥がないかを
検証してもらった。結果: 診断ロジックは正しい（ただし60001.22 eVの行をそのまま使っていた点を
指摘され、60000 eVちょうどへの線形補間に修正——結果はz_self=0.71σで結論は変わらず）。
コード側にも単位換算・材料取り違え等の欠陥は見つからなかった。約0.5%のPENELOPE-EPDL全断面積差は
物理的に妥当であり、このプロジェクトのCLAUDE.mdが記録する別の既知の乖離（xraylibの`CS_Energy`
とNIST XAAMDIの最大17%乖離、ただしこれはμen/ρの話で今回のμtotal/一次透過率とは別物）とも
矛盾しない、との評価だった。

**対応**: P2ゲートの合否判定を「EGS5比較（独立コードとの一致）」と「MC-GPU自己無矛盾チェック
（自身が持つ材料データを正しくシミュレートしているか、`water.mcgpu`を実行時に読んで60000 eVへ
補間して検証）」の2つのANDに変更し、xraylib比較は`p2_gate.json`にreference情報として残すが
合否判定からは外した（`revision 5`としてDriveへ再アップロード）。空気コントロール
（xraylib比較、単位換算式そのものの検算が目的で物理データベース間比較ではないため変更なし）は
現状維持。Codexの追加提言（材料ファイルのSHA-256記録）はP2セルの`sha256_manifest.json`に
`water.mcgpu`/`air.mcgpu`が既に含まれているため対応済み。

**追記5（2026-08-05、P3タイミング正規表現の実物不一致）**: revision 5でP2ゲートを通過し
（`z_self`・`z_egs5`とも合格）、P3（スループット測定）に進んだところ、`timed_run()`の
`RuntimeError('No CUDA-event kernel time found...')`で停止した。原因は、P1〜P2の実行で
Driveに蓄積されていた`execution.log`（実物のMC-GPU標準出力）を確認したところ、
正規表現`r'(?:GPU|kernel).*?(?:time|Time).*?([0-9.]+)\s*(?:s|sec)'`が想定していた
「GPUまたはkernelという語＋time＋数値＋s」というパターンが実際の出力に一度も出現しない
ことが判明したため。実際のMC-GPU出力（`>>> TOTAL SIMULATION PERFORMANCE`セクション）は:

```
>>> Execution time including initialization, transport and report: 0.299 s.
>>> Time spent in the Monte Carlo transport only: 0.021 s.
>>> Time spent in initialization, reporting and clean up: 0.278 s.
```

という形式で、GPU輸送のみの時間は`"Time spent in the Monte Carlo transport only"`という
行に3桁精度で出力される（`IMAGE TALLY PERFORMANCE REPORT`節にある`Simulation time [s]: 0.02`
は2桁精度で粗いため使わない）。正規表現をこの実物の行に一致するよう修正した
（`r'Time spent in the Monte Carlo transport only:\s*([0-9.]+)\s*s'`、P2の`execute()`と
P3の`timed_run()`の両方）。あわせて周辺コメント（"CUDA-event kernel report"という表現）を
実態（MC-GPU自身がホスト側タイマーでMonte Carlo輸送区間だけを計測して報告している値）に
即した記述へ修正した。`revision 6`としてDriveへ再アップロードする。

## シナリオと観測量（既存実測との接続が本計画の価値なので厳密に固定する）

- **シナリオ**: water60_free相当。60 keV単色・水スラブ10 cm・細ビーム垂直入射。
  既存実測: EGS5透過率クロスチェック合格済み（相対差0.88%・1.7σ）、
  スループットはEGS5(-O, 1proc)=1.52M hist/s、EGS5(-O2, 8proc)=8.8M hist/s、
  ChatCarlo=349k hist/s、EGS5+LCG上限=2.8M hist/s相当（1e6/0.357s単スレッド）。
- **観測量**: 一次透過率（相互作用ゼロで検出器領域に到達した光子の割合）。
- **最大の落とし穴は観測量の定義合わせ**である（過去のEGS5クロスチェックでも
  定義合わせが主要な作業だった）。子として以下を実装時に文書化してから測る:
  - MC-GPUの「primary」の定義（Rayleigh散乱のみの光子をどう扱うか、
    エネルギーカットの既定値）
  - 幾何（ビーム径、検出器サイズ・距離、ボクセル化したスラブの厚さの離散化誤差）
  - 解析基準値: Beer-Lambert `exp(−μt)` をxraylibのμ(60 keV, water)から導出して
    3コード共通の物差しにする（**値を手打ちしない**。lessons_learned参照）

## 手順（Phase分割）

### P1: 入手・ビルド・仕様確認（合格するまで測定に進まない）

- MC-GPU v1.3のソースを**固定commit**（DIDSR公式リポジトリの特定commit SHAを
  ノートブック・RESULTS.mdの両方に記録）から入手する。
- **ビルド分岐判定（上記「使用コードと選定理由」の3択に従う）**:
  `-arch=sm_75`へのビルド設定差し替えのみでビルド成功するか確認する。
  成功しなければ**本計画は不合格として終了**し、その旨をRESULTS.mdに記録する
  （P2以降へ進まない）。
- ビルド成功後、サンプル入力の実行成功を確認する。
- ドキュメント・実物から確認して記録する事項:
  - 入力ファイル形式、単色スペクトルの指定方法、ボクセルジオメトリ形式、
    材料データのエネルギー範囲、乱数と再現性の仕様
  - **線源形状**（平行ビームか点源コーンビームか。上記の疑義を確認・確定する）
  - **一次/散乱弁別タリーの単位と定義**（photon countかeV/cm²か。上記の疑義を
    確認・確定し、count換算式を固定する）
- 記録する環境情報（すべて必須・欠けたら受入条件未達）:
  `nvcc --version`、GPUドライババージョン、`nvidia-smi`によるGPU機種・
  compute capability、ビルドに使った全コマンド、MC-GPUのcommit SHA、
  材料データ・入力ファイルのSHA-256。

### P2: シナリオ構築と物理ゲート

- 水スラブ10 cmのボクセルファントム＋60 keV単色のMC-GPU入力を作成する。
  P1で線源がコーンビームと確認された場合は検出器中心1ピクセルへの
  狭角ビームに固定し、開き角から生じる通過長ずれを比較誤差予算に含める。
- P1で一次タリーがeV/cm²と確認された場合、**空気のみファントム・N=1e6**
  実行で「count換算後の一次透過率が1.0と統計誤差内で一致する」ことを
  確認するテストをこのPhaseの最初に行う（換算式そのものの検算）。
- **物理ゲート（事前登録・一本化）**: 水スラブ10cmでのMC-GPUの一次透過率が、
  解析値`exp(−μt)`および既存EGS5実測値と、合成統計誤差の**3σ以内**で
  一致すること。N=1e7以上で判定する。**この3σ基準に例外は設けない**
  （「系統差なら継続」という条件付き許容はレビュー指摘により削除した）。
  3σを超えた場合は原因（線源形状・単位換算・幾何離散化・断面積データ差の
  どれか）を特定するまでP3へ進まず、原因を特定できたら比較誤差予算に
  正しく組み込んだ上で再判定する。原因不明のまま停止した場合も、
  その旨と切り分け結果をRESULTS.mdに記録して計画を終了する。

### P3: スループット測定（主目的）

- **タイミング手法を固定する**（Codexレビュー指摘により明確化）:
  - **カーネル時間**: CUDA eventで輸送カーネル自体の実行時間のみを計測
  - **end-to-end時間**: プロセス起動からファイル出力完了までの壁時計時間
  - 上記2つに加えて、CUDAコンテキスト初期化・入力読込・出力書込の内訳を
    分離して記録する（GPUは固定費の内訳を曖昧にすると誤読を招くため）
- N = 1e6 / 1e7 / 1e8 の3点、**各ウォームアップ1回＋3反復**、上記の
  カーネル時間・end-to-end時間の両方を記録する（各反復値・中央値・
  範囲をすべて残す。Colabは共有環境のためばらつきが出うる）
- **GPU実行の確認（CPUフォールバック除外）**: 各実行で`nvidia-smi`の
  GPU使用率、またはCUDA APIのデバイス表示により、実際にGPU上で
  実行されたことを確認する。CPUへフォールバックしていないかのテストを
  受入条件に含める。
- **N=1e8実行時の無料枠切断への対処**: 切断が発生した場合は再開後の実行を
  切断前と同一環境の測定として混ぜない（別実行として記録するか、
  その回を欠測として扱う）。
- 報告する数値（事前登録）:
  - histories/s（カーネル時間ベースの限界レート）と、end-to-end時間ベースの
    実効レート（固定費込み）
  - **対EGS5比**: 単スレッド(-O)比 / 8プロセス並列比 / RNG置換上限比 の3つを併記
    （「GPUは○倍」の分母を曖昧にしない——過去の速度比較計画と同じ流儀）
  - FOM = 1/(R²·T)（一次透過率のRで計算。同等統計到達時間の比較。
    Tはend-to-end時間を使う——反復ループでの実務的な待ち時間を表すため）
  - 実際に割り当たったGPU機種・compute capability、CUDAバージョン、
    MC-GPUのビルドフラグ・commit SHA
- **比較の分母にColabのCPUを使わない**（弱すぎて過大宣伝になる。分母は常に
  手元M3の既存実測値）

### P4: 記録と監査

- 結果を `docs/gpu_speedup/route1_mcgpu/RESULTS.md` に記録
  （生ログ・ノートブック・入力ファイル一式を同ディレクトリに保存）
- 既存の速度比較結果（`docs/egs5_crosscheck/speed_comparison/RESULTS.md`）から
  本結果への相互参照を追記
- vive-audit（監査エージェント）に、観測量定義の整合・分母の妥当性・
  外挿の有無を監査させる（速度比較計画で監査が実際に指摘を出した前例に倣う）
