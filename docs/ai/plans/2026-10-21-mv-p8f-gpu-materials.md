## 1. 目的（この計画が答える問い）

1. P8e の CPU（Numba）の核（`photon_transport_p8e.py`：材料ごとの表、層の境界、境界の扱い (a)、光電効果の結合エネルギー、K・L 殻の蛍光、220 個の深さの bin）を GPU に移せるか。
2. 移した GPU の核が P8e の Numba の核と同じ計算をしていることを、P5・P6 と同じ検証の鎖（0・1・2）で示せるか。
3. GPU の計算が、P8e の 19 ブロックの判定（保存済みの EGS5 と比べる）に合格するか。EGS5 は新しく回さない。
4. 速度は報告だけ（目標値は置かない）。

物理は P8e から変えない（カットオフ 10 keV、境界の扱い (a)、蛍光あり、陽電子に固有の物理なし、ステップの規則は P3s）。
この段階の目的は「多材料の GPU の核」を作って検証すること。照射野つきの不均質（横方向の評価）は、この核を土台にした次の段階で行う（§6）。
結論の言い方は「この配置・19 ブロックで採用基準に合格」までとし、同等性の証明とは言わない（参考 1）。

## 2. 中心になる設計の判断

### D1. 範囲（ユーザーが決める。既定案つき）

- **既定案: P8e と同じ配置だけ**（横に無限の積層、平行ビーム、深さの 220 bin）。比べる相手（保存済みの MT の試作と EGS5）がどちらも揃っていて、新しい EGS5 の計算が要らない。
- ただし核は、照射野（発散線源）と P6 の領域採点を後から足せる形にする。
  - 全粒子の x・y を運ぶ（P8e の Numba は運んでいる）。
  - 採点の呼び出しを、1 か所の関数（sink）にまとめる。
  - 照射野の枝そのものは、この段階では実装しない（未検証のコードを置かない）。
- 案 B: 照射野つきの不均質まで一度に行う。推奨しない。EGS5 側に複数媒質の照射野のユーザーコードと新しい本計算が要り、CPU の参照も無いので、原因の切り分けが難しくなる。

### D2. どう書くか（Codex の代替案を採用: 状態機械にしない）

- **1 履歴を完走する共通の C++ 関数** `p8f_history(materials, geometry, rng, sink, ...)` に、P8e の `_run_coupled` の 1 履歴分のループ（本番の経路）を写す。P8e のループの形（スタック、光子と荷電粒子の分岐、事象の優先順位）をそのまま保ち、**P5j の段階ごとの状態機械には変換しない**。物理の移植と状態機械への変換を同時に検証せずに済むため。P5k F 相当の並べ方は、P8f が通ったあとの速度改善の別計画にする。
- 駆動は 3 つあり、どれも同じ `p8f_history` を呼ぶ（物理の遷移は 1 本）。切り替えるのは、乱数の初期化と sink（足す先）だけ。
  - CPU・MT（鎖 0）: MT の状態を持ったまま、履歴を番号順に呼ぶ。
  - CPU・Philox（鎖 2 と関門 3 の参照）: 履歴番号で初期化する。
  - GPU・Philox: 各スレッドが履歴を完走し、`atomicAdd` で次の履歴番号を取る。
- 再利用と新設の線引き:
  - 再利用（既存の C++ を `#include` するだけで編集しない）: P8e の Numba が P5 系と同じ関数を呼ぶ箇所。`compton`、`pair`、`annihilation`、`photons`、`gs_mu_cached`、`table_rates`、`direction`、`new_remaining`、`advance_remaining`、`initial`、`energy_init`。再利用する前に、C++ 版が P8e の呼び出しと同じ引数・同じ乱数の消費であることを関門 0a で確かめる。
  - 新設: `boundary` は `p8f_boundary`（F12）。材料に依存する関数も新しく書く。`material_collision`（ESTAR と旧来の解析式の両方の枝）、`material_hard`、`material_coefficients`、`material_quantities`、`material_sample_k`、`material_shape`、`material_annihilation_rate`、`shell_distribution`、`select_shell`、`relax_vacancy`、`material_boundary`、`score_bins`、`tracked_local`・`tracked_segment` 相当。
- 試験用の旗: `binding_enabled` と `fluorescence_enabled` を切る経路も移す（関門 1b のため）。それ以外の P8e の試験用・記録用の旗（記録、故障、Fano、質量座標、領域、カーマ）は移さない。
- 乱数を使う式は、1 つの式の引数の中で乱数関数を 2 回以上呼ばない。一時変数に取って、順序を固定する。
- 材料の表は、材料ごとの配列を 1 本の連続した配列に並べ、材料ごとの先頭位置と長さを持つ構造体で渡す。形の検査は Python 側で行う。これは**格納の形の変換だけ**で、値と演算は変えない。§6 で外した「表の詰め直し」（速さのための配置や精度の変更）とは別のもの。
- 速さの工夫（log の事前計算、共有メモリ、状態機械、変種の比較）は、この段階では入れない。

### D3. 検証の鎖（P5・P6 と同じ型）

- 鎖 0（ビット）: C++ の CPU・MT で、**保存済みの P8e 本番のバッチをバイトまで再現する**（12 個の出力すべて）。
  - C++ は 100 群の配列と生の集計を返す。`dose` への縮約は `run_coupled` と同じ NumPy の式を Python 側で通す（加算の順を変えない）。
- 鎖 1（統計）: 最後の GPU（Philox）の本計算を、保存済みの MT の試作と比べて兼ねる（P6 と同じ）。乱数の変更だけでなく、**CPU から GPU への移植全体の比較**と記す。
- 鎖 2（履歴ごと）: 同じ（種、履歴番号）で、CPU・Philox と T4 の GPU を履歴ごとに比べる。比べる量を、220 bin・境界の数と分布・蛍光の数に広げる。
- 水の系統への接続: 関門 1b。F7 の試験と同じ条件（結合・蛍光なし）で、C++ と P8e の Numba が一致することを確かめる。これで P8e → P4 → P3b の水の系統につながる。
  - P5k F の GPU とは演算が違うので、ビットでは比べない。

### D4. ホストで計算した `log_stop_T` の扱い（mv.md の常設ルールとの関係）。ユーザー決定 2026-10-21「長い目で見て一番良い方法」

- **決定: `log_stop_T` は束の中の表（入力データ）として、NumPy が作った値をそのまま GPU に送る。** 正典の Numba の核自体がこのビットを入力として使っているので、鎖 0・鎖 2 の照合が成り立つのはこの値だけ。束のハッシュで照合する。
- P5i のルールが禁じているのは、「正典の核が輸送の中で計算する log を、ホストで計算して送ること」。核の中で `np.log` を呼んでいる箇所（`log_interp` の表の節点、`material_quantities` の `np.log(energies[i])` など）は、P8f でも核の中で、輸送と同じ `log` で計算する（事前に計算しない）。
- 長い目で見た形: 例外を足すのではなく、mv.md の P5i の行を一般の決まりに書き換える。
  - **正典の核が入力として受け取る値（束の表）は、データとしてハッシュつきで送る。**
  - **正典の核が輸送の中で計算する値は、各装置の上で、輸送と同じ関数で計算する。**
  - 理由: GPU の `log` は NumPy と最後の 1 ビットが違いうるので、装置の上で計算し直すと正典と照合できなくなる。将来、本体（chatcarlo）に移すときも、材料の表は束のデータとして配る形になる。
  - 書き換えは §4 の許可範囲に入れた。

### D5. 採点と縮約（正典の加算の順を写す）

- 履歴の中: 付与ごとに、履歴内の配列（`history_bins` 220、`hs` 108、`fine` 430）へ足す。`touched` の扱いも P8e と同じにする。`brems` は正典どおり、事象が起きたときに直接足す。
- 履歴の終わり:
  - `p8_max` と収支（`maxima`・`violations`）を、履歴内の配列と `dep` から計算する。
  - 群へ足す。CPU は `p8_batches[b]+=history_bins` と `add_clear` と同じ順。GPU は atomic（P5b・P6 と同じ）。
- 1 履歴あたりの採点の配列は 758 個の double（約 6 KB）。粒子のスタックと状態は別に要る（D6）。
- GPU の集計は、同じ種・履歴番号でも atomic の加算の順が変わりうる。合否の対象は次の 2 つで、**集計結果のバイト一致は求めない**（許容の式は 2c）。
  - 同じ履歴の出力を再現できること（鎖 2）。
  - 集計が、履歴ごとの出力を足した値と許容内で合うこと（2c）。

### D6. スタックの深さ

- 蛍光（1 空孔あたり最大 8 本）と鉛があるので、P3b の最大 8 は引き継げない。保存バッチには `maxdepth` が無い（F2）。
- 関門 0f で深さを測ってから容量を決める。
  - P8e の `_run_coupled` を直接呼び、本番と同じ条件で 10⁶ 履歴の `maxdepth` を測る。
  - GPU の容量を「測った最大の 2 倍以上、かつ 16 以上」に決め、関門の記録に書く。
- あふれは失敗として数える（`counts[6]`）。本番で 0 でなければ判定しない。

## 3. 関門（すべて事前登録。順に通す）

**共通の決まり**
- 故障を入れたビルドの検査は、正常なビルドが同じ検査に合格したあとで行う。故障のビルドが数値の比較で失敗することを求め、ビルドの失敗や入力の不一致は「検出した」に数えない。
- 入力（束・スペクトル・コード）のハッシュは、保存時の記録と照合してから回す。
- 照合の指紋には、計画ファイル・報告ファイル・ノートブック・測定の駆動を入れない。
- 種と履歴の範囲は下のとおり固定する。どれも関門ごとに新しい値で、保存データの選抜や確認に使った値と重ならない。

**関門 0（手元、決定論）**
- **0a 材料の関数:** 新しく書いた C++ の関数（D2 の新設の一覧）と再利用する P5 の関数を、P8e の Numba の関数と、4 材料それぞれについて比べる。
  - 入力は乱数の 10 万個と、端の入力。端の入力は、境目の両側を `nextafter` で具体化する: 表の節点ちょうどとその両隣、吸収端の重複した節点の両側、`T` = 10 keV ちょうどと 20 MeV、`material_hard` の `2·DELTA` と `.5-x<1e-7` の分岐の前後、殻の結合エネルギーちょうど。
  - 戻り値がバイトで一致すること。
  - 乱数を引く関数は、同じ MT の状態から始めて、戻り値、変更された状態の配列、緩和の記録（trace）、**続く乱数の列**が一致すること。
- **0b 演算の順:** 次の和はそれぞれ別の演算として、Numba 0.66 での順を試験で確かめ、C++ を同じ順にする（推測で決めない）。
  - `material_coefficients` の 4 成分の和
  - `shell_distribution` の行ごとの和・全体の和・正規化
  - `history_bins` の和
  - `touched_sum`
  - 整数乗と分数乗（`**2`、`**(-2/3)` など）の書き方も、同じ試験で照合する。
- **0c 採点器:** `score_bins` と C++ 版を、乱数の線分 10 万本と端の入力で比べ、配列がバイトで一致すること。端の入力は、bin の端ちょうど、層の境界の上の点、長さ 0 の線分、鉛の 0.05 cm の bin。`p8f_boundary` も、各内部面と外面について両方向・`w=0`・面の上・面の直前と直後で、P8e の `boundary` とバイトで一致すること。
- **0d 状態を固定した試験:** 本番でまれな枝と事象の競合を、状態を固定した小試験で確かめる。Numba と C++ の結果（状態の配列・戻り値・乱数の個数と続く列）がバイトで一致すること。出発点は既存の `test_p8e.py:768` 付近の境界・エネルギー・hard の競合の試験。

| 対象 | ケース |
|---|---|
| 殻の選択 | 確率の和が 0、累積確率ちょうど、最後の正の確率の要素に落ちる |
| 緩和 | 非放射遷移、殻 4 で即終了、線が CUT 未満・ちょうど・直上、子の空孔の連鎖（鉛の K → L） |
| 運ばれた蛍光の光子 | 蛍光の印（`a[17]` = 2・3）の付いた光子が CUT 未満で吸収される（F8 の 3 回の枝） |

| 境界 | 散乱の強さが 0・最小値の直前・直後、終端の状態、反転、反転のあと同じ面からもう一度通る、距離 0 |

- **0e 収支（故障は 3 つに分ける）:** それぞれ、正常なビルドの合格のあとで、故障のビルドが拒否されること。
  - (e1) 履歴内の付与の 1 か所を `history_bins` から落とす → `p8_max` が 1e-12 を超え、健全性の検査が拒否する。
  - (e2) 履歴の終わりの群への加算を落とす → 「履歴ごとの出力を足し直した値」と群の出力の比較で拒否する（比べ方は 2c と同じ式）。
  - (e3) 補充（次の履歴）で局所の配列を消し忘れる → **実際に出力する局所の配列**の和と、その履歴の `dep` の収支で拒否する。
- **0f スタックの深さ（D6）:** 10⁶ 履歴の `maxdepth` を測って記録し、容量を決める。小さい容量のビルドで、あふれが `counts[6]` に数えられ、健全性の検査が拒否すること。

**関門 1（手元、鎖 0）**
- **1a 保存バッチの再現:** 保存済みの P8e 本番のバッチ 0、50、99（種は F3）を C++ の MT で回し、12 個の出力すべてがバイトで一致すること。
  - `brems` も含む。逐次で、P8e と同じ加算の順なので、例外は置かない。
  - 3 バッチの中で各枝を通った回数を、C++ 側で数えて報告する。対象は、光子の境界の通過、光電効果、蛍光の放出と脱出、異なる材料の境界、偏向の省略、反転。
  - 「1 回以上」を条件にするのは、F8 から期待値が 20 以上の枝だけ。終端と 10 keV 未満の蛍光は 0d で確かめる。
- **1b 水の系統への接続:** `test_p8e.py:557` と同じ条件（旧来の水の束 1 材料、水 30 cm、単色 1 MeV、結合・蛍光なし、10,000 履歴、同じ種）で、C++（MT）と P8e の Numba を比べる。P8e が返す出力のうち、C++ が出すもの（`KEYS` と `coarse`・`fine`・`counts`）がすべてバイトで一致すること。
- **1c 故障の検出:** 次の 4 つの故障を、それぞれ別のビルドで入れる。
  - (i) 層の材料の番号をずらす
  - (ii) 境界で率の作り直し（`cached_ev=-1`）を落とす
  - (iii) 蛍光の線のエネルギーをその場に沈着させる
  - (iv) 吸収端の両側の選び方を逆にする

  比較の相手は、関門 0 の種で P8e の Numba を 2 万履歴回した参照（このために作る）。正常なビルドが一致したうえで、4 つの故障がそれぞれ失敗すること。

- 関門 3 用に、CPU・Philox の 10⁵ 履歴 × 100 バッチ（計 10⁷ 履歴）。
  - 0f と同時に C++ の速さを測って、時間を見積もり直す。
  - 見積もりが 3 時間を超えるなら、2 プロセスで回す・分けて回すなどの段取りをユーザーに出す。ここで合否の条件は変えない。

**関門 2（T4、鎖 2）**
- **2a 履歴ごと:** 同じ（種、履歴番号）で、CPU と GPU を 2 万履歴比べる。P6 の `core.c2` の規則をそのまま使う。中身は次のとおり（参考 2）。
  - 健全性と線源は、全履歴で一致することが合否。
  - 乱数の呼び出しは、P6 が呼ぶ `p5b_core.c2_calls` の規則のまま: **先頭の最大 2 つの診断の地点について、地点の数と各地点の累積の乱数の呼び出し数がともに一致する履歴の割合**が 99% 以上。総乱数の回数の完全一致は求めない。
  - bin の対差は報告だけ。
  - 比べる量に、220 bin、通常の深さ集計、`boundary_counts`、`boundary_hist`、`boundary_omitted_hist`、`fluorescence_counts` を加える。これらの数は、履歴ごとの一致率と最初に食い違った履歴を報告するだけにする。食い違いが出たら、すぐに物理の違いと決めつけず、最初の分岐を調べる（参考 3: CPU と GPU の数学関数の最後の 1 ビットの違いで枝が変わりうる）。
- **2b 補充の経路:** 2a と同じ比較を、§3 の表の履歴数で行う。0e の (e3) の故障ビルドが、(e3) の収支で拒否されること。
- **2c 集計:** atomic で合わせた 100 群と、履歴ごとの出力を足した値を比べる。
  - 許容: P6 追補 1 の式（そのビンに群の中で加えた付与の数 + 群の中の履歴数）× 2^-52 × 絶対値の和。
  - 非有限の値が 0。
- **2d 速さ（報告だけ。本計算の分け方に使う）:** 2 万履歴の µs/履歴を記録する。
- **2e 状態を固定した試験を GPU で:** 0d の各ケースから 1 つずつを GPU の核で回し、CPU の C++ と比べる。比べる量を分ける。
  - **合否:** 強制した枝を通ったこと、整数の遷移の結果（粒子の種類・材料と領域の番号・スタックの深さ・事象の種類）、乱数の消費の数、健全性が一致すること。
  - **浮動小数点の状態:** 数学関数（`log`・`exp`・`sqrt`・`pow`・三角関数）を通らない値はバイトで一致すること。通る値は報告だけ（最初の食い違いの位置と相対差）。
  - 丸めの差で枝まで変わったケースは、原因を調べ終えるまで関門を通さない。

**関門 3（T4、規模）**
- GPU で、参照と同じ種・履歴の範囲の 10⁵ 履歴 × 100 バッチを回す。
- P6 の `core.c4` の規則を、P8e の 19 ブロックに当てる。
  - ブロック平均の差 ≤ 0.5%。
  - **対応する外側バッチの差**の SEM ≤ 0.2%（`Dref` 比）。差の SEM は `SEM = std(Δb, ddof=1)/√100/Dref`。
  - 同じ Philox の履歴を使うので、CPU と GPU の値には強い相関がある。独立な 2 つの計算の誤差からの見積もり（0.34%）は当たらない（実質 6）。
- 精度の条件が届かなければ「統計不足」と記録し、追加の計算はユーザーが決める。

**本番（T4）**
- **履歴数: 2.0×10⁷**（外側 100 バッチ、各 200,000）。根拠は次のとおり。
  - 判定 A（EGS5）と判定 B（保存済みの MT の試作）の両方で、SEM ≤ 0.33% に届く数にする。
  - 既存の判定の定数 `t = .0033` で、ブロックごとに N ≥ sp²·10⁶ /(t² − se²) を計算した。sp は P8e の試し計算の SEM、se は相手の SEM。
  - A は最大 5.71×10⁶、**B は最大 1.33×10⁷**（肺 5〜6 cm。保存済みの試作の SEM が 0.256% あるため）。B の 1.5 倍は 1.996×10⁷。
  - 2.0×10⁷ での予測の SEM は、B で最大 0.307%。
  - 参考: 同じ 8,564,600 履歴では、B の差の SEM が最大 0.364% になり、条件に届かない。
- 2d の速さで本計算が 1 つの Colab の時間（目安 3 時間）を超えるなら、外側のバッチ単位で Drive に保存し、続きから回せる形にする。同じ種と履歴番号なので、分けても各履歴は同じ。再開の決まり:
  - 各外側バッチは、種・履歴の範囲・束とコードのハッシュ・健全性を添えて、1 ファイルずつ書き終えてから名前を確定する（途中のファイルは使わない）。
  - 再開した回は、保存済みのバッチの添え書きを照合して飛ばし、無いバッチだけを回す。
  - 分けて回した場合は、再開した回で、保存済みのバッチ 0 をもう一度回し、保存値と 2c の許容の式で一致することを確かめる（atomic の順が違うので、バイトの一致は求めない）。
- **判定 A（主）:** 保存済みの EGS5 と比べる。P8e と同じ 19 ブロック・基準 v2（|差| ≤ 1% かつ SEM ≤ 0.33%、`Dref` 比、上流から順）で、`Dref` は F4 の固定値。
- **判定 B:** 保存済みの P8e の試作（MT）と、同じ 19 ブロック・同じ規則・**同じ固定 `Dref`** で比べる。CPU から GPU への移植全体の比較と記す。
- P8f の合格は、A と B の両方が合格。精度の条件が届かなければ「統計不足」と記録し、履歴数の追加はユーザーが決める。全バッチで健全性（`healthy` と同じ条件）を満たし、`counts[5:7]` が 0 であること（0 でなければ判定しない）。
- **判定の入口:** `run_p8e.py` は編集しない。P8f 側に薄い包み（ラッパー）を置く。
  - `run_p8e.block_statistics` と `classify_blocks` を import して再利用する。
  - A・B とも、F4 の固定 `Dref` を明示して渡す（`judge_batches` に保存 MT を渡さない）。
  - 判定の前に入力を照合する: 両方の保存データのハッシュ、履歴数、種、範囲、束のハッシュ。
  - 判定のコードを Claude が書く場合は、判定を出す前に Codex のレビューを通す。
- **報告だけ:**
  - 速さ（同じセッションで、P5k F の水の板と交互に測る）
  - ビルドアップ 0〜3 cm
  - 鉛の 0.05 cm の bin
  - 境界の数と蛍光の数（P8e の本番との比）
