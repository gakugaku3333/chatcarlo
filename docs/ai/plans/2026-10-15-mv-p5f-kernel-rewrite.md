## 目的

T4 の V0（P5c で合格した構成）の時間の使われ方を、**本体のプロファイルと核全体の切り替え実験**で調べ、**次に試す書き直しの候補を選ぶ**。律速を完全に特定することは目的にしない（GPU では計算とメモリ待ちが重なるので、部品の時間を足して本体の時間にはできない）。分けきれなかった原因は、分けきれなかったと書く。

## 0. 前提事実（検証済み、2026-10-15）

- P5e: 割り当て・スタック・レジスタの上限の 12 変種がすべて V0 の ±2%。常駐ブロックを 2 → 4 にしても変わらない。ステップ数で降順に並べると 33% 遅い。
- GPU が読む表の大きさ（束 `p5b_inputs.npz` から）: **`ys` 49×9×20,483 倍精度 = 72.3 MB**、`us` 20,483 個 = 164 KB、`brems_v` 124 KB、そのほかは小さい。`single`（78.7 MB）は束にあるが GPU の核には渡していない。T4 の L2 は 4 MB。
- `p5_gs_mu_cached`（`p5_kernel.h:121`、弾性散乱の角度、多重散乱のステップごと）は、`zero<p0` のとき表を読まずに戻る。それ以外は、`ts`（49）を `lower_bound` と対数の重みで、`ks`（9）と `us`（20,483、等間隔ではない、二分探索で約15回の読み出し）を `p5_bracket` で探し、`ys` の8点（隣り合う2点 × 4組、組どうしは 20,483×8 B または 9×20,483×8 B 離れる）を読む。平均666ステップは GS の呼び出しの数でも、8点を読む回数でもない。
- 1履歴あたりの平均ステップ数 666（P5c）。1スレッドの作業領域 30 KB（スタック 11.8 KB、`hs`・`fine` 6.0 KB、`P5bLocal` 6.6 KB、`nspec_work` 5.1 KB）。
- **未確認**: Colab の T4 で Nsight Compute（`ncu`）が使えるか（ツールの有無と、性能カウンタへの権限）。

## 1. 測るもの（すべて報告のみ）

**M0 プロファイラが使えるか**（最初の小さいセル）: `command -v ncu`、CUDA の既知の場所、`ncu --version`。次に短い CUDA の核を別のプロセスで `ncu` から起動し、性能カウンタが取れるか（`ERR_NVGPUCTRPERM` などのエラーの全文を記録）。

**M1 本体のプロファイル**（M0 が通った場合）: CuPy で V0 を暖機したあと、**n=100,000 の対象の起動1回だけ**を選んで `ncu` で測る専用スクリプトを別プロセスで実行する。記録するもの:

| 疑うもの | 見るもの |
|---|---|
| 作業領域 | ローカルの読み書きの命令数・要求量、L1/L2/DRAM の実際の転送量、spill |
| 大きな表 | グローバルの読み出しの要求数・セクタ数、L1/L2 のヒット率 |
| 倍精度 | FP64 パイプの稼働率、発行した命令、依存の待ち |
| 分岐の発散 | ワープあたりの有効なスレッド数、predication、分岐 |
| 待ち時間を隠せているか | 実際に有効・発行可能なワープ数、発行の状況、停止の理由（long scoreboard など） |

`ncu` の設定（セクション、replay の方式、pass の数、キャッシュの制御）を保存する。**速さの値は、プロファイラなしの実行から取る**（プロファイラの下の時間は使わない）。帯域の使用率や停止の割合を単独で原因と読まず、組み合わせて判断する。

**M2 核全体の切り替え実験**（M0 の結果によらず行う）: 診断用に**生成した派生のソース**（凍結ファイルは編集しない。組み立てのときに関数名のマクロで呼び出しを差し替える。生成の規則と sha256 を記録）で、2要素 × 2水準の4条件を、同じセッションで交互に3巡、n=100,000 で測る。

| 条件 | `ys` の8点の読み出し | 線量の書き込み（`hs`・`fine` と `P5bLocal` への集計） |
|---|---|---|
| B（基準） | 元の表 | 元のまま |
| T（表の対照） | 読み出し先を、小さい共通の面（キャッシュに乗る）へ写す。探索・補間・乱数の消費は残す | 元のまま |
| W（書き込みの対照） | 元の表 | 書き込みを、履歴の中の少数のチェックサムへの足し込みに置き換える（輸送と乱数の列はそのまま） |
| TW | 写す | 置き換える |

- B は V0 と同じ出力（健全性、整数3種の一致、深い5ブロックの相対差 ≤ 1e-8）になることを確かめる。派生のソースで機械語が変わっても出力が同じであることの確認。
- W は輸送が変わらないので、`counts`・`step_batches`・`nspec` が B と完全一致することを確かめる（線量は比べられない）。
- T と TW は散乱の角度が変わり、その後の輸送も変わる。**時間の差を「表の費用」と断定しない**。ステップ数・散乱の回数・乱数の消費を並べて報告する。
- 各条件で `num_regs`・`local_size_bytes`・常駐ブロック数を記録する。

**M3（必要なときだけ）**: M1・M2 で分けきれない部分があれば、詳細計画の改定で、CPU の観測用ビルド（呼び出しのフック）で入力の列を記録して部品を再生する。今回は作らない。

## 2. 何を決めるか

M1・M2 の結果を並べ、P5f-1（作り直し）の候補を、根拠と分けきれなかった点を添えて挙げる。候補の例（Codex の提案。順番は結果で決める）:
- 作業領域の重複を除く（`hs`・`fine` から `P5bLocal` への写しをやめ、同じ場所へ直接足す。`nspec_work[640]` を1つの番号にする）。輸送と乱数の順を保ちやすい。
- 表の探索・補間の繰り返しを減らす（エネルギーの更新のときに添字と重みを持っておく）。
- ワープの中で近い表の要素を読む配置や処理の順（粒子・事象ごとの処理）。
- 全体の単精度化は後回し（輸送・分岐・乱数の消費を変える範囲が広い）。

## 3. 範囲

- 新規のみ: 派生のソースを組み立てる関数、診断用の入口、Colab のノートブックと実行スクリプト（M0〜M2）、テスト、`RESULTS_P5F0.md`（Claude）。

## 4. 停止条件

- B が V0 と同じ出力にならない、または W の整数が B と一致しない → 派生の仕組みの誤りとして停止。
- `ncu` が使えなくても停止しない（M2 だけで進み、その事実を記録する）。

## 6. 詳細（2巡目の反映。§1〜§5 と食い違うときは本節が優先）

**派生のソースの作り方（共通）**: 新しい組み立て関数が、凍結ファイルの本文を読み、**決まった文字列の置き換えの一覧**（各置き換えは元の本文にちょうど1回現れることを確かめ、そうでなければ停止）を当てて派生のソースを作る。凍結ファイルは書き換えない。置き換えの一覧・派生のソースの sha256・各条件のコンパイル指定を記録する。コンパイル指定は V0 と同じ（`-DP5_GPU -DP5_RNG_PHILOX --fmad=false -DP5_TRANSPORT_FAULT=0 -DP5_STACK_CAP=64`）。割り当ては静的（V0 と同じ、1スレッド1履歴、128スレッド/ブロック）。

**T（表の対照）**: `p5_gs_mu_cached` の本文の中の `t->ys[` を `P5F_YS(` 系の読み出しに置き換えた派生の定義を使う。`P5F_YS(q)` は `t->ys[p5f_base + (q % t->nu)]`（`p5f_base` は実行時の引数で、(i, j) の1つの面の先頭。面は (i=24, j=4) の固定）。探索・補間・乱数の消費のコードはそのまま残る。面の大きさは 164 KB で L2 に乗る。4組の読み出し先は同じ面の中の別の位置になり、値は同じになり得るが、コンパイル時には分からないので計算は消えない。これは「表の読み出しの局所性を大きく良くしたときの感度」で、DRAM の費用そのものではないと報告する。

**W（線量の集計の経路を縮めた対照）**: 次をまとめて置き換える（「書き込みの命令だけ」ではなく、**線量の集計の経路全体を縮めた対照**と報告する）。
- 派生の `history`: `double hs[150]={0.},fine[600]={0.};` をなくし、`p5_local`・`p5_track_local`・`p5_track_segment` の呼び出しを、履歴ごとの2つの倍精度のチェックサム（Σloss と Σ z·loss）に足す関数へ置き換える（`touch` の更新は残す）。履歴の終わりの `p5_touched_sum` と出力の配列への写しをなくし、粗い・細かい誤差の検査は |Σloss − dep| で代える。エネルギーの収支（residual）の検査はそのまま。
- 新しい入口（`P5fLocal`）: 線量の配列（150＋600）を持たない。本番の核は、チェックサム2つを原子的に足す（線量の 750 回の原子的加算をなくす）。ほかの出力（`totals`・`maxima`・`brems`・`violations`・`counts`・`nspec`・`step_batches`・`maxdepth`・`nan_count`）は V0 と同じ。
- TW: T と W の置き換えを両方当てる。

**正しさの確認（測る前に固定）**:
- (P1) B: 本番の核の n=100,000・start=0 が V0 と同じ（健全性0件、整数3種が束の `c4_*[0]` と完全一致、深い5ブロック相対差 ≤ 1e-8）。さらに履歴ごとの核の n=20,000 の全出力が V0 の履歴ごとの出力と `core.bits` で一致。
- (P2) 輸送が同じであることの確認: 4条件それぞれの**履歴ごとの診断の核**（n=20,000・start=0）が、履歴ごとに `calls`（乱数の消費）・`steps`・`counts`（16種）・`nspec_index`・`maxdepth` を出す。B と W、T と TW がこれらすべてで `core.bits` で一致すること。
- (P3) 健全性（全条件・全計時の実行）: 非有限値0、`counts[5]`（上限ステップ）・`counts[6]`（スタックあふれ）0、`violations[0]`（エネルギー収支）0、`nspec` の総数 = n。W/TW の線量の検査は |Σloss − dep| ≤ 入射の 1e-9 で行う。T/TW は輸送が変わるので、これに合格した場合だけ時間を比べ、ステップ数・GS の呼び出しの数（`counts[1]`）・8点を読んだ回数（派生の GS の中で数える）・乱数の消費を並べて報告する。不合格の条件は時間の比較から外し、「その診断の条件は成立しなかった」と記録する。
- (P1)・(P2) が不合格なら停止（派生の仕組みの誤り）。

**計時**: P5d と同じ境界（イベントの `kernel_ms`、ホストの `call_s`）。暖機のあと、B→T→W→TW と TW→W→T→B を交互に3巡、n=100,000・start=0。各条件の `num_regs`・`local_size_bytes`・占有率の API の常駐ブロック数を記録する。

**M1 の対象**: V0（P5b の `p5b_run_kernel`、派生でないもの）。対象の起動は暖機のあとの n=100,000 の1回。`ncu` が使えて時間に余裕があれば、B と W も同じ設定で測ってよい（報告のみ）。

**成果物（RESULTS_P5F0.md、Claude）**: M0〜M2 の結果、**最初に試す書き直しの候補1つ**、その根拠、分けきれなかった原因、次の比較の方法。M1 が使えず M2 でも差がはっきりしなければ、「律速は特定できないが、輸送の順を保ちやすい作業領域の重複の除去から試す」という選び方でもよい。

**範囲（ファイル）**: 新規のみ `prototypes/mv_electron/gpu/p5f_derive.py`（派生のソースの組み立て、NumPy と標準ライブラリだけ）、`p5f_gpu.cu`（新しい入口: `P5fLocal`、B/T/W/TW の本番の核と履歴ごとの診断の核）、`p5f_colab.py`、`p5f_ncu_target.py`（`ncu` から起動する対象のスクリプト）、`p5f_colab.ipynb`、`prototypes/mv_electron/tests/test_p5f.py`。ノートブックは P5e と同じく固定コミット・束の sha256 を書き込み、`git fetch` してから checkout する。結果は Drive `viveMonte/p5/p5f0/`。

**テスト**: 置き換えの一覧がそれぞれちょうど1回当たること（当たらない・2回当たるときに停止すること）、派生のソースの sha256 が決まった値になること、B の派生のソースを手元の clang++ で CPU 用にビルドした（`P5_GPU` なし）とき凍結の `p5_cpu.cpp` 経由の出力と n=2,000 で10出力が一致すること（派生の仕組みが本文を壊していないことの確認）、W の CPU ビルドで B と `counts`・`step_batches`・`nspec` が一致し |Σloss − dep| の検査が通ること、P3 の判定が人工の違反を拒否すること、`p5f_colab` が import の時点で `cupy`・`numba`・`p5a` を読み込まないこと。
