## 目的

1. **発散の地図**（報告のみ）: V0 の核で、どの命令・どの行で参加レーンが少ないかを SASS の命令の単位で測る。原因（合流の失敗か物理の分岐か）は判定しない。場所を特定するだけ。
2. **状態機械の試作**: 履歴をレーンに固定したまま、核を「1回の呼び出しで1つの処理だけ進める遷移の関数」に組み直し、GPU の外側のループでワープの中の同じ種類の処理を選んで進める。CPU は同じ遷移の関数を1履歴ずつ最後まで回す。**各履歴の演算と乱数の呼び出しの順番、共有の出力へ足す時点を変えない**ことを目標にし、ビット一致を**測って**示す。
3. 試作が関門に合格したら、V0 と同じセッションで速さと参加レーンを並べて報告する。採否はユーザーが決める（速さの足切りはない）。

## 0. 前提事実（2026-10-15。観測・差し引きの推定・仮説を分ける）

**観測**
- 10万履歴（束のバッチ0 `c4_counts[0]`）: ステップ 66,421,651、荷電粒子の区間（`counts[0]`）65,628,031、GS（`counts[1]`）38,536,884、硬い衝突（`counts[2]`）704,251、境界（`counts[3]`）854、光子の相互作用（`counts[8..11]`）527,423。
- V0 の `ncu`（P5f-0）: 全命令の平均参加レーン 2.10、述語が真のレーン 1.92、FP64 パイプ 82.7%、発行スロット 3.7%。**2.10 は全命令の値で、FP64 命令だけの値ではない。**
- 核の形（`p5_kernel.h:334〜`）: `while(top>=0)` で粒子を1つ取り出し、光子は1回の処理、荷電粒子は `for(;;)` で1ステップずつ。事象の優先順は **境界 → eb → GS → 硬い衝突 → 制動放射 → 飛行中の消滅**（許容差 1e-13 付き）。`cached_ev` などの計算済みの値は、スタックから粒子を取り出すたびに初期化され、同じ粒子の `continue` では保たれる。`break` には、硬い衝突・制動放射（`suspended`）・飛行中の消滅（`annihilated`）・停止・失敗の別があり、後の処理が違う。
- CPU の入口（`p5_cpu.cpp`）は複数の履歴で共有する `P5Output` に直接足す。GPU の入口（`p5b_wrap.h`）は履歴ごとの `P5bLocal` に足してから集計する（`brems[1]` などは履歴の途中で足すので、2つの足し方は末尾のビットが違い得る。既知）。

**差し引きの推定**: 区間からGS・硬い衝突などを引いた残り（約 2,600 万）の多くは eb の事象で、そのたびに `ev` が変わり計算し直すと見込む（境界の `continue` や終わりの経路もあるので確定ではない）。

**仮説（未確認）**: 入れ子のループで分かれたレーンが長く合流しない。T4 の FP64 のワープ命令は参加レーンが少なくてもパイプを同じだけ使う。

## 1. 発散の地図（報告のみ）

- 行の情報の指定（NVRTC `--generate-line-info`。`-G` は使わない）の**ありとなしだけを変えて**、同じ環境で V0 をコンパイルし、(i) 2万履歴の履歴ごとの全出力の `core.bits` 一致、(ii) 対象の核の SASS と資源（レジスタ・ローカル）を比べる。実行コードが変われば「行の情報付きの構成の地図」と明記し、V0 への直接の帰属は保留する。
- `ncu --page source --print-source cuda,sass` で、SASS の命令ごとに「実行したワープ命令の数」「実行したスレッド命令の数」「述語が真のスレッド命令の数」を取る。保存の基本の単位は「関数・SASS のアドレス・命令・対応するソースの行・3つの数」。行ごとの値はその派生で、**ワープ命令の数で重みを付けた平均参加レーン**（Σスレッド命令 ÷ Σワープ命令）。全命令と FP64 の命令（`DADD`・`DMUL`・`DFMA` など）を分けて出す。コンパイラに渡した全文（`core.source()`）を保存し、元のヘッダーの行への対応表を付ける。`.ncu-rep` も保存。

## 2. 状態機械の試作

- 新しいファイルに、凍結した `p5_kernel.h` の `history()` と同じ演算を、遷移の関数に分けて書き直す（凍結ファイルは編集しない）。状態は最初は少数: 「粒子を取り出す／光子の処理」「荷電粒子の1ステップ」「粒子の終わりの処理」「履歴の終わり」。各履歴の継続の状態として保存するもの: 粒子の状態、スタックと `top`、Philox の `seed/history/calls`、`cached_ev` と `S/rate/total/G1/brate/bsoft/arate`、線量の配列と `touch`、履歴の中の集計、`suspended`・`annihilated`・`failed`、診断の位置、継続の位置。キャッシュの寿命と事象の優先順は元と同じ。
- **CPU の駆動**: 同じ遷移の関数を1履歴ずつ最後まで回し、既存の CPU の入口と同じ共有の出力へ、同じ時点で足す（保存済みの100バッチとのバイト一致を狙う）。
- **GPU の駆動**: 1レーン1履歴（V0 と同じ割り当て）。外側のループはワープで一様にし、各周回の頭でワープの中の未終了のレーンの状態を `__ballot_sync` などで集め、決まった順に、同じ状態のレーンだけを1つずつ進める（周回の頭で対象を固定し、途中で状態が変わったレーンを同じ周回の後の処理に混ぜない）。終わったレーンもワープの集合の操作には参加させる。集計は P5b と同じく履歴ごとの局所の出力から。履歴ごとの出力の核と本番の核は同じ遷移の関数を使う。
- 試作で参加レーンが十分に増えなければ、その場所だけを細かくする（履歴をまたぐ事象のキューは第2案として、結果を見てから別の計画にする）。

## 7. 詳細（2巡目の反映。§1〜§6 と食い違うときは本節が優先）

**遷移の表（最初の形）**: 初期化は一度だけの処理。状態は (P) 粒子の取り出し／光子の処理（`p5_kernel.h:334〜378` 付近。荷電粒子を取り出したときにキャッシュと終わりの理由を初期化）、(C) 荷電粒子の1ステップ（380〜465 付近。`continue` は同じ状態、`break` は終わりの理由を付けて (E) へ）、(E) 粒子の終わりの処理（467〜474 付近。停止時の消滅など。`suspended`・`annihilated`・`failed` で分ける）、(H) 履歴の終わり（476〜487 付近。未解決のエネルギー、検査、共有の出力への最後の加算）、(D) 終了。**スタックから退避した粒子を取り出し直すとき（P 経由）はキャッシュを初期化し、同じ粒子の次のステップ（C → C）では保つ。** 硬い衝突の `break` を粒子の消滅と解釈しない。失敗のときは今の `state` とスタックを保ったまま (H) へ。継続の状態は各レーン専有で、参照（ポインタ）で渡し、遷移ごとに大きな配列を写さない。

**GPU の集合の操作の契約**: ブロックは128（32の倍数）。`i>=n` のレーンも早く `return` せず状態 (D) で残り、履歴のデータに触れない。正常に終わった・失敗したレーンも、ワープ全体が終わるまで集合の操作に参加する。各周回の頭で全レーンの状態を保存し、**全状態の対象のマスクを遷移の実行前に確定する**（`__ballot_sync(0xffffffffu, state==X)` を全レーンが同じ順で呼ぶ）。決まった順（P → C → E → H）に、そのマスクのレーンだけが1つの遷移を実行する。外側のループは全レーン共通の終了の判定（`__ballot_sync` で全レーンが D）だけで抜ける。分岐の中で `__activemask()` を状態の集合の代わりに使わない。有効な履歴だけ、(H) の後に出力を1回書く。

**通常の実行で通らない遷移の検査**（CPU と GPU の両方、凍結版との出力の比較と、通ったことを示す遷移の記録付き）: (a) 小さい `maxsteps` で、光子の処理中と荷電粒子の処理中の打ち切り、(b) 小さいスタックの上限（`-DP5_STACK_CAP` を小さく）で二次粒子の追加時の失敗、(c) 硬い衝突・制動放射によるスタックへの退避と取り出し直し、(d) 陽電子の停止時の消滅・飛行中の消滅・領域外への脱出。CPU は凍結の `p5_cpu.cpp` と、GPU は同じ条件の V0（P5b の履歴ごとの核）と、出力のビット一致。

**細かくしたとき**: 遷移の分け方を変えたら新しい構成として関門 1〜3 をやり直す。測る対象のソースを固定してから関門を通す。

**ファイルとテスト**: 新規 `prototypes/mv_electron/gpu/p5g_kernel.h`（遷移の関数。`P5_FN` で CPU/GPU 共通、`p5a0_common.h`・`p5_rng.h` は読み込んでよい）、`p5g_cpu.cpp`（CPU の駆動、`p5a_run` と同じ C の契約）、`p5g_gpu.cu`（GPU の駆動、履歴ごとの核と本番の核、C3 の故障版）、`p5g_core.py`（NumPy だけ: 指紋、関門の判定）、`p5g.py`（手元: 関門 1 と通常でない遷移の CPU 側の検査）、`p5g_colab.py`・`p5g_colab.ipynb`（地図、関門 2、速さ、関門 3 は別のセル・別の承認の旗）、`prototypes/mv_electron/tests/test_p5g.py`。ノートブックは固定コミット・束の sha256、`git fetch` してから checkout。結果は Drive `viveMonte/p5/p5g/`。テスト: n=2,000 で CPU の新旧の一致、通常でない遷移 (a)〜(d) の CPU 側の一致、遷移の記録の形、関門の判定が人工の1ビットの差を拒否すること、`p5g_colab` が import の時点で `cupy`・`numba`・`p5a` を読み込まないこと。

## 修正3（2026-10-16、Colab で発覚。測定の道具の誤り）

修正1で取り出した ELF（CUDA の cubin、e_machine 190、`.text.p5b_run_kernel` などを含む）を `cuobjdump --dump-sass` が「device code を含まない」とした。取り出した 958,639 バイトのうち、ELF の見出しから計算した終わり（section header table の終わり = e_shoff + e_shnum × e_shentsize = 958,416）より後ろに 223 バイトの余分がある（CuPy のキャッシュの付加とみられる）。直し方: (1) ELF の見出しから、section header table の終わりと、各 section・program header の (offset+size) の最大のうち大きいほうを ELF の長さとし、そこで切って `.cubin` に書く。(2) `cuobjdump --dump-sass` が失敗するか対象の関数が見つからなければ、`nvdisasm`（`shutil.which` か `/usr/local/cuda/bin/nvdisasm`）で同じ `.cubin` を逆アセンブルし、対象の関数の命令を取り出す（命令の文字列の比較に使う。比較の規則は変えない）。どちらでも取れなければ今と同じく停止。ほかは変えない。テスト: 人工の ELF（見出しと section header を持つ最小のもの）＋末尾の余分から、正しい長さで切れること。

## 修正5（2026-10-16、SASS の取り出しをあきらめる）

修正3でも Colab で「invalid ELF header table」で止まった。実物（CuPy のキャッシュのファイル）を手元で調べると、ELF の見出しは e_phoff 958,416、e_phnum 4、e_phentsize 56 で、program header table の終わりは 958,640 バイトだが、取り出せる ELF は 958,639 バイトで **1 バイト足りない**（修正3で「余分」とした 223 バイトは program header table だった）。CuPy のキャッシュから完全な cubin は得られない。この SASS の比較は「行の情報の指定で実行コードが変わらないこと」の補足で、地図の読み方（§1: 変わったなら「行の情報付きの構成の地図」と明記）を決めるだけのもの。直し方: `divergence_map` で SASS が取れない（`core.Stop` が出る）ときは停止せず、`sass_equal=None`、`sass_note` にエラーの文、`attribution='行の情報付きの構成の地図。SASSの同一性は確認できず、V0への直接の帰属は保留'` を記録して、資源の比較と `ncu` の地図に進む。出力のビット一致（`lineinfo_bits`）は今までどおり必須（不一致なら停止）。テスト: SASS が取れない場合に停止せず上の値が記録されること、ビット不一致では停止すること。
