## 目的

板（Mohan 10 MV、30 cm 水、深さの線量）の同じ入出力で、1履歴あたりの時間を次の3段に並べる。速さの目標値は置かない（ユーザーの決定）。

| 段 | 機種 | 核 |
|---|---|---|
| 1 | M3（手元） | P4の核（Numba、MT、1プロセス） |
| 2 | M3（手元）／Colab の CPU（x86、g++） | Cの核のCPU版（Philox、1スレッド） |
| 3 | Colab T4 | 同じCの核のGPU版（P5bの `p5b_run_kernel`、1ブロック128スレッド） |

あわせて、P5cで見えた「T4がM3のCPUの約2倍にとどまる」について、**資源量・出力方式の差・起動の寸法への感度を観察する**（報告のみ。原因の特定はしない。必要になったら別の計画で実行時のプロファイルを取る）。

## 0. 前提事実（検証済み、2026-10-15）

- P5cの粗い値: バッチ0〜99のファイル時刻から 793 s / 990万履歴 ≈ 80 µs/履歴（Driveへの書き込みを含む）。P5aの手元の値: Cの核 164、P4の核 284 µs/履歴（M3、1プロセス、5万履歴）。
- GPUの起動は `p5b_colab.GPU.launch`: `((n+127)//128,), (128,)`。`production(n,start)` は出力を確保 → 起動 → `download`（同期を含む）。`check_range` の上限は n ≤ 2,000万。
- 1スレッドの局所の作業領域: `P5bLocal`（倍精度 150+600+6+3+10+28 ほか）、`p5b_history` 内の `long long nspec_work[640]`、核の中の `P5State stack[64]` と `double hs[150], fine[600]`（`p5_kernel.h:325`）。合計は数十KBの見込みで、レジスタに乗らずローカルメモリに置かれるはず（**未確認**。CuPyの `RawKernel.attributes` の `local_size_bytes`・`num_regs` で確かめる）。
- `p5b_run_kernel` は1履歴ごとに倍精度の原子的加算を 150+600+6+10 = 766 回行う（値が0でも行う）。
- Colab の環境（P5a0で記録）: g++ 13.3.0、x86_64、CuPy 14.0.1、CUDA 13.0。CPUの型番・コア数は未記録。
- 凍結されたファイル（P5aの5つ、P5bの9つ、P3/P4の凍結対象）は編集しない。P5dは新しいファイルだけを足す。

## 2. 正しさの関門（合否はこれだけ。速さは報告のみ。照合は計時の外）

- **A-g**: 同じ条件の Cの核 MT 版（`p5a.CPU(rng="mt").run`）と、10出力を既存 `p5a.compare_outputs` で比較し不一致0（鎖0の再確認）。
- **B-g**: 保存済みバッチ0と10出力を `p5a.compare_outputs` で不一致0。
- **C**（機種・コンパイラが違うので丸めの幅は使わない）: 各回の出力について、整数の `nspec`・`counts`・`step_batches` が、束の2万履歴の参照（`history_*`）を既存 `core.sum_histories(..., nspec)` で行の対応どおりに足した和と完全一致。深い5ブロック `core.deep_blocks(out["batches"].sum(axis=0), n, float(reference["conversion"]))` と参照側の同じ量が、5要素すべてで `core.relative` ≤ 1e-8。根拠: P5c で数学関数の最後のビットが違う GPU でも、全履歴が同じ道で深いブロックの差が 1e-15 % 水準だった。整数が1つでも違えば（ある履歴が違う道を通った）停止して報告する（合否ではなく、事実を調べてから決める）。
- **D-g**: (i) GPU 自身の履歴ごとの出力と本番の出力を既存 `core.c3`（P5c の C3 と同じ）。(ii) n=100000 の `nspec`・`counts`・`step_batches` が束の `c4_*[0]` と完全一致、深い5ブロックが `c4_blocks[0]` と5要素すべてで `core.relative` ≤ 1e-8。
- **D3**: 128版（D の n=100000 の1回）と、整数3種の完全一致と深い5ブロックの `core.relative` ≤ 1e-8。不合格なら**その診断値だけ**採用しない（停止しない）。D2 は D-g の (i) が関門を兼ねる。

**全計時実行の健全性**（各回）: 新しい関数 `cpu_health(r)`（CPU の10出力用）と既存の `core.require(core.health(r), ...)`（GPU 本番出力用）で判定する。CPU 用は、10出力すべて有限、`violations` 全0、`counts[...,5]`（上限ステップ）と `counts[...,6]`（スタックあふれ）が0、`nspec` の総数 = n。`nan_count` は CPU 出力にないので補わず、有限性を実出力で確かめる。履歴ごとの出力（D2）は `nspec_index` の個数 = n。

## 3. 停止と継続の優先順位

1. 出力が得られて、関門または健全性が不合格 → **停止**して報告（その構成の速さは記録しない）。n=1,000,000 でも同じ。
2. 出力が得られなかった（メモリ不足、セッションの切断、時間切れ、CUDAのエラー）→ n=1,000,000 と D3 に限り、その事実を記録して**継続**。CUDAのエラーの後は、ノートブックを再起動して D の残りを最初から（暖機を含めて）やり直す。それ以外の構成で起きたら停止。
3. Colab の GPU が T4 以外 → 記録はするが T4 の値として扱わない。

## 4. 計時の境界（固定）

- **GPU の1回**: `cp.cuda.Device().synchronize()` → ホスト時計開始 → 出力の確保とゼロ初期化 → 同じ stream で開始イベント → `p5b_run_kernel` → 終了イベント → 既存の取り出し（同期を含む）→ ホスト時計終了。記録 `kernel_ms`（イベント）と `call_s`（ホスト）。照合・保存はこの外。
- **一度きりの費用**（各操作の後に `synchronize`）: (a) CUDA の文脈の作成 = 最初の `cp.cuda.runtime.getDeviceCount()` から最初の小さい配列の確保までのホスト時間、(b) コンパイル = 各 `RawModule`/`RawKernel` の `compile()` のホスト時間（CuPy のキャッシュの有無を `CUPY_CACHE_DIR` の該当ファイルの有無で記録し、「キャッシュ込みのコンパイル要求時間」として報告。キャッシュを消さない）、(c) 表の転送 = `GPU.__init__` 相当の `cp.asarray` 全体＋同期。ノートブックの再実行かどうか（同じ実行時の中での2回目か）を記録する。
- **CPU**: ctypes の呼び出しの前後（`p5a.CPU.run` の `seconds` と同じ境界）と、出力の確保を含む呼び出し全体の両方。P4 の `seconds` は `run_coupled` と結果の整形を含む（既存の境界）と明記する。
- 各回に時刻、GPU は `nvidia-smi --query-gpu=clocks.sm,clocks.mem,temperature.gpu,power.draw,power.limit --format=csv`、Colab CPU は `lscpu` の型番・コア数と `nproc`。

## 5. 診断（報告のみ。本測定と混ぜない）

- D1: 各カーネルの `attributes`（`num_regs`、`local_size_bytes`、`max_threads_per_block`、`shared_size_bytes`）と、デバイスの `multiProcessorCount`・`maxThreadsPerMultiProcessor`・`regsPerMultiprocessor` を**そのまま報告**する。占有率は計算しない。
- D2: 本番の集計方式と履歴ごとの書き出し方式のイベント時間、資源属性、出力の大きさ。差を原子的加算の単独の費用と解釈しない。
- D3: ブロック 64・256 の時間（起動の寸法への感度）。

## 6. 報告の形（RESULTS_P5D.md、Claude が書く）

- µs/履歴（中央値・最小・最大）の表。比は**同じ種類の時間どうし**で、式を列名に書く: 「A÷B（CPU 内側時間）」「C÷D（CPU 内側 ÷ GPU イベント）」「C÷D（CPU 呼び出し全体 ÷ GPU 呼び出し全体）」「B÷D」。どれも「何倍速いか」（大きいほど右側が速い）。A÷B は言語・実装・乱数の違い、C÷D はコンパイラと実行の実装の違い、B÷D は機種の違いも含むと明記する。
- T4 の n に対する変化、一度きりの費用、D1〜D3、P5c の粗い値（80 µs）との対応。

## 8. テスト

```bash
.venv/bin/python -m pytest prototypes/mv_electron/tests/test_p5d.py -q
.venv/bin/python -m pytest prototypes/mv_electron/tests -q
.venv/bin/python -m prototypes.mv_electron.gpu.p5d local   # Claude が実行（~/.cache を使う）
```

`test_p5d.py` に入れるもの:
- `p5d_core` の ctypes 読み込み（clang++）が `p5a.CPU(rng="philox").run` と10出力で不一致0: (n=2000, start=0) と (n=2000, start=7000) の2条件、別の seed でもう1条件、maxsteps=2 で1条件。
- 実際の CPU 出力が `cpu_health` を通ること、`seconds` を除くこと、欠けた／余分なキー・形・型・非有限値・`counts[...,5]`>0 を拒否すること。
- C・D の関門が人工の整数の不一致と深いブロックの 1e-7 の差を拒否し、1e-9 の差を通すこと。
- 束・ソースの sha256・コンパイル指定の不一致で停止すること（`p5b_core.load_bundle` を使う経路を含む）。
- 偽の GPU（CuPy の代わりの記録用オブジェクト）で、同期 → 確保 → 開始イベント → 起動 → 終了イベント → 取り出しの順序と、`kernel_ms`・`call_s` の記録。
- 停止と継続の分岐: 健全性不合格は停止、n=1,000,000 の「出力なし」は継続、それ以外の構成の「出力なし」は停止。
- `p5d_core`・`p5d_colab` を読み込んでも `numba`・`p5a`・`cupy` が `sys.modules` に入らないこと（`cupy` は関数の中でだけ読み込む）。

## 修正1（2026-10-15、Colab のスモークで発覚）

Colab の g++ 13.3 で `p5_cpu.cpp` のビルドが失敗した: `p5_kernel.h:402` の修飾なしの `isfinite` を g++ は大域の名前として見つけられない（clang・NVRTC は通す）。凍結ファイルは編集しない。代わりに新規 `prototypes/mv_electron/gpu/p5d_gxx_compat.h`（`#include <cmath>` と `using std::isfinite;` だけ）を足し、C の指定に `-include <そのヘッダーの絶対パス>` を加える（指定とヘッダーの sha256 を identity に含める）。M3（B-g・B）の clang の指定は変えない。関数は同じ `std::isfinite` なので計算は変わらない。確かめること: 手元の clang でもこの指定で `p5_cpu.cpp` がビルドでき、新しい読み込みが `p5a.CPU` と10出力で不一致0（既存テストの n=2000 の条件）。
