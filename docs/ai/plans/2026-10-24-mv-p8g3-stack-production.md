## 1. 目的

積層（水–肺–水–骨–水–鉛、Mohan 10 MV 平行ビーム）の GPU の入射光子を、EGS5 と同じ **合計 1.0×10⁸ 個**にする。保存済みの P8f の本計算（2.0×10⁷ 個、種 820101、100 バッチ）に、P8g-2 の核で **8.0×10⁷ 個**を別の種で追加し、10 MV・4 MV の統計の追加（`docs/validation/mv/stats10mv/`・`stats4mv/`）と同じく履歴数の重みで合算する。

- ユーザーの決定（2026-10-24）: 「EGS5 を 1×10⁸ にする計算をしながら、GPU 計算の高速化を行った後に GPU の光子数を決める」→ 高速化（P8g-2）のあと「本計算用スクリプトの計画から進めて」。
- EGS5 側は済み: 保存済み P8e 本番 6×10⁷（種 820001）+ 追加 2×10⁷ × 2（種 820201・820202、`~/.cache/chatcarlo/statsstack/out/`、`docs/validation/mv/statsstack/run_add.py`）。19 ブロックの χ² は 3 組とも p ≥ 0.46。
- P8g-2 は検査した履歴で P8f と履歴ごとにバイト一致し、P8f の判定 A・B を引き継いでいる。この計画は核を変えない（駆動と記録だけ）。

- P8g-2 の T4 の速さ: 40×256・20 万履歴で 42.5 µs/履歴（`p8g2/t4/timing.json`）。8×10⁷ 個の核の時間は約 57 分。

- P8g-2 の GPU の 1 回の呼び出しの上限は 200,000 履歴（P8g-1 から継承）。P8g-2 の書き出し（`p8g2.py export`）は関門 0・1 の合格と指紋を要求する。
- Colab の運用（mv.md）: CLI で T4、10 分おきに `colab exec` で確認し、そのたびに完了した結果を回収。VM が途中で消えた前例が 3 回ある。完了はログの印で判定（pgrep を使わない）。`colab` の呼び出しには時間の上限。

## 3. 設計

- 新規 `p8g3_colab.py`（T4 の本計算の駆動）、`p8g3.py`（手元: 書き出し・完了の照合）、`p8g3_cli/`（起動・確認。`p8g2_cli` と同じ形）、テスト `test_p8g3*.py`。P8g-2 の核・`p8g2_core`・`p8g2_colab` は `import` して使い、編集しない。
- 種: **820301**（P8f の本計算 820101・P8e の各種・EGS5 の 820001/820201/820202 と重ならない）。履歴番号は 0〜79,999,999。
- バッチの形: 外側のバッチ 100 個 × 800,000 履歴。各バッチは 200,000 履歴の呼び出し 4 回（履歴番号 `b*800000 + k*200000`、k = 0〜3）。**4 回の結果は個別の呼び出しの単位で封印して保存**し（400 ファイル）、合算の側で 4 つずつを 1 バッチにまとめる（保存の単位を小さくして、VM が消えたときの損失を 1 回分に抑える）。
- 起動の大きさ: 40×256（P8g-2 で最速。関門 2 で 3 構成とも合格）。
- 各呼び出しの前に何もしない。VM の最初に 1 回だけ、P8g-2 の関門 2b に相当する短い照合を行う: 同じ VM の GPU の P8g-1 と P8g-2 を 20,000 履歴（`core.SEED2`）、履歴ごとの全出力のバイト一致。合格しなければ本計算に進まない。
- 各呼び出しは `run_health`（P8f と同じ）を通ったものだけ保存。履歴番号ごとの出力回数がちょうど 1（P8g-2 の `visits`）も各呼び出しで確かめる。
- 再開: 既存の封印したファイルは読み直して受領のハッシュと健全性を確かめ、飛ばす。再開したときは、最初の保存済みの呼び出し（b=0, k=0）を回し直して保存値と照合する（P8f の `check_resume` と同じ規則。集計の加算順の違いの範囲）。
- 完了: 400 ファイルがそろい、すべて受領と一致したら `complete.json`（種・総履歴数・呼び出しの一覧とハッシュ・指紋・起動の大きさ・GPU の名前）。
- 記録: 各呼び出しの核の時間を受領に残す（速さの報告用、合否に使わない）。

## 10. Codex レビュー 1 巡の反映（§3〜§9 と食い違うときはこちらが優先）

**10.1 駆動の単純化（参考 13 を採用）。** 駆動は呼び出し `j = 0〜399`、`start = j*200000`、`n = 200000`、種 820301 だけを持つ。外側のバッチは合算のときに `b = j//4` で作る（保存・再開・受領に二重の番号を持たない）。入力は封印済みの P8g-2 の書き出し（`p8g2.py export` の束）をそのまま検証して使い、P8g-3 の新しいコードは「VM の最初の照合・400 呼び出し・回収・verify」に限る。

**10.2 合算の計算（指摘 1・2）。** 各呼び出しの正規化済みの `dose`（形 (220,)）を d_j とし、q_b = (d_{4b}+d_{4b+1}+d_{4b+2}+d_{4b+3})/4、m₃ = mean₁₀₀(q_b)、s₃ = std₁₀₀(q_b, ddof=1)/10。P8f の 100 ファイルの `dose` から m_f・s_f（P8f の既存の解析 `p8f.py:328` と同じ）。GPU の合算は m_G = 0.2 m_f + 0.8 m₃、s_G = √((0.2 s_f)² + (0.8 s₃)²)。EGS5 も同じ規則（重み 0.6・0.2・0.2）。SEM の加重平均や、生の `p8_batches` を正規化済みの `dose` と同じに扱う実装はしない。
- 入力の検証: P8f の受領・完了・関門、P8g-3 の受領・完了・セッションの関門（10.3）、EGS5 の封印と追加計算の記録、層・密度・材料の束・スペクトル・単位・ビンの配置を確かめてから合算する。P8f と P8g-3 は核の指紋が違うのが正常なので、`identity` 全体の一致は要求しない（物理の入力の一致と、それぞれの核の合格の記録を別に確かめる）。
- 比較の定義は抄録の積層の定義（PDD の基準は抄録で採用した水の基準のビン。鉛を含む全体の最大ではない）。2 ビンの統合は各バッチの中で線量を統合してから SEM を計算する（通常の層 0.1→0.2 cm、鉛 0.05→0.1 cm。層の境界をまたがない）。
- 抄録の積層の数値の再現（Codex が保存値から 0.2303%・1.451%・0.3167%・2σ 超 10/220 を再計算）は、本計算の前に Claude が自分のスクリプトで行う。
- χ²（220 点・19 ブロック）は名目の p 値として報告し、220 点の比較をブロックの判定や同等性の証明に読み替えない（参考 12）。

**10.3 VM ごとの関門の記録（指摘 3）。** VM の最初の照合ごとに固有のセッション ID と不変の関門の記録（`session_<id>.json`）を作る。各呼び出しの受領はそのセッション ID を参照する。回収は**関門の記録を先に**行う。再送の前と最終の verify で、すべての受領が参照する関門の記録が手元にあって合格していることを確かめる（stats10mv の 16 バッチの事故の再発防止、`colab_cli.require_sessions` と同じ考え方）。

**10.4 保存と回収の途中切れ（指摘 4・5）。** VM では受領（JSON）まで書けた組だけを公開する（npz を一時名で書き、受領を書いたあとで公開名に移す、または受領のある組だけを列挙する）。手元では一時名に取得し、ハッシュ・条件を確かめてから確定する。npz だけ／受領だけの組は完成と数えず、再計算の対象にする。検証済みの組は上書きせず、内容が違えば拒否する。回収は**増分**（未回収の組だけ）にする。完了の判定はファイル数ではなく、期待する 400 個の呼び出し ID と封印された組の集合で行う。VM が消えたときに失うのは「前回の回収以降に VM で保存した分」（最大で約 10 分 ≈ 70 呼び出し）で、それは再計算する（「1 回分」とは書かない）。

**10.5 再開の照合（指摘 6・7・10）。** 再開の照合は P8f の `check_resume` の規則（整数は一致、浮動小数点は加算の回数と絶対値の和の上限）を新規側のアダプターで使う。GPU の結果に必要な配列（`_groups_d`・`_groups_i`・`_absolute`・`additions`）は保存する。手元の CPU 版にはそれらがないので、関門 0 の CPU の駆動は保存・封印・完了の照合・スケジュールの試験に限り、再開の数値照合は GPU で試す。再開の照合に使う呼び出しは、手元にある検証済みの最小の ID（0 個なら照合なしで新規）。関門 0 のバイト一致は数値の配列だけに適用し、時刻・計算時間・再開の記録は仕様の検査にする。

**10.6 スケジュールの検査（指摘 8）。** 実際の呼び出しの引数を記録する試験で、400 個すべての `(n, seed, start)` と受領が一致し、履歴の区間に重複・欠落がないことを確かめる（全部 `start=0` を渡して受領に予定の値を書く故障 p4 を拒否する）。各呼び出しの `visits` の検査の結果（すべて 1）を受領に残す。

**10.7 T4 の再開の関門と故障（指摘 7）。** 本計算の前に T4 で小規模に「保存 → VM の停止 → 回収 → 別のセッションへ再送 → 再開の照合」を必ず行う（1c を条件つきから必須に）。故障の注入を追加: 再開の照合で整数の不一致・許容幅を超える浮動小数点の不一致を拒否、`visits=0` と `visits=2` をそれぞれ拒否、関門が不合格・関門の記録が欠けた既存の結果を拒否、保存・転送の途中の停止から復旧。核の内部の経路は再検証しない。

**10.8 停止の方針（指摘 9）。** 次でも止める: `visits` の異常、再開の照合の失敗、受領の条件の不一致、関門の記録の欠落、合算前の χ² の p < 0.001（合算と抄録の更新に進まない）。VM 側の状態は、成功・失敗のログの印に加えて、駆動のプロセスの消失（PID を控えて確かめる）を異常として検出する。手元の見張りは、取得の失敗や確認の最終失敗でも回収と `colab stop` まで行う。

**10.9 既存の関門の回帰（指摘 11）。** §7 の `p8g2 local`・`p8g local`・`p8f local` は既存の段階の `gate0.json` を書くので、一時コピーの中で実行し、元の核と記録のハッシュが変わらないことを確かめる（P8g-2 の実装と同じ手順）。
