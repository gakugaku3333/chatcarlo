## 目的

今の GPU の駆動（`p5j_warp`）は、1つのワープに32の履歴を固定し、その32本が全部終わるまで同じワープで回す。各状態（P/C/E/H）の遷移は、その状態にいるレーンだけが行う。このため、履歴の長さの違いと状態の混ざりで、働くレーンが少ない（実測 5.21/32）。

P5k では、**ブロックの中に履歴の置き場（スロット）を持ち、毎回、同じ状態にいるスロットを詰めてワープに割り当てる。終わったスロットにはすぐ次の履歴を入れる。** 遷移の関数（`p5j_kernel.h`）は変えず、駆動だけを替える。各履歴の計算の順は P5j と同じなので、**各履歴の結果は P5j とビット単位で同じ**になる見込み（関門で確かめる）。速さは報告のみで、採否はユーザーが決める。

この計画が答える問い: 「各履歴の結果を変えずに、ワープの中で働くレーンを増やすと、T4 でどれだけ速くなるか。状態をスロットに置くことで起きるメモリの読み書きの増え方が、それを打ち消さないか」。

## 0. 前提事実（2026-10-17 に Claude が手元で確認）

### 0-1. 状態の並び（CPU のトレース、P5j の核そのもの）

`p5j_trace`（CPU、Philox、`core.SEED`、`core.MAXSTEPS`、履歴番号 7,000〜39,767 の 32,768 履歴、トレースのあふれ 0）で、各遷移で実行した状態を記録した。

```
histories 32768 transitions mean 704.1213684082031 max 4612
phase share P,C,E,H [0.0377, 0.9332, 0.0276, 0.0014]
C transitions: to E 0.0296, to C 0.9704, other 0.0000
```

- 遷移の 93% は C（荷電粒子の1歩）。1履歴あたり平均 704 遷移、最大 4,612。
- 4,096 履歴（7,000〜11,095）でも割合は同じ（P 0.0375・C 0.9336・E 0.0275・H 0.0014）。

### 0-2. 割り当て方ごとの理想の稼働率（上のトレースを使った模擬。遷移1回を1単位と数える）

稼働率 = 全遷移数 ÷（実行したワープの回数 × 32）。遷移の中の分岐による発散は数えていない。

```
fixed warps (all N): 0.189                       ← 今の方式（32履歴を固定し、状態ごとに1回ずつ）
block pool R= 256, 10 histories/slot: 0.739       ← ブロックに256スロット、状態ごとに詰めて32ずつ
block pool R= 256, 40 histories/slot: 0.768
block pool R= 512, 10 histories/slot: 0.864
block pool R= 512, 40 histories/slot: 0.890
block pool R=1024, 10 histories/slot: 0.921
block pool R=1024, 40 histories/slot: 0.933
```

参考（4,096 履歴）: 詰め直さずに、終わったレーンにすぐ次の履歴を入れるだけの方式（補充）は 0.33〜0.41。詰め直しより低いが、同期もスロットも要らない安い代替案なので、比べる変種に加える（review1 指摘6、§5）。

- 今の方式の模擬 0.189 × 32 = 6.05 レーン。実測（P5j の地図）は全命令 5.21、倍精度 4.70。この比 0.861（全命令）・0.777（倍精度）を、遷移の中の分岐による目減りの目安とする（仮定: 詰め直した後も同じ割合で目減りする）。
- R=256・10履歴/スロット（10万履歴、T4 の 40 SM × 256 スレッドに相当）: 0.739 × 0.861 = 0.636（20.4 レーン）、倍精度は 0.739 × 0.777 = 0.574（18.4 レーン）。
- **ワープ命令の数は、理想では 0.739/0.189 = 3.9 分の1。** 時間が倍精度のワープ命令に比例するなら（P5i・P5j の観察。n=3 の仮説）、上限の目安は ×3.9。
- **これは上下限ではなく、仮定つきの参考の場面である**（review1 指摘5）。0.739/0.189 は「遷移を等しい費用とみた、ワープの呼び出しの数」の減り方で、ワープ命令が同じ割合で減るとは限らない。実測のレーン数との比 0.861・0.777 には、状態ごとの費用の差や駆動の命令も混ざる。
- 遅くなる方向の先例: P5e で履歴を歩数で並べ替えたら 33% 遅くなった（×0.75。別の方式の実測なので下限ではない。もっと遅くなることもありうる）。主な危険は、スロットの読み書きが散らばること（0-3）、ブロックの同期での待ち、レジスタに置けていた値の読み書きが増えること（review1 指摘3）。**実時間の上下限は評価していない。**

### 0-3. 1スロットに要る記憶（clang++、`-DP5_RNG_PHILOX`、`sizeof`）

```
P5State 184 P5jState 18136 RngState 24 P5bLocal 6560 P5Output 80 P5Diagnostic 24
```

- 1スロット ≈ 18,136 + 6,560 + `nspec_work` 5,120 + 128 ≈ **29,944 バイト**（今のローカルメモリ 30,800 バイト/スレッドとほぼ同じ）。
- R=256/ブロック、1 SM あたり1ブロック、40 SM: 10,240 スロット × 29,944 ≈ **307 MB**（T4 の 15 GB に対して余裕。L2 の 4 MB には入らない。今のローカルメモリも同じ量で、L2 の当たり 99% は「よく使う部分が小さい」ため）。
- L2 の当たり 99% の理由（よく使う部分が小さい）は仮説。容量の計算は概算。
- 今はローカルメモリが「スレッドごとに交互に並ぶ」配置なので、32レーンが同じ場所を読むと1回にまとまる。詰め直すと、ワープの中のレーンがばらばらのスロットを読むので、**まとまらなくなる**。これが速くならない最大の理由になりうる。配置（構造の配列か、配列の構造か、よく使う部分とそうでない部分の分割か）は設計の選択として §4 で決め、地図でメモリの帯域と L2 の当たりを報告する。

### 0-4. 遷移の関数が書く先（ビット一致の根拠）

`p5j_transition` → `p5j_particle`・`p5j_charged`・`p5j_end`・`p5j_finish` が書くのは、その履歴の `P5jState *q`、`RngState *s`、`P5Output *o`（P5bLocal を指す）、`P5Diagnostic *d` だけ。共有の書き込みは検査版の `t->log_counts`（`atomicAdd`、数え上げで順序に依らない）だけ（`grep -n "log_counts\|atomic"` で確認）。表 `t` は読むだけ。

→ 駆動が「どのスロットを、いつ、どのレーンで」進めるかを変えても、各履歴の中の遷移の順と乱数の呼び出しは同じにできる。ただし次の**所有の契約**を守ることが条件（review1 指摘1）:
  - 履歴に属するものは `P5jState`・`RngState` だけでなく、`P5bLocal`（`P5Output` の指す先すべてと `maxdepth`）、`nspec_work[640]`、`P5Diagnostic` の `used`・`overflow` と記録先。`P5Output`・`P5Diagnostic` はポインタを含むので、スロットに保存せず、**遷移を呼ぶたびにそのスロットの記憶を指すように組み立てる**。
  - スロットは固定し、キューにはスロット番号だけを入れる。1つのスロットを同時に進めるのは1スレッドだけ。
  - スロットに元の入力の添字 `i` を持たせ、乱数は `start+i`、履歴ごとの出力の先は `i`、行は `p5b_row(i,n)`。
  - 履歴の終わり（D になった時）の処理は `p5j_warp` の末尾（`calls`・`maxdepth`・`diag_used`・`nspec_index`）と、`p5j_run_kernel`・`p5j_per_history_kernel` の書き出しを同じ式で行い、終わってからスロットを使い回す。輸送の失敗で H を通った履歴も同じ。
  - 浮動小数点の指定（`--fmad=false`・`-ffp-contract=off`）と端末での定数の初期化（`p5j_initialize_kernel`）は P5j と同じ。`#include` しただけで生成される命令が同じとは限らないので、T4 の関門2は省かない。全体の和は、今と同じく履歴ごとの `atomicAdd` で足すので、足す順は今も不定（P5b 以来の扱い。`brems[1]` だけ計算した上限の中で比べる）。

## 1. 判定ルール（事前に固定）

関門の鎖は P5g〜P5j と同じ。比べる相手は P5j。

各関門が何を示すかを分ける（review1 指摘2）。保存済み100バッチへの鎖は、凍結した P5j の CPU の経路がすでに示している（RESULTS_P5J の関門1）。P5k の関門は「**新しい駆動が、各履歴について P5j と同じ出力を作る**」ことを、履歴ごとの出力で示す。履歴ごとの出力（`P5bLocal`）どうしなら、`brems[1]` も含めて全項目をビットで比べられる。

- **関門0（CPU、手元）**: 駆動のスロットの管理（詰め直し・補充・添字と行の対応）を CPU でも動く共通のコード（`P5_FN`）にし、CPU でブロックとワープを順に模擬して動かす。次をすべて満たす。
  - 全履歴がちょうど1回ずつ実行される（P5e の E3 と同じ形: n < スロット数、n がスロット数の倍数でない、n=1、start ≠ 0、続けて呼ぶ）。各変種・各 R・各 K で。
  - 添字から行（バッチ）への対応が P5j と同じ。
  - 小さい輸送（n=2,000、start=7,000）で、各履歴の `P5bLocal` 全項目が、P5j の履歴ごとの参照（`p5j_history` を `p5b_history` と同じ形で包んだもの）とビット一致。トレース（`p5j_record` の記録）も履歴ごとに一致。
- **関門1（M3、clang++）**: 保存済みの P5a Philox 100バッチと同じ seed・添字（10万履歴×100）で、CPU の模擬の駆動の各履歴の `P5bLocal` が P5j の参照と全項目ビット一致（通常版・検査版）。加えて、模擬の駆動の履歴ごとの出力を添字の順に足した値が保存済みバッチと一致すること（`brems[1]` は P5b の上限の中、他はビット）を報告する。検査版の `log_counts` の合計は P5j の関門1と同じ値。
- **関門2（T4）**: 2万履歴で、各変種の履歴ごとの出力が `p5j_per_history_kernel` の出力と全項目ビット一致。合算の核の10出力は P5j と一致（`brems[1]` は計算した上限の中）。
- **関門3（T4）**: P5c の C0〜C4（1,000万履歴）。識別に `nspec=20` を含める。
- **速さ（報告のみ）**: 同じセッションで P5j と各変種を交互に3回ずつ、10万履歴、核の時間の中央値。地図（ncu）で、ワープ命令の数・参加レーン（全命令／倍精度）・global と local の要求量と実際の転送量・L1 と L2 の当たり・バリアでの待ち・実際に常駐したブロックとワープの数・レジスタ・ローカルメモリを P5j と並べる。初期化・終わりの合算・詰め直しの時間も分けて記録する。どれも説明の材料で、合否には使わない。
- 関門3と地図は、関門2に合格した変種のうち、交互の測定で一番速かった1つ（P5j より遅ければ詰め直しの基本形 Q1）について行う。
- **停止条件**: どの関門でも不一致が出たら、速さの測定に進まず止めて報告する。原因の説明は Claude が独立に確かめるまで採らない。

## 4. 設計の選択（review1 の推奨を採用）

1. **詰め直しの範囲**: ブロックの中。共有メモリには状態ではなくスロット番号を置き、各回の境目で次のキューを作る。全体のキューや自作の全体の同期は今回は作らない（C を K 回進めてから全体で振り分け直す複数の核の方式は、別の計画の候補）。
2. **R とスレッド数**: 基本は R=256・256スレッド。比較に R=512（1スレッドが2スロット）を加える。R=1024 は今回は作らない。
3. **状態の置き場**: スロットごとにまとめた配置（AoS）をグローバルメモリに固定して置き、番号だけ並べ替える。同じ状態のキューの中はスロット番号の順にする。よく使う部分を分ける配置は、凍結した `P5jState *` の関数では直接できないので、今回は作らない（地図で必要と分かれば別の計画）。
4. **1回の詰め直しで進める遷移の数**: 1遷移を基本形とし、C だけ「C にいる間、最大 K 回」続ける方式（K=4・8）を比べる。C を出たらすぐ止めて次の詰め直しに回す。

## 5. 詳細

### 5-1. 変種（すべて新規の `p5k_*`、遷移の関数は `p5j_kernel.h` のまま）

| 名前 | 方式 | R | C の連続 K |
|---|---|---|---|
| F（補充） | 今の `p5j_warp` と同じ ballot の駆動。D になったレーンは書き出しの後、全体の数え上げ（`atomicAdd`）で次の添字を取り、`p5j_init` で始める。全32レーンが、取れる添字がなくなり全員 D になるまで ballot に加わる | ー | 1 |
| Q1 | ブロックの中で詰め直し | 256 | 1 |
| Q4 | 同 | 256 | 4 |
| Q8 | 同 | 256 | 8 |
| Q1-512 | 同 | 512 | 1 |

### 5-2. 詰め直しの駆動（Q 系）の手順

1. 起動時に、ブロックごとのスロット R 個を `p5k_slot`（`P5jState`、`RngState`、`P5bLocal`、`nspec_work[640]`、`P5Diagnostic` の `used`・`overflow`、添字 `i`、使用中の旗）の配列としてグローバルメモリに取る（ホストが確保して渡す。`R × ブロック数 × sizeof` を記録する）。
2. 各スロットは全体の数え上げで添字 `i` を取り、`i<n` なら `rng_init(seed,start+i)`・`P5bLocal{}`・`nspec_work` を0・`p5j_init`（`batch0=0`、トレースなし）。`p5j_warp` の始めと同じ式。
3. 各回: (a) 全スレッドが自分の受け持つスロットの状態を読み、共有メモリの状態ごとのリスト（P・C・E・H）にスロット番号を加える（スロット番号の順になるように、ワープごとの ballot と前置和で位置を決める）。`__syncthreads`。(b) P・C・E・H の順に、リストの k 番目をスレッド `k mod 256` が受け持ち、そのスロットの記憶を指す `P5Output`・`P5Diagnostic` を組み立てて `p5j_transition` を1回（C なら C にいる間 K 回まで）呼ぶ。D になったら 5-3 の書き出しをして、次の添字を取ってスロットを始め直す（新しい履歴は次の回のリストに入る）。`__syncthreads`。(c) 使用中のスロットがブロックになく、添字も尽きたら終わる。
4. 1つの状態のリストは、32ずつに分けて、ワープの中が同じ状態になるようにする（リストの長さが32の倍数でないときの端は、そのワープの一部が休む）。

### 5-3. 履歴の終わりの書き出し

`p5j_warp` の末尾（`L->calls=s.calls`、`maxdepth`、`diag_used`、`nspec_index`）を同じ式で行い、合算の核では `p5j_run_kernel` の `atomicAdd`・`atomicMax` の列を、履歴ごとの核では `p5b_store(&L,i,...)` を、同じ式で行う。`P5B_MERGE_FAULT` も同じ扱い（P5c の故障の検査に使う）。トレースの記録（監査の核）は、各履歴について `p5j_audit_kernel` と同じ記録を同じ添字の場所に書く。

### 5-4. CPU の模擬（関門0・1）

5-2・5-3 の手順を `P5_FN` の共通コード（`p5k_driver.h`）にし、CPU では「ブロック数1、スレッドを順に回す」形で動かす。ワープの ballot は、32スレッドの状態を配列で持ち同じ順に処理する関数で置き換える。F も同じ共通コードで模擬する。CPU の参照は `p5j_history` を `p5b_history` と同じ形で包んだ関数（新規、`p5k_cpu.cpp` の中）。

### 5-5. Colab（「すべてのセルを実行」1回）

`p5k_colab.ipynb` が、Drive の `viveMonte/p5/p5k/`（ソースの zip と手元の関門1の記録）と既存の `viveMonte/p5/p5b/` の入力の束を読み、次を順に行う。前の段の記録が合格でなければ止まる。

1. 関門0（T4）: P5j と同じ関数の比較（P5j の関門0の関数をそのまま呼ぶ）、スロット管理の E3 型の検査（全変種、n<R、n が R の倍数でない、n=1、start≠0、続けて呼ぶ）。
2. 関門2: 全変種で2万履歴、履歴ごとに `p5j_per_history_kernel` と比較。監査の核のトレースも比較。

## 7. review2 の反映（§5 と食い違うときは §7 を優先する）

1. **持ち越す値**: `maxdepth` は `L.maxdepth` を持ち越し先とし、遷移を呼ぶ前に `o.maxdepth=L.maxdepth`、後に `L.maxdepth=o.maxdepth`。`P5Diagnostic` の `used`・`overflow` も同じくスロットに持ち、呼ぶ前に戻し、後に書き戻す。スロットを使い回すときは、これらと `P5bLocal`・`nspec_work`・使用中の旗をすべて初期値に戻す。
2. **監査のトレース**: 監査版では、初期化（`p5j_init` の `from=-1`）から履歴ごとの `P5jTrace` を渡し、`used`・`overflow` をスロットに持ち越し、終わりに `from=5` の印とメタ情報を `p5j_audit_kernel` と同じ形で書く。通常版だけトレースなし。CPU の参照も `p5j_history` の後に `from=5` の印を同じ形で加える。完全一致の検査では `overflow=0` を要求し、容量不足は不合格（切り詰めた一致を合格にしない）。
3. **同期をまたぐ CPU の模擬**: 共通コードの単位を「スロットの初期化」「分類（リストづくり）」「リストの1仕事（遷移を1〜K回、D なら書き出しと補充）」「終わりの判定」に分ける。CPU は「全スロットの分類 → 各状態のリストを順に全部実行 → 終わりの判定」を段階ごとに回し、GPU は同じ段階の間で `__syncthreads`。各回のリストは、その回の始めの状態から一度だけ作り、その回の中で状態が変わったスロットを同じ回のリストに足さない。受け持ちは `for(k=tid;k<count;k+=blockDim.x)`。CPU の模擬は複数ブロックも順に模擬する（添字の払い出しはブロックをまたいで1つの数え上げ）。
4. **関門2の合算**: 履歴ごとの出力は全項目ビット比較。合算の核（P5j・各変種）は、同じ履歴ごとの出力を基準に、既存の `core.c3`（加算の誤差の上限）でそれぞれ検査する。`brems[1]` だけの特例にはしない。T4 でも通常版・検査版の両方で履歴ごとに比べる。
5. **足すテスト**（`test_p5k.py` と T4 の関門0）:
   - 複数ブロックでの払い出し・重複・欠落。n は総スロット数 B×R の直前・一致・直後も。
   - 状態のリストの長さ 0・1・31・32・33・255・256・257・511・512（R=512 の2巡目、空のリスト、端のワープ）。強制的に作る試験用の入口でよい（遷移の代わりに状態を書き換えるだけの模擬の遷移を使い、輸送の結果は使わない）。
   - 小さい `maxsteps` による P→H・C→H→D の失敗の履歴の書き出しと、その直後のスロットの使い回し。
   - 同じ確保領域で n を大→小→大と続けて呼び、数え上げ・使用中の旗・診断・最大深さが残らないこと。
   - 監査のトレースの容量不足の検出。
6. **関門1の範囲と保存**: 各変種を通常版・検査版で検査。`log_counts` は、関数の比較と参照の実行の分を除き、同じ10万履歴の輸送の分だけを比べる。参照の生成 → 各変種と比べる → 添字の順に足していく、を小分けに行い、正常時は要約だけを保存し、不一致の時はその履歴だけを保存する。比べるのはパディングを除く全フィールド（構造体全体の `memcmp` にしない）。
7. **時間の内訳**: 正式な比較は核全体の時間。初期化・詰め直し・書き出しの内訳は、別の計測版による参考の値とし、スレッドごとの `clock64` の差の合計を経過時間の内訳として足し合わせない。
8. **再現の数値**: `p5k_emulate.py` の数値の再現は報告のみ（テストにしない）。テストは、模擬の中で遷移の総数が保たれること、稼働率が 0〜1 に入ることなどの不変条件だけ。
9. **単純化**: F はレーンの中で状態を持ち（スロットを使わない）、Q 系だけが固定 AoS のスロットを使う。履歴ごとの書き出しは既存の `p5b_store`、合算の検査は `core.c3` を使う。
10. 関門3の前の交互の測定で選ぶ候補は「関門2合格・関門3未確認」として扱う。
