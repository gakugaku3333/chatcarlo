## 1. 目的

P8f の積層の核（水–肺–水–骨–水–鉛、Mohan 10 MV）は T4 で約 333 µs/履歴で、水の核 P5k F（約 23 µs）の約 15 倍遅い。
積層の GPU の統計を 1×10⁸ 個まで増やせる速さにする（目標は §5）。そのために、**検証の方針を「前の核とのビット一致」から「4 段の検証」に替える**（ユーザー決定 2026-10-24、下記）。

この計画が答える問い: 「表を引く形と GPU 向けの実行の形にした積層の核は、EGS5・P8e との検定に合格したまま、何倍速くなるか」。

## 2. ユーザーの決定（2026-10-24）

- 「ビット単位で一致することにこだわるのがボトルネック。正確性を保ちながら他の方法で効率的に」→ 次の 4 段の検証に替える（「その方針で進めて」）。
  1. 表の精度: 表から引いた物理量を、細かい格子で元の関数と比べる（乱数を使わない、手元で数分）
  2. 部品ごとの照合: 同じ乱数を新旧のサンプリング関数に入れ、許容幅つきで比べる。多数回の分布の形も比べる
  3. 履歴ごとの健全性: エネルギーの収支・範囲・スタックなど、P8f の既存の関門
  4. 結果の検定: 保存済み EGS5 と P8e の CPU 試作に対し、P8f の判定 A・B と同じブロックの検定
- 誤差の予算: 表・補間による系統誤差は判定の基準（ブロックの |差| ≤ 1%、SEM ≤ 0.33%）の 1/10 以下（0.01% 程度）。
- わざと壊した版（故障の注入）が 1〜4 のどこかで必ず止まることを確かめる。
- ビット一致を守るための常設ルール（mv.md の P5i「表の定数の log はホストで計算して送らない」など）は、**新しい積層の核では外す**。水の核（P5k F）・P8f・これまでの記録はそのまま。

## 4. 方針（地図の結果: A → B → D の順。C は A・B と合わせて測り直す）

- A. 表を引く形に揃える: 材料ごとに、エネルギーの log の等間隔の格子の表をホストで作る（自前の物理から。EGS5 の PEGS の出力は使わない — 公開システムは EGS5 に依存しない）。輸送の中は区間番号の直接計算と 1 次補間だけにし、二分探索と log の計算を除く。
- B. 実行の形: 水の核で効いた P5g（状態機械）と P5k F（終わったスロットへの補充）を積層の核に持ち込む。
- C. 起動の大きさ: 40 ブロック × 128 の固定を見直す（コード変更なしで測れる。実行中の試験で効果を確認）。
- D. 集計: 1 ステップの 3 種のビン（220・108・430）への分け方。地図で重ければ扱う。
- 新しい核は新しいファイル（`p8g_*`）に作り、P8f のファイルは変更しない。CPU 版（同じソースを CPU でもビルド）を持ち、検証 1〜3 は手元で回す。

## 5. 判定のルール（事前登録の案）

- 正しさ: §2 の 4 段すべてに合格。4 段目は P8f と同じ（19 ブロックすべて |差| ≤ 1% かつ SEM ≤ 0.33%、固定 Dref）。
- 誤差の予算: 1 段目の表の最大相対誤差 ≤ 1×10⁻⁴（量ごとの上限は詳細で決める）。
- 故障の注入: 用意したすべての故障が 1〜4 のどこかで止まる。
- 速さ（報告。合否にしない）: 同じセッションで P8f と交互に 3 回、2 万履歴の µs/履歴の中央値。目標の目安は 1×10⁸ 個が T4 で数時間（約 100 µs/履歴以下）。

## 8. Codex 骨子レビュー 1 巡の反映（2026-10-24）

致命 0。ビット一致をやめる決定に異議なし（「遅さの主因がビット一致」とまでは測定から言えない、との留保つき）。

- **順番の変更（代替案を採用、ユーザー確認待ち）**: 全面的な再格子化を初手にせず、段階に分ける。
  1. **A1 既存の格子のまま前計算**: 表の `log(x)`・`log(y)`・区間の傾き・しきい値の開始位置をホストで用意し、二分探索のループ内の `log` と補間の `log` を除く（行 692 の 11.4% と補間の log）。格子・吸収端・しきい値の扱いは変わらないので、誤差は丸めの水準。
  2. **B 状態機械と補充**（P5g・P5k F 型）。表の物理は A1 のまま。
  3. **A2 必要な量だけ再格子化**（滑らかな量。吸収端・しきい値・GS の難しい部分は従来の方式を残す）。A1・B の実測のあとで要否を決める。
  - 各段で「表の変更だけ／実行の形だけ／両方」を小規模に交互測定し、寄与を分ける。4 段の検証の全部は最終候補に課す。
- 指摘 1（不連続点）: 再格子化する場合は吸収端・CUT・しきい値で区間を分け、元の節点・境界・`nextafter` の両隣、ゼロの領域、端のクランプを第 1 段で検査する。GS は T・K・u の全領域。
- 指摘 2（誤差予算）: 個別の表に加え、輸送が実際に使う合成量（連続阻止能、全相互作用率、分岐確率、GS のゼロ散乱確率）を比べる。ゼロ近傍は絶対誤差も使う。線量 0.01% を主張する場合は旧表／新表／より細かい表の感度計算を根拠にする（第 4 段の統計では測れない）。予算の数値: 表の相対誤差 ≤ 1×10⁻⁴、線量への系統誤差の目標 0.01%（1% 基準の 1/100、SEM 0.33% の約 1/33）。
- 指摘 3（サンプラー）: 材料・エネルギー・K ごとの条件付き分布、GS の μ=1 の点質量・平均 1−μ・後方、同時に作るエネルギーと角度・二次粒子の組、離散事象率と平均損失が阻止能の分解を再現すること、棄却法の包絡が上から覆うこと。
- 指摘 4（健全性の穴）: 履歴番号ごとの実行・完了回数（欠落・重複の拒否）、Philox の既知入力、線分とビンの重なり・層境界の点付与の手計算の小例、親粒子の退避・再開の状態固定試験、履歴別の出力の和と群の集計の照合（丸めの上限つき）。
- 指摘 5（GPU 固有）: 第 1・2 段の代表点・境界点と第 3 段の管理・集計の検査を T4 でも行う（半端なワープ、スロット数の直前／一致／直後、補充、連続呼び出し）。検証した表・配置・コンパイル指定と計時・本番の構成を指紋で結ぶ（P8f の関門 2b・2c・2e を再利用）。
- 指摘 6（故障の注入）: 故障と検出器の対応表を先に決める（吸収端の側の反転、しきい値以下への漏れ、材料の表の取り違え、境界でのキャッシュ未更新、GS のゼロ散乱確率、乱数の使い回し、隣のビンへの付与、履歴の重複・飛ばし、補充時の消し忘れ、群への加算の欠落）。正常版の通過・故障箇所への到達・意図した検出器での拒否を記録。ビルド失敗・ハッシュ不一致は数えない。
- 指摘 7（速さ）: 2 万履歴に加え本番と同じ大きさのバッチでも交互に測る。初期化と継続の速さを分ける。比較相手は固定起動の P8f と 40×256 の P8f。倍率は第 4 段に合格した構成について報告。
- 指摘 8（地図の読み方）: 「表の参照・補間を含む関数に停止標本の約 6 割が帰属した。A を試す根拠にする」と書く。停止標本は待っている命令に付くので原因の行とは限らない。行の情報付きのビルドの命令総数（8.02×10¹⁰）が通常の測定（6.13×10¹⁰）と違う理由は未確認。生の CSV と集計は `~/.cache/chatcarlo/p8f_prof/line/`（`source2.csv`、`linemap_summary.txt`）。
- 指摘 9: 「表の定数の log を除き、そのエネルギーの `log(E)` は 1 回だけ計算して使い回す」と書く。

## 9. A2（表の格子の作り直し）の扱い — 保留中の高速化の候補（2026-10-24）

- **状態: 未着手・保留。** A1（P8g-1、×1.25〜1.31）と B（P8g-2、P8g-1 の ×4.68、T4・40×256・20 万履歴で 42.5 µs/履歴）で、積層の 1×10⁸ 個が約 1.2 時間になり、当面の目的を満たしたため（ユーザー了承 2026-10-24）。
- **高速化の可能性の根拠（P8f の行の地図、`docs/validation/mv/p8f_prof/linemap_summary.txt`）:** A1 で除いたのは表の定数の `log` だけで、**表の二分探索は残っている**。P8f の時点で時間の標本の割合は `lower_bound` 9.9%、`p5_gs_mu_cached` 10.7%（log 2 回と区間探し 2 回）、`p5_bracket` 4.9%、`quantities` 7.9%、`p5_table_rates` 5.8%、`interp` 3.6%、`p5_pair_interp` 2.1%（しきい値の線形の走査を含む）。エネルギーの log の等間隔の格子に作り直せば、区間番号を `(log E − log E0)/Δ` で直接計算でき、探索を除ける。
- **未確認の点:** B のあとの核で、この割合がどう変わったかは測っていない（P8g-2 の ncu は子プロセスの import の誤りで取れていない）。B で実行の形が変わったので、残っている割合は P8f と違うはず。着手する前に P8g-2 の行の地図を取り直し、探索が今も大きいかを確かめる。
- **着手するときの条件:** 格子が変わるのでビット一致は成り立たない。上位の方針どおり 4 段の検証（表の精度・部品の照合・履歴ごとの健全性・EGS5 と P8e に対する検定）と故障の注入を使う。Codex の骨子レビュー（§8）の指摘 1〜3 がここに当たる: 吸収端・しきい値で区間を分け、元の節点・`nextafter` の両隣・ゼロの領域を検査する。合成量（連続阻止能・全相互作用率・分岐確率・GS のゼロ散乱確率）でも比べる。条件付きのサンプリング分布で比べる。滑らかな量だけを作り直し、吸収端・しきい値・GS の難しい部分は従来の方式を残す段階案が推奨。
- **やる価値が出る場面:** 積層の統計をさらに増やす、照射野・他の積層へ広げるなど、GPU の時間が再び律速になったとき。
