## 目的

F は倍精度の回路で頭打ちになっている。倍精度の命令1回あたりの参加レーン（10.19/32）を増やせば、時間は縮む見込み。ブロックの同期を使わずにレーンを増やす2つの方法（C を K 回まで続ける、ワープの中で置き場を 32×m 個持って詰め直す）を、各履歴の結果を P5j と同じビットに保ったまま試す。速さは報告のみで、採否はユーザーが決める。

この計画が答える問い: 「ブロックの同期なしで詰め直すと、置き場をグローバルメモリに移す費用を払っても F より速くなるか。その費用はどれだけか」。

### 0-2. Q 系の地図（RESULTS_P5K.md 末尾）

Q は F より命令が 7〜14% 少なく、参加レーンも多い（Q1 12.98）。それでも遅いのは、各回の終わりの `__syncthreads` で待つため（待ちの標本の 37〜47%）。読み込みの散らばり（1要求あたり 9.1 セクタ、F は 2.25）は、メモリの待ちを増やしていなかった。

### 0-3. 模擬（P5j の CPU のトレース 32,768 履歴から、ランダムに選んだ 32×m×10 履歴、4回の平均と標準偏差）

1つのワープが 32×m 個の置き場を持つ。各回、状態ごとに置き場を32ずつ組にし、C は K 回まで続ける。組の費用は、組の中で一番長く続くレーンの回数とする。終わった置き場には次の回に新しい履歴が入る。スクリプトは `data/p5l_emu4.py`（追跡外）で、実装では `p5l_emulate.py` として追跡する。

```
m=1 K=1 util 0.385 (±0.005)     m=2 K=1 util 0.473 (±0.005)     m=4 K=1 util 0.612 (±0.005)
m=1 K=2 util 0.430 (±0.014)     m=2 K=2 util 0.546 (±0.011)     m=4 K=2 util 0.675 (±0.005)
m=1 K=4 util 0.461 (±0.010)     m=2 K=4 util 0.569 (±0.011)     m=4 K=4 util 0.680 (±0.007)
m=1 K=8 util 0.412 (±0.024)     m=2 K=8 util 0.502 (±0.011)     m=4 K=8 util 0.703 (±0.003)
```

- m=1・K=1 が F に当たる（0.385。P5k の模擬の 0.376〜0.42 と同じくらい）。
- K=4 がどの m でもほぼ最良。m=4・K=4 は 0.680（F の 1.77 倍）。
- 注意（P5k の教訓）: 模擬の稼働率は速さの予測ではない。Q は模擬で 0.74 だったが、T4 では F より遅かった。実測の参加レーン／模擬の値は、F で 0.83、Q1 で 0.55。

### 0-4. 置き場の大きさ

1つの置き場（`P5kSlot`）は 29,872 バイト。m=4 で1ワープ 128 個 = 3.8 MB、40 SM × 8 ワープでは 1.22 GB（T4 の 15 GB の中）。m=2 では 0.61 GB。

### 0-5. ビット一致の根拠

P5k と同じ。遷移の関数（`p5j_kernel.h`）と、置き場の初期化・1仕事・書き出し（`p5k_driver.h` の `p5k_initialize`・`p5k_work`・`p5k_finalize`、K を取る）を変えずに使う。P5k の §0-4・§7 の所有の契約をそのまま守る。`p5k_work` は C のときに K 回まで続け、C を出たらすぐ止める（P5k の Q4・Q8 で関門0〜2 合格済み）。

## 1. 変種（すべて新規の `p5l_*`。§6-5 で GK4 を追加し5変種）

| 名前 | 方式 | 状態の置き場 | 確かめたいこと |
|---|---|---|---|
| G1 | F と同じ駆動（ワープの ballot、レーンが自分で補充）。状態を各レーンのローカルではなくグローバルの置き場（1レーン1個）に置く | グローバル | 置き場をグローバルに移す費用だけ（F との差） |
| FK4 | F に C の連続 K=4 を足す | ローカル（F と同じ） | 詰め直しなしで K の効き目 |
| W2K4 | 1ワープが 64 個の置き場を持ち、状態ごとに32ずつ選んで進める。C は K=4 | グローバル | 詰め直しの効き目（m=2） |
| W4K4 | 同上で 128 個 | グローバル | 同（m=4） |

FK4 の補足: 各回、ワープの状態の ballot は今の F と同じ。C のレーンは `p5k_work` の K=4 で進む（C を出たレーンはその場で止まり、ほかの C のレーンを待つ）。

W の手順:
1. ワープごとに 32×m 個の置き場をグローバルメモリに取る。起動時に各置き場が全体の数え上げで添字を取って初期化する（P5k の Q と同じ）。
2. 各回: ワープの32レーンが m 個ずつ自分の受け持つ置き場の状態を読み、ballot と前置和で、状態ごとのリスト（共有メモリのワープ専用の区画）に置き場の番号を番号順に入れる。`__syncwarp`。
3. P・C・E・H の順に、リストを32ずつ組にしてレーンに割り当て、`p5k_work`（C は K 回まで）を呼ぶ。D になったら書き出しと補充をする（新しい履歴は次の回のリストに入る）。`__syncwarp`。
4. ワープの置き場がすべて空で、添字も尽きたら終わる。ブロックの同期（`__syncthreads`）は使わない。

## 2. 判定ルール（事前に固定。P5k §1・§7 と同じ形）

- **関門0（CPU、手元）**: 4変種で、置き場の管理の検査（全履歴がちょうど1回、行の対応、n の端、続けて呼ぶ、植えた故障の検出、リストの長さの端 0・1・31・32・33・63・64・65・127・128）と、小さい輸送（n=2,000、start=7,000）で各履歴の `P5bLocal` 全項目と監査の記録が P5j の参照とビット一致。`maxsteps`=1・2 の失敗の経路と、大→小→大の使い回しも同じ。

- **関門2（T4）**: 4変種で2万履歴、各履歴が `p5j_per_history_kernel` とビット一致、監査の記録も一致、合算は `core.c3` の中。通常版・検査版。

## 6. review1 の反映（§1〜§5 と食い違うときは §6 を優先する）

1. **W の同期**: 初期化の完了から最初の分類の前に、全32レーンで `__syncwarp`。分類の後と、各回の仕事の後にも `__syncwarp`。端の組で休むレーンも同期に加わり、終わりの判定と回の数はワープ全体で同じにする。リストはその回の始めの状態から一度だけ作り、その回の中で状態が変わった置き場を同じ回に足さない（P5k §7-3 と同じ）。
2. **K が本当に効いていることの検査**: 1仕事あたりの遷移の数を直接確かめる。CPU・GPU の両方で、合成の遷移列で `C,C,C,C,C,E` → 最初の仕事が4遷移、次が2遷移（C を1回、E を…ではなく、C を出たらそこで止まる）、`C,E` → 1遷移で止まる、`P→C` → 同じ仕事で C を続けない、を確かめる。変種と（駆動、置き場、m、K）の対応は1か所の表に固定する。
3. **補充とレーンの移動を通す監査**: 少数のワープ（例 1〜2ブロック、各1〜2ワープ）で `n > 総置き場数` とし、レーンの移動・複数の組・補充を通した完全な監査の記録の比較を CPU と T4 の両方で行う。あふれ 0 を要求する。2万履歴の比較とは別に行う（2万履歴は W4 の総置き場 40,960 より少なく、補充を通らないため）。
4. **W の分類の合成の検査**（CPU と T4 の両方）: 各32区間に P/C/E/H/空きを混ぜ、状態ごとのリストが番号順で重複・欠落なし。同じ回に P→C・C→E・E→P と D→補充を起こし、各置き場がその回に1回しか処理されない。同じブロックの一方のワープだけ先に空になる場合。隣のワープの共有メモリの区画が干渉しない。リストの長さの端 0・1・31・32・33・63・64・65・127・128。
5. **5変種目 GK4 を加える**: G1 と同じ駆動・グローバルの置き場で K=4。これで F−G1（置き場の場所）、G1−GK4（K）、GK4−W2K4・W4K4（詰め直し）に分けて比べられる。差は「コンパイラのレジスタの使い方などを含む方式全体の差」として報告する。駆動は2系統にする: F 型（G1・GK4・FK4。置き場の場所と K だけを切り替える）と W 型（W2K4・W4K4。m だけを切り替える。置き場は動かさず番号だけを並べ、`j=32*a+lane` の順の ballot と前置和で番号順を作る）。関門1は5変種で約6〜7時間。
6. **起動の構成を固定**: どの変種もブロック数 40、256 スレッド（8ワープ）。W のワープごとの置き場の添字は `(blockIdx.x*8+warp)*32*m`。総置き場数は G1・GK4 が 10,240、W2K4 が 20,480、W4K4 が 40,960。管理の検査では総置き場数の直前・一致・直後の n を使う。保持した置き場の合計バイトを記録する。
7. **地図の対象**: 一番速い変種と、もう1つ（一番速いのが W 系ならもう一方の W、そうでなければ W4K4）。項目は P5kq と同じ節（SpeedOfLight・SourceCounters・MemoryWorkloadAnalysis(_Tables)・WarpStateStats・Occupancy・LaunchStats・SchedulerStats・InstructionStats・ComputeWorkloadAnalysis）。時間の内訳の参考の核は作らない。
8. 「倍精度で頭打ち」「Q が遅いのは同期のため」は測定に支えられた解釈（仮説）として扱う。
